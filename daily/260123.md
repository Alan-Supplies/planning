## 이슈 & 회고

### API 도메인 설계: /payments vs /orders 관점
- **상황:** 환불 API 설계 시 엔드포인트를 `/payments`와 `/orders` 중 어디에 둘지 고민
- **고민 포인트:**
  - `/payments/{id}/refund` - 결제 도메인 관점. 환불은 결제의 역행위
  - `/customer-orders/{id}/refund` - 주문 도메인 관점. 클라이언트는 주문 단위로 환불 요청
- **결정:** `POST /customer-orders/{id}/refund` 채택
  - 클라이언트는 주문번호로 환불 요청 (결제ID를 모름)
  - 하나의 주문에 여러 결제가 있을 수 있음 (부분결제, 추가결제)
  - 비즈니스 관점에서 "주문을 환불한다"가 자연스러움
- **배운 점:** API 설계 시 클라이언트가 알고 있는 정보와 비즈니스 흐름을 기준으로 도메인을 결정하는 것이 중요

> "API는 서버 내부 구조가 아닌, 클라이언트의 관점에서 설계해야 한다"
