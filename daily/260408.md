APISIX Route 배포 순서
1. YAML 수정 후 apply
kubectl apply -f apisix-route-pri.yaml
2. Sync 확인 — OpenLens 이벤트
해당 ApisixRoute 리소스의 Events에서 synced successfully의 Last seen 시각이 apply 이후인지 확인.

CLI로 확인:

kubectl describe apisixroute <route-name> | tail -15
3. Sync가 안 되는 경우
generation 비교:

kubectl get apisixroute <route-name> -o jsonpath='{.metadata.generation} {.status.conditions[0].observedGeneration}'
두 숫자가 같으면 sync 완료 (단, RBAC 이슈로 status 업데이트가 안 되면 이 값은 신뢰 불가 — 이벤트로 확인)
Ingress Controller 로그:

kubectl logs -n apisix <ingress-controller-pod> --tail=30
GlobalRule 등의 에러 retry loop가 route sync를 블로킹할 수 있음
이 경우 Ingress Controller 재시작:
kubectl rollout restart deployment apisix-ingress-controller -n apisix
4. 최종 검증 — 서버 로그에서 실제 헤더 확인
kubectl logs <app-pod> --tail=100 | grep "store_ids"
주의사항
kubectl context 확인: apply 전에 현재 context가 dev/prod 어디인지 반드시 확인. 잘못된 클러스터에 apply하면 불필요한 route 생성됨
APISIX 데이터 플레인 재시작은 불필요: Ingress Controller가 sync하면 자동 반영됨. Pod rollout은 Ingress Controller만 대상
Admin API (curl :9180)는 비추: API Key가 환경별로 다를 수 있고, Ingress Controller 방식과 route 저장 경로가 다를 수 있어 결과가 안 나옴

5. 최종 event 확인
kubectl get events --field-selector involvedObject.name=preppers-order-server-private-prod --sort-by='.lastTimestamp'
