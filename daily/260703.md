[프론트 미수신 원인 후보] 2026-07-03

백엔드 개발 서버에 직접 붙인 smoke test에서 두 곳 모두 받았다면, 백엔드 SSE fan-out은 정상입니다. 프론트에서만 안 된다면 거의 클라이언트 구독 조건/연결 유지/인증 전달 문제입니다.

가장 가능성 높은 건 이 순서입니다.

1. 프론트가 `EventSource`를 쓰면서 `Authorization` 헤더를 넣으려는 경우  
   브라우저 기본 `EventSource`는 custom header를 못 보냅니다. 개발 APISIX 설정은 `jwt-auth`가 `query: "token"`도 받게 되어 있어서, 기본 `EventSource`라면 URL에 `?token=...`이 붙어야 합니다. `@microsoft/fetch-event-source`를 쓰면 Authorization 헤더 방식도 가능합니다.

2. 탭이 백그라운드가 되면서 연결이 끊기는 경우  
   `@microsoft/fetch-event-source`는 기본적으로 페이지가 hidden 되면 연결을 닫는 동작이 있습니다. smoke test는 `openWhenHidden: true`를 넣었습니다. 프론트가 이 옵션 없이 쓰면 여러 포지션 화면 중 백그라운드/비활성 탭만 못 받을 수 있습니다.

```179:185:apps/kds/test/kds-order/sse-smoke2.html
        fetchEventSource(url, {
          signal: controller.signal,
          // 탭이 백그라운드여도 연결을 유지 (기본값은 hidden 시 연결 종료)
          openWhenHidden: true,
          headers: {
            Accept: 'text/event-stream',
```

3. 구독 `storeId`와 실제 주문 `storeId`가 다른 경우  
   서버는 SSE path의 `storeId`와 Redis 메시지의 `data.storeId`가 같을 때만 통과시킵니다. 포지션별 브라우저가 서로 다른 storeId나 stale token을 들고 있으면 해당 탭은 못 받습니다.

4. 이벤트 이름을 잘못 듣는 경우  
   서버 이벤트명은 `kds.orders.updated`입니다. `onmessage`만 보고 있거나 다른 이벤트명을 듣고 있으면 안 잡힐 수 있습니다.

5. 프론트가 `updatedAt` 비교로 이벤트를 버리는 경우  
   서버는 변경 snapshot을 보냅니다. 프론트가 `id + updatedAt` 기준으로 stale event를 무시한다면, 날짜 파싱/타임존/문자열 비교 문제로 실제 수신했는데 UI 반영만 안 될 수 있습니다.

프론트 개발자에게는 이 체크를 요청하면 빠릅니다.

- Network 탭에서 SSE 요청이 `200`이고 `text/event-stream`인지
- `kds.connected`, `kds.ping`, `kds.orders.updated` 중 어디까지 받는지
- 기본 `EventSource`면 URL에 `?token=`이 붙어 있는지
- `fetchEventSource`면 `openWhenHidden: true`가 있는지
- 수신 로그에는 있는데 UI만 안 바뀌는지
- SSE URL의 `storeId`와 urgent 변경 주문의 `storeId`가 같은지

특히 “여러 브라우저/포지션 중 랜덤하게 하나만 된다”는 설명은 백엔드 fan-out보다는 프론트에서 백그라운드 탭 연결이 닫히거나, 화면별 storeId/token/state 조건이 달라지는 쪽이 더 잘 맞습니다.

### SSE모니터링
[SSE Client 모니터링] 2026-07-03

네, 훨씬 빨라집니다. 지금 같은 이슈는 “서버가 안 보낸 건지, 특정 클라이언트가 연결이 끊긴 건지, storeId/token이 다른 건지, 프론트가 받고 버린 건지”를 구분하는 게 핵심이라서요.

추천하는 모니터링 정보는 이 정도입니다.

- 연결 생성/종료 로그: `storeId`, `requestId`, `user-agent`, `ip`, `referer`, `origin`
- 서버 pod 식별자: `HOSTNAME` 또는 pod name
- SSE client id: 연결마다 UUID 하나 생성
- 연결 지속 시간
- 마지막 ping 전송 시각
- 마지막 `kds.orders.updated` 전송 시각
- 전송한 이벤트 수
- Redis 메시지 수신 시 `storeId`, `orders.length`, `eventId`
- 각 Redis 메시지를 몇 개 SSE client에 fan-out 했는지

특히 이번 문제에는 “현재 붙어 있는 client 목록” API가 있으면 좋습니다. 예를 들면 dev 전용으로:

```text
GET /pri/v1/kds/debug/sse-clients
```

응답은 이런 형태면 충분합니다.

```json
[
  {
    "clientId": "uuid",
    "storeId": 56,
    "connectedAt": "2026-07-03T09:40:00.000Z",
    "lastPingAt": "2026-07-03T09:44:45.000Z",
    "lastOrdersUpdatedAt": "2026-07-03T09:44:12.000Z",
    "ordersUpdatedCount": 3,
    "userAgent": "...",
    "origin": "https://...",
    "referer": "https://...",
    "pod": "preppers-kds-server-xxx"
  }
]
```

그리고 Redis 메시지를 받았을 때 로그를 이렇게 찍으면 바로 판별됩니다.

```text
received redis message storeId=56 orders=1 eventId=56-...
fanout storeId=56 clients=2 eventId=56-...
```

이렇게 보면 프론트 개발자가 “안 된다”고 한 순간에:

- 해당 브라우저가 애초에 SSE 연결 중인지
- 같은 `storeId`로 붙었는지
- 어느 pod에 붙었는지
- Redis 이벤트를 받은 pod가 그 client에게 fan-out 했는지
- 중간에 연결이 닫혔는지

를 바로 볼 수 있습니다.

주의할 점은 운영 API로 열면 안 되고, 최소한 dev 전용이거나 내부 인증/권한으로 막는 게 좋습니다. 헤더 전체나 토큰은 절대 그대로 저장/노출하지 말고 `user-agent`, `origin`, `referer`, `storeId` 정도만 남기는 게 안전합니다.

[포지션 완료 검사(224-228) 효율성 판단] 2026-07-03

먼저 결론부터 말하면, **이 검사는 "방어 코드"로서는 꼭 필요하지만, 이름(`findPositionCompletableOrder`)이 암시하는 "완료 가능 여부 검증"으로서는 커버 범위가 좁습니다.**

### 검사 대상 코드

```224:234:apps/kds/src/module/kds-order/kds-order.service.ts
    const currentIndex = positionFlow.indexOf(order.currentPosition)

    if (currentIndex < 0) {
      throw new BadRequestException('처리할 수 없는 포지션입니다.')
    }

    const nextPosition = positionFlow[currentIndex + 1]
```

### 1. 연산 효율 — 문제 없음
`positionFlow`는 `store.positionOrder`(최대 5글자 `A~E`)에서 파생되므로 `indexOf`는 원소 ≤5개에 대한 O(n)입니다. 사실상 상수 시간이라 성능은 고려 대상이 아닙니다. (실제 비용은 `indexOf`가 아니라 그 앞의 `resolveStorePositionFlow` → `storeQueryRepository.findById` DB 조회인데, 이건 flow를 얻기 위해 어차피 필요한 쿼리라 정당합니다.)

### 2. 방어 코드로서는 "필요한" 검사
아래에서 `positionFlow[currentIndex + 1]`로 인덱스 산술을 하기 때문에, 만약 이 가드가 없다면 `indexOf`가 `-1`을 반환할 때 `positionFlow[-1 + 1] = positionFlow[0]`이 되어 **주문이 조용히 맨 첫 포지션으로 점프하는 데이터 오염 버그**가 발생합니다. 즉 이 `if`는 단순 장식이 아니라 아래 산술을 보호하는 실질적 가드라서 존재 자체는 타당합니다.

### 3. 실제로 이 검사가 걸리는 경우는 단 하나
- `currentPosition`은 enum 타입(`POSITION`, non-nullable)이라 항상 유효한 포지션 값입니다.
- 바로 위 219줄에서 `order.currentPosition === position`이 이미 보장됩니다.

따라서 `indexOf`가 `-1`이 되는 유일한 현실 시나리오는 **주문 진행 중에 매장 `positionOrder` 설정이 바뀌어 해당 주문의 현재 포지션이 flow에서 사라진 경우(설정 드리프트)** 뿐입니다.
반대로, `position` 파라미터에 잘못된 문자열이 들어오는 케이스는 219줄에서 `ConflictException`(409)으로 먼저 걸러지므로 이 224줄까지 오지 않습니다. → **이 검사는 "잘못된 입력 방어"가 아니라 "설정 드리프트 방어" 용도**입니다.

### 4. 정작 못 막는 것 (실질적 약점)
`findPositionCompletableOrder`는 이름과 달리 `findMutableOrder`와 완전히 동일합니다. `displayStatus`를 전혀 필터/검증하지 않습니다.

```329:337:apps/kds/src/module/kds-order/kds-order.service.ts
  private async findPositionCompletableOrder (storeId: number, id: number): Promise<KdsOrderEntity> {
    const order = await this.kdsOrderQueryRepository.findByStoreIdAndId(storeId, id)

    if (!order) {
      throw new NotFoundException('주문을 찾을 수 없습니다.')
    }

    return order
  }
```

그 결과:
- 이미 `COMPLETED`/`CANCELED`/`ON_HOLD` 상태인 주문이 `completePosition`에 들어와도, 그 주문의 `currentPosition`이 flow 안의 유효 값(예: 마지막 `PICKUP`)이면 `indexOf ≥ 0`이라 이 검사를 **통과**합니다.
- 그러면 완료 로직이 다시 실행되어 **중복 완료 / 중복 액션 로그**가 생성됩니다. `indexOf` 검사는 이 상태 기반 오완료를 전혀 막지 못합니다.

즉, 진짜 막아야 할 "완료 가능 여부"(상태 기반)는 이 검사의 범위 밖입니다.
