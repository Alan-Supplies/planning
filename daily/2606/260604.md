# KDS 주문 변경 API 후속 정리

## 목적
이번 작업에서는 프론트 연동을 위해 KDS 주문 변경 API의 1차 동작과 e2e 테스트를 추가했다.

현재 구현은 API 계약 확인과 화면 연동 가능성을 빠르게 검증하는 성격이 강하다. 실제 운영 기준으로는 도메인 규칙, 저장 책임, 포지션 flow, 실패 케이스 테스트를 보강해야 한다.

## 현재 구현된 범위
- 상태 변경 API
  - `PATCH /pri/v1/kds/orders/{order_id}/status`
  - `ACTIVE`, `ON_HOLD`, `CANCELED` 변경 허용
  - `COMPLETED` 직접 변경은 거부
- flag 변경 API
  - `cancel-requested`
  - `urgent`
  - `modify`
- 용기 변경 API
  - `plate`
  - `SERVICE_TYPE.HALL`, `SERVICE_TYPE.TOGO`만 허용
- 포지션 변경 API
  - `position/{position}/complete`
  - `position/{position}/revert`
  - 현재는 목업 flow 기준으로 동작
- 변경 API e2e 테스트
  - 정상 변경 케이스
  - 일부 잘못된 상태 변경 케이스
  - 다른 매장 주문 접근 제한 케이스

## 부족한 부분

### 1. 포지션 flow가 목업이다
현재 `PLATING -> SEARING -> SAUCE -> PICKUP` 고정 flow로 동작한다.

하지만 문서 기준 실제 포지션은 매장별로 `ABCDE`, `ABE`처럼 다르게 저장될 수 있다. `D=DRINK`는 독립 작업 공간이라 주문의 `currentPosition` 이동 대상에서 제외해야 한다.

따라서 현재 구현은 매장별 flow 설정을 반영하지 못한다.

### 2. 음료 완료 상태를 저장할 schema가 없다
`DRINK`는 독립 작업 공간인데, 현재 `kds_orders`에는 음료 완료 여부를 표현할 필드가 없다.

프론트에서 음료 완료 액션을 제공해야 한다면 별도 필드나 별도 테이블이 필요하다.

### 6. 실패 케이스 테스트가 부족하다
현재 e2e 테스트는 정상 흐름 중심이다.

추가 검증이 필요한 케이스는 다음과 같다.
- body 누락
- 잘못된 boolean value
- `plate`에 `DELIVERY` 전달
- 현재 포지션과 요청 포지션 불일치
- 첫 포지션에서 revert 요청
- 존재하지 않는 주문 변경
- 완료/취소된 주문에 대한 변경 허용 여부

### 7. action log가 연결되지 않았다
`kds_order_action_logs` 엔티티와 action type은 있지만, 변경 API에서 아직 저장하지 않는다.

운영 추적이 필요하면 상태 변경, flag 변경, 포지션 변경 시 action log를 함께 남겨야 한다.

### 8. SSE 전파와 변경 API의 연결이 없다
현재 변경 API는 DB row를 변경하지만, 변경 직후 SSE publish를 직접 수행하지 않는다.

현재 구조에서는 polling worker가 `updated_at` 변경분을 잡아 Redis publish하는 전략이다. 이 전략을 유지할지, 변경 API에서 즉시 publish까지 할지 결정이 필요하다.

### 9. 동시성 처리가 없다
여러 KDS 클라이언트가 동시에 같은 주문의 포지션을 완료할 수 있다.

현재 구현은 현재 포지션 검증 후 저장하지만, DB update 시점의 원자적 조건 검증은 없다. 실제 운영에서는 조건부 update나 transaction 기준을 정해야 한다.

-> 업무 방식상 동시 완료를 할 수 없다. 진행중인 단계만 완료가 가능하다.
문제되는 케이스는 픽업 포지션의 강제 완료와 진행중 포지션의 완료가 경쟁 붙었을 경우다. 현실적으로 거의 발생하지 않는다.(2년간 문제된 적 없다.)

## 앞으로 해야 할 일

### 4. 매장별 position flow 반영
- 매장별 flow 저장 위치를 확정한다.
- `ABCDE`, `ABE` 같은 flow 값을 서버에서 해석한다.
- `D=DRINK`는 `currentPosition` 이동 대상에서 제외한다.
- 마지막 이동 대상 완료 시 `COMPLETED` 처리한다.

### 5. 음료 완료 모델 결정
- `kds_orders`에 음료 완료 필드를 추가할지 결정한다.
- 별도 작업 상태 테이블을 둘지 결정한다.
- 음료 완료 API가 별도로 필요한지 결정한다.

### 6. 테스트 보강
- API별 실패 케이스를 추가한다.
- 포지션 flow별 e2e를 추가한다.
- service 단위 테스트에서 전이 규칙을 검증한다.
- repository 테스트에서 store scope와 조건부 update를 검증한다.

### 7. action log 연결
- 변경 전/후 값을 `changeJson`에 남긴다.
- position, status, flag별 action type을 매핑한다.
- request id를 어떻게 전달받을지 결정한다.

### 8. 동시성 정책 결정
- 같은 주문에 대한 중복 complete 요청 처리 방식을 정한다.
- 현재 포지션이 기대값일 때만 update되는 조건부 update를 검토한다.
- 실패 시 응답 코드를 정한다.

## 추천 진행 순서
1. DTO와 API 계약을 먼저 정리한다.
2. command repository를 분리한다.
3. 현재 목업 position flow를 별도 service로 빼고 테스트한다.
4. 매장별 flow 저장소를 연결한다.
5. 실패 케이스 e2e를 보강한다.
6. action log와 SSE 전략을 확정한 뒤 붙인다.

## 현재 상태 요약
현재 코드는 프론트 연동과 기본 API 흐름 검증에는 사용할 수 있다.

다만 운영 기준 구현으로 보기에는 아직 포지션 flow, validation, repository 책임, 동시성, action log, SSE 전파 정책이 부족하다. 다음 단계에서는 기능을 더 늘리기보다 현재 API의 계약과 저장 책임을 먼저 정리하는 것이 좋다.
