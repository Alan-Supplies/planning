# 옵션 매핑: 두 종류 주문에 대한 이해

> 목적: 주문 옵션이 **두 가지 서로 다른 방식**으로 들어온다는 사실과, 그 둘이 "왜 다를 수밖에 없는지"를 공유해 이후 논의에서 오해를 없앤다.
> 범위: 신규 주문 생성 경로인 `POST /preppers-order` 기준. (`POST /customer-orders` 는 레거시이며 본 문서 논외)

## 1. 핵심 한 줄

**옵션을 "식별하는 방식"이 근본적으로 다르기 때문에, `food_option` 기반 주문과 `platform_option` 기반 주문은 다를 수밖에 없다.**

값이 다른 정도가 아니라 **해석 경로 자체가 다른 두 흐름**이다.

## 2. 두 종류

| 구분 | food_option 기반 | platform_option 기반 |
|---|---|---|
| 발생 | `platform = PREPPERS` (POS 자체 · 키오스크 주문) | `platform ≠ PREPPERS` (배달 플랫폼) |
| 클라이언트가 아는 것 | **food_option.id 를 안다** | food_option.id 를 **모른다.** 옵션 **이름(name)** 만 안다 |
| 식별자 | 숫자 ID (안정적, 1:1) | 문자열 name (불안정, 매칭 필요) |
| 해석 단계 | 없음 (직접 사용) | `name → platform_option → food_option.id` 간접 해석 |
| 실패 가능성 | 없음 (항상 확정) | 있음 (미매핑 가능) |
| 저장 결과 | 항상 `option_id` 채움 | `option_id` 채움 **또는** null + 이름 스냅샷 |

> 정리: 식별자 종류 / 해석 단계 유무 / 실패 가능성 / 저장 결과 — 네 축이 모두 다르다.
> 그래서 DTO·분기를 어떻게 포장하든, 한쪽에만 의미 있는 필드(name·nullable·실패 처리)가 끌려올 뿐 "두 경로"라는 본질은 사라지지 않는다.

## 3. 매핑 흐름

```text
[ 주문 생성 (POST /preppers-order) ]
            │
   platform 값으로 분기
            │
 ┌──────────┴───────────────────────────────┐
 │ platform == PREPPERS                      │  → 옵션이 food_option_id 를 가짐
 │ (POS 자체 · 키오스크)                      │     → customer_order_food_option.option_id = 그 값
 └───────────────────────────────────────────┘     → 미매핑 없음 (항상 확정)

 ┌───────────────────────────────────────────┐
 │ platform != PREPPERS (배달 플랫폼)         │  → 옵션이 name 만 가짐
 │                                            │     → name 으로 platform_option 조회
 │                                            │        ├─ row 있고 option_id != null
 │                                            │        │     → option_id = platform_option.option_id
 │                                            │        └─ row 없음 또는 option_id == null (미매핑)
 │                                            │              → option_id = null + 옵션 이름 스냅샷 저장
 └───────────────────────────────────────────┘
```

## 4. 관련 데이터 구조 (현재 lib 기준)

라이브러리: `@suppliesfitness/preppers-kds-lib` (`2.14.0-next-kds.4` 에서 `platform_option` 추가됨)

### platform_option (배달 옵션 → food_option 매핑 테이블)
`PlatformOptionEntity` — 레거시 `options` 테이블을 대체한다.

- `name` (varchar) — **이 값으로 조회한다**
- `option_id` (nullable) — 매핑된 `food_option`(`option` 테이블) id. **null 이면 아직 매핑되지 않음**
- `option` — `FoodOptionEntity` 관계

> `platform` 컬럼이 없으므로 매칭은 **name 단일 키**로 이뤄진다. (name 정규화 규칙은 별도 정의 대상)

### food_option (`option` 테이블)
`FoodOptionEntity` — 프레퍼스 표준 옵션. 이름은 직접 컬럼이 아니라 `food_option_detail` 에 국가별로 존재.

### customer_order_food_option (주문 옵션 저장)
`CustomerOrderFoodOptionEntity`

- `option_id` — `food_option` 참조 (DB FK 제약 없음: `createForeignKeyConstraints: false`)
- 옵션 관계 `option → FoodOptionEntity`

## 5. 저장 모델 합의 (예정 변경 포함)

`customer_order_food_option.option_id` 에는 **항상 food_option id 만** 들어간다. platform_option 기반은 매핑 결과를 넣고, 매핑 실패 시 null.

합의했으나 **아직 lib/스키마에 반영되지 않은 변경** (작업 예정):
- `option_id` → **nullable** 로 변경
- `option_name`(스냅샷) 컬럼 **추가** — **매핑 실패 시에만** 저장 (성공 시 이름은 `food_option_detail` 조회로 표시)

## 6. 결정 사항 요약

- `POST /customer-orders` 와 `POST /preppers-order` 는 **통합하지 않는다.** (`/customer-orders` 는 레거시 유지)
- 옵션 식별 분기는 **주문 단위 `platform`** 으로 한다. (`PREPPERS` = food_option 기반 / 그 외 = platform_option 기반)
- platform_option 조회 키는 **name**.
- `customer_order_food_option.option_id` 는 **food_option 으로만** 채우고, 실패 시 **null + 이름 스냅샷**.

## 7. 용어 주의 (혼동 방지)

- `option` 테이블 = **food_option** = 프레퍼스 표준 옵션
- `options` 테이블 = 레거시 (deprecated 예정), `platform_option` 으로 대체
- `platform_option` 테이블 = 배달 옵션 name → food_option 매핑용 신규 테이블
- 이름이 비슷하므로 문서/대화에서는 **food_option / platform_option** 으로 부른다.
