[이벤트전환계획] 2026-07-02 12:45

점진적으로 가려면 **현재 `kds-polling`은 유지**하고, 먼저 “주문 취소 → KDS read model 반영” 부분만 이벤트 기반으로 분리하는 게 좋습니다.

## 1단계: 현재 구조 보강

먼저 POS는 직접 `kds_order`를 건드리지 않고, **order-server에 주문 취소 요청**만 하도록 정리합니다.

```text
POS
  → order-server 취소 API
  → customer_order.canceled_at 저장
  → kds_order.display_status = CANCELED 갱신
  → 기존 kds-polling이 KDS로 전달
```

이 단계의 목적은 이벤트 도입 전에도 취소가 KDS에 정상 반영되는지 검증하는 것입니다. 책임은 완벽히 분리되지 않지만, POS가 KDS를 아는 구조는 제거됩니다.

## 2단계: 이벤트 계약 정의

`OrderCanceled` 이벤트 구조를 먼저 고정합니다. 소유권은 `order-server`가 갖고, 타입은 공용 lib로 분리할 수 있습니다.

```json
{
  "eventId": "uuid",
  "eventType": "OrderCanceled",
  "version": 1,
  "occurredAt": "2026-07-02T03:45:00.000Z",
  "orderId": 123,
  "storeId": 41
}
```

이 단계에서는 아직 실제 consumer를 붙이지 않아도 됩니다. 이벤트 필드가 KDS뿐 아니라 다른 consumer도 사용할 수 있는 주문 도메인 표현인지 검증합니다.

## 3단계: Redis Streams 발행 추가

order-server가 주문 취소 성공 후 Redis Stream에 `OrderCanceled`를 발행합니다.

```text
order-server
  → customer_order.canceled_at 저장
  → 트랜잭션 성공
  → Redis Stream XADD OrderCanceled
```

처음에는 `kds_order` 직접 갱신도 유지합니다. 즉, 이벤트는 “그림자 발행”으로 시작해서 운영 리스크를 줄입니다.

## 4단계: KDS projection consumer 추가

별도 worker를 추가합니다.

```text
kds-projection-consumer
  → Redis Stream에서 OrderCanceled consume
  → orderId/storeId 기준 kds_order 조회
  → display_status = CANCELED 갱신
```

이때 기존 `kds-polling`은 그대로 둡니다.

```text
kds_order 변경
  → 기존 kds-polling
  → Redis Pub/Sub
  → KDS_SERVER SSE
  → KDS 클라이언트
```

## 5단계: 이중 처리 검증 후 책임 이전

consumer가 안정적으로 동작하는지 확인한 뒤, order-server의 `kds_order` 직접 갱신을 제거합니다.

최종 목표 구조는 이렇게 됩니다.

```text
POS
  → order-server 취소 요청
  → customer_order.canceled_at 저장
  → OrderCanceled 이벤트 발행
  → kds-projection-consumer
  → kds_order.display_status = CANCELED
  → 기존 kds-polling
  → KDS SSE
```

## 6단계: 장기 개선

이후 필요하면 `kds-polling`도 줄일 수 있습니다. projection consumer가 `kds_order` 갱신 후 바로 KDS용 이벤트까지 발행하면 됩니다.

다만 첫 전환에서는 추천하지 않습니다. **1차 목표는 취소 projection만 이벤트 기반으로 분리하고, KDS 전달 경로는 기존 polling을 유지하는 것**이 가장 안전합니다.
