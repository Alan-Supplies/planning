# 신규 매장 오픈 업무 자동화 논의

## 논의 목적

신규 매장 오픈 및 관리자 권한 설정 업무를 반복할 때 다음 두 방식 중 어떤 방식을 사용할지 결정한다.

1. 이 폴더의 문서를 AI에게 제공하고 작업을 요청한다.
2. 회사 업무 규칙과 검증 절차를 Codex 스킬로 만든다.

## 현재 상황

- 이 업무는 담당자가 DBMS에서 직접 여러 번 처리해 온 반복 업무다.
- AI에게 맡긴 것은 이번이 두 번째이며, AI 사용 횟수가 적을 뿐 업무 사례가 적은 것은 아니다.
- 첫 AI 작업은 관련 엔터티가 있는 애플리케이션 코드베이스에서 수행해 스키마와 비즈니스 규칙을 찾기 쉬웠다.
- 현재 저장소는 개인 지식창고라 애플리케이션 코드베이스의 엔터티, 마이그레이션, 서비스 로직을 직접 참조하기 어렵다.
- 이 저장소에 정리한 첫 사례는 2026-07-21 송도학원가점 요청이다.
- 요청 내용은 Slack에 있고 실제 상태는 운영 DB 조회로 확인해야 한다.
- 운영 DB의 읽기와 쓰기 권한이 분리돼 있다.
- `employee_store_access`에는 `(employee_id, store_id)` 유니크 제약이 없어 중복 방지 로직이 필요하다.
- 매장 생성, OWNER 생성, 관리자 권한 추가 중 이미 완료된 단계가 요청마다 다를 수 있다.
- 기존 수작업 경험은 담당자에게 축적돼 있지만, AI가 재사용할 수 있는 형태로 아직 구조화되지 않았다.

## 선택지 비교

| 기준 | 문서 참고 후 AI 요청 | Codex 스킬 |
| --- | --- | --- |
| 시작 비용 | 낮음. README와 사례 SQL만 유지하면 됨 | 높음. 트리거, 절차, 스크립트, 검증을 설계하고 테스트해야 함 |
| 변경 대응 | 문서를 바로 수정하면 됨 | 스킬과 참조 문서 또는 스크립트를 함께 수정하고 재검증해야 함 |
| 실행 일관성 | 요청 프롬프트와 AI 판단에 따라 달라질 수 있음 | 정해진 순서와 검증 규칙을 강제하기 쉬움 |
| 운영 DB 안전성 | 사람이 매번 실행 범위를 확인하기 쉬움 | 잘 설계하면 안전하지만, 잘못된 자동화가 반복될 위험도 큼 |
| 반복 작업 효율 | 매번 문서 위치와 요청 내용을 알려줘야 함 | 짧은 요청만으로 동일한 절차를 재사용할 수 있음 |
| 예외 처리 | 초기처럼 예외가 많은 시기에 유연함 | 규칙이 안정된 뒤에 더 효과적임 |
| 유지보수 주체 | 업무 담당자가 Markdown과 SQL을 관리 | 업무 규칙과 Codex 스킬 구조를 모두 이해해야 함 |
| 권한 문제 해결 | 해결하지 않음 | 스킬도 DB 권한과 사용자 승인을 대신할 수 없음 |

## 권장안

**문서를 업무 지식의 원본으로 유지하면서, 지금부터 최소 기능 스킬을 만든다.**

이유는 다음과 같다.

- 업무 자체는 이미 여러 번 반복됐으므로 자동화 투자 근거가 충분하다.
- 개인 지식창고에서는 코드베이스 문맥을 매번 새로 찾기 어렵기 때문에, 필요한 문맥을 선택적으로 로드하는 스킬의 효용이 크다.
- DB 조회, 대상 식별, 중복 검사, 안전한 SQL 생성은 반복적이고 오류 비용이 높아 낮은 자유도의 스크립트가 적합하다.
- 실제 쓰기 실행은 우선 사람에게 남겨 두면, 권한과 승인 정책이 완성되지 않아도 읽기 검증과 SQL 생성부터 자동화할 수 있다.
- 문서는 사람과 AI가 함께 읽는 업무 원본으로 두고, 스킬은 문서를 읽고 정해진 순서로 실행하는 도구로 역할을 분리할 수 있다.

즉, 문서와 스킬 중 하나를 고르는 것이 아니라 다음 두 계층을 함께 사용한다.

| 계층 | 역할 |
| --- | --- |
| `docs/preppers/신규매장오픈/` | 업무 정책, 체크리스트, 사례 SQL, 의사결정 이력의 원본 |
| `skill/open-easyprep-store/` | 문서 로딩, Slack 확인, DB 사전 조회, SQL 생성, 사후 검증의 반복 실행 절차 |

## 코드베이스가 없는 문제를 다루는 방법

스킬이 애플리케이션 코드베이스 전체를 복제하거나 항상 필요로 하게 만들지 않는다. 필요한 문맥을 세 종류로 나눈다.

1. **운영 DB에서 확인할 사실**
   - 실제 테이블과 컬럼
   - 현재 매장, 직원, 접근 권한 상태
   - 인덱스와 외래키
2. **이 저장소에 명시할 업무 규칙**
   - 생성 및 검증 순서
   - 상태값의 의미
   - 중복 처리와 롤백 정책
   - 민감정보 취급과 승인 경계
3. **코드베이스가 있을 때만 교차 확인할 내용**
   - 애플리케이션 레벨 기본값
   - ORM 훅과 서비스 로직
   - ID 또는 비밀번호 생성 규칙

구조 확인은 매번 `information_schema`와 읽기 전용 쿼리로 수행해 스키마 드리프트를 감지한다. 코드베이스에서만 알 수 있는 비즈니스 불변조건은 최초 스킬 작성 시 최소 범위로 추출해 `references/operation-policy.md`에 기록한다. 코드베이스 경로를 사용할 수 있으면 교차 확인하되, 없어도 읽기 검증과 SQL 생성은 가능해야 한다.

코드베이스를 참조하지 못해 확신할 수 없는 기본값이나 생성 규칙이 발견되면 추정하지 않고 SQL 생성을 중단해 사용자 확인 항목으로 남긴다.

## 스킬 도입 전까지의 운영 방식

신규 요청마다 이 폴더를 AI에게 알려주고 다음 정보만 제공한다.

- Slack 요청 링크
- 대상 매장명
- 요청 범위: 매장 생성, OWNER 생성, 관리자 권한 추가 중 해당 항목
- 실제 변경 실행까지 원하는지, SQL 작성과 검증까지만 원하는지

AI는 다음 순서로 처리한다.

1. [`README.md`](./README.md)의 체크리스트를 읽는다.
2. Slack 원문과 스레드에서 요청자, 매장, 대상자, 요청 범위를 확인한다.
3. 운영 DB 읽기 전용 계정으로 현재 상태를 조회한다.
4. 이미 완료된 단계와 필요한 변경을 분리한다.
5. 사례별 SQL을 이 폴더에 생성한다.
6. SQL은 기본적으로 트랜잭션과 `ROLLBACK`을 포함해 작성한다.
7. 쓰기 실행 전 대상 행, 영향 행 수, 중복 여부를 사용자에게 보여준다.
8. 쓰기 권한과 명시적 승인이 있을 때만 반영한다.
9. 반영 후 읽기 전용 조회로 최종 상태를 검증한다.

## 스킬 MVP 범위

첫 버전은 운영 DB 쓰기를 자동화하지 않는다. 다음 범위만 지원한다.

- 이 폴더의 README와 요청별 SQL을 읽는다.
- Slack 링크에서 요청 범위와 대상자를 추출한다.
- 운영 DB 읽기 전용 계정으로 현재 상태와 스키마를 조회한다.
- 완료된 단계와 필요한 변경을 구분한다.
- 중복 실행에 안전하고 기본값이 `ROLLBACK`인 SQL을 생성한다.
- 예상 변경 행과 검증 결과를 요약한다.
- 사람이 SQLTools 또는 승인된 쓰기 세션에서 실행한 뒤 사후 검증을 수행한다.

다음 항목은 규칙이 확정된 뒤 두 번째 단계로 추가한다.

- `store` 자동 생성
- OWNER 계정과 초기 비밀번호 자동 생성
- 운영 DB 쓰기 실행
- 실패 시 자동 복구

## 향후 스킬 구성안

스킬로 전환한다면 설명만 담은 거대한 `SKILL.md`보다 절차와 결정론적 스크립트를 분리한다.

```text
open-easyprep-store/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   ├── inspect_context.sh
│   ├── generate_change_sql.py
│   └── verify_change.sh
└── references/
    ├── schema-minimum.md
    └── operation-policy.md
```

- `SKILL.md`: 입력 확인, 읽기 검증, 변경 승인, 사후 검증 순서만 간결하게 정의한다.
- `scripts/inspect_context.sh`: `information_schema`와 실제 데이터를 이용해 매장, OWNER, 관리자, 기존 권한을 읽기 전용으로 조회한다.
- `scripts/generate_change_sql.py`: 사례별 값으로 중복 실행에 안전한 SQL을 생성한다.
- `scripts/verify_change.sh`: 반영 후 기대 행 수와 상태를 검증한다.
- `references/schema-minimum.md`: 코드베이스 없이 업무를 이해하는 데 필요한 최소 엔터티 관계만 기록한다. 실제 구조는 실행 시 DB에서 다시 확인한다.
- `references/operation-policy.md`: 코드베이스에서 추출한 비즈니스 불변조건과 운영 권한, 승인, 민감정보, 롤백 정책을 기록한다.

운영 DB 변경 스크립트는 자동 커밋하지 않고, 기본값을 미실행 또는 `ROLLBACK`으로 둔다. 스킬은 사용자의 명시적 승인 없이 쓰기 쿼리를 실행하지 않는다.

## 사례 축적 규칙

사례별 SQL은 이 폴더에 저장하되, 파일명은 매장명을 사용한다.

```text
신규매장오픈/
├── README.md
├── DISCUSSION.md
├── 송도학원가점.sql
└── <다음매장명>.sql
```

새 사례에서 발견한 공통 규칙은 README와 스킬 참조 문서에 반영하고, 특정 매장에만 적용되는 값과 결과는 해당 SQL에 남긴다. 문서가 업무 원본이며 스킬이 그 문서를 실행 절차로 사용하므로, 동일한 규칙을 두 곳에 서로 다르게 복사하지 않는다.

## 남은 논의

- 스킬을 이 저장소의 `skill/`에 둘지 개인 Codex 스킬 디렉터리에 설치할지
- 최초 스킬 작성 시 기존 애플리케이션 코드베이스에서 어떤 엔터티와 비즈니스 규칙을 가져올지
- 애플리케이션 코드베이스의 선택적 로컬 경로를 설정으로 받을지
- 쓰기 작업은 사람이 SQLTools에서 실행할지, AI가 승인 후 CLI로 실행할지
- 사례별 SQL을 저장소에 계속 보관할지, 완료 후 별도 이력 폴더로 이동할지
- 초기 비밀번호 같은 민감정보를 어떤 채널로 전달하고 어디에도 남기지 않을지
- 신규 매장 생성까지 자동화 범위에 포함할지, 관리자 권한 설정만 자동화할지
