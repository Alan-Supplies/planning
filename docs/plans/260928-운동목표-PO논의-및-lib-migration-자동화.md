# 운동 목표 PO 논의 및 gymboxx-lib 마이그레이션 자동화 계획

작성: 2026-09-28

## 오늘의 우선순위

1. 새 목표 생성·목표 삭제 때 진척을 어떻게 처리하고 안내할지 PO와 결정한다.
2. 직접 입력 목표의 분류가 부정확하거나 매칭되지 않을 때의 사용자 흐름을 PO와 결정한다.
3. `gymboxx-lib`의 스키마 마이그레이션 자동화를 시작하기 위한 선행 조건과 도입 단계를 확정한다.
4. 위 결정이 끝난 뒤 운동 목표 API 대표 흐름 검증을 재개한다.

## 1. 새 목표 생성과 목표 삭제

### 현재 확인된 동작

- 최신 운동 목표 개발 브랜치에서 새 목표를 생성하면 기존 `IN_PROGRESS` 목표는 `ENDED`, 연결 미션은 `CLOSED`가 된다.
- 새 미션은 새 `assigned_at` 이후에 끝난 운동만 집계한다. 따라서 기존 운동 기록 자체는 남지만 새 목표의 미션 진척은 0부터 시작한다.
- 목표 완료 API는 있지만 목표 삭제 API는 아직 없다.
- 제품 문서에서는 목표 삭제 정책이 미확정이다. 과거 초안에는 목표를 물리 삭제하고 연결 미션도 함께 삭제하는 안이 남아 있다.
- DB 관계는 목표가 물리 삭제되면 연결 미션이 `CASCADE` 삭제되는 구조다.

### PO에게 결정받을 항목

| 결정 | 선택지 | 권고안 |
|---|---|---|
| 새 목표 생성 시 기존 목표 | 기존 목표·미션 이력 보존 / 모두 삭제 | `ENDED`·`CLOSED`로 보존 |
| 새 목표의 진척 | 이전 운동 실적 승계 / 새 미션 부여 시점부터 0 | 0부터 시작 |
| 같은 날 새 목표 생성 전 운동 | 새 목표에 포함 / 제외 | 제외. 미션 부여 전 수행은 새 미션의 수행이 아님 |
| 확인 시점 | 생성 완료 후 안내 / 생성 확정 전 확인 | 생성 확정 전 확인 |
| 목표 삭제 | 소프트 삭제·사용자 화면에서 숨김 / 물리 삭제 | 소프트 삭제. 분석·오조작 대응을 위해 이력 보존 |
| 삭제 후 복구 | 가능 / 불가 | 소프트 삭제를 택하더라도 초기 버전은 사용자 복구 불가로 안내 |

### 제안 문구

새 목표 생성 확인:

> 새 목표를 만들면 현재 목표와 미션은 종료되고, 새 미션 진척도는 0부터 시작해요. 기존 운동 기록은 삭제되지 않아요.

목표 삭제 확인 — 소프트 삭제 권고안을 택할 때:

> 목표를 삭제하면 이 목표와 미션 진행 내역이 목록에서 사라지고 복구할 수 없어요. 기존 운동 기록은 삭제되지 않아요.

목표 삭제 확인 — 물리 삭제를 택할 때:

> 목표를 삭제하면 이 목표의 미션 진행 내역도 함께 영구 삭제되며 복구할 수 없어요. 기존 운동 기록은 삭제되지 않아요.

### 결정 후 구현·검증

- 서버: 새 목표 생성과 기존 목표 종료가 한 트랜잭션인지 유지한다.
- 서버: 삭제 정책에 맞는 상태·조회·통계 제외 규칙을 추가한다.
- 앱: 새 목표 생성 확정 전과 목표 삭제 확정 전에 결정된 문구를 표시한다.
- 테스트: 기존 목표 상태, 기존 미션 상태, 새 미션 0%, 운동 기록 보존, 같은 날 경계, 재요청을 검증한다.

## 2. 직접 입력 목표 분류 실패

### 현재 확인된 동작

- 직접 입력 문구는 규칙 기반으로 다이어트·근력·건강·체력·자세 중 하나로 분류된다.
- 매칭 점수가 0이어도 요청은 실패하지 않는다. 현재는 무조건 `근력 증가`로 저장된다.
- 동점 또는 낮은 점수도 한 목적을 골라 목표 생성을 성공시킨다.
- 저신뢰·매칭 실패는 `goal_intent.uncertain` 로그만 남고 사용자에게는 알려지지 않는다.
- 공개 분류 함수는 선택된 목적만 반환하므로 현재 목표 생성 흐름에서는 신뢰도나 매칭 실패 여부를 구분할 수 없다.

### PO에게 결정받을 항목

| 상황 | 선택지 | 권고안 |
|---|---|---|
| 고신뢰 매칭 | 자동 생성 / 사용자 확인 | 자동 생성 |
| 저신뢰·동점 | 임의 목적 생성 / 생성 차단 / 목적 재질문 | 목적 재질문 |
| 매칭 없음 | 근력으로 생성 / 생성 차단 / 목적 재질문 | 목적 재질문 |
| 재질문 표현 | 내부 목적 코드 노출 / 사용자용 5개 목적 문구 | 사용자용 문구 |
| 사용자가 선택하지 않음 | 기본값 저장 / 카드 선택으로 복귀 / 취소 | 카드 선택 또는 취소 |

제안 흐름:

1. 사용자가 목표 문구를 직접 입력한다.
2. 고신뢰면 현재처럼 바로 생성한다.
3. 저신뢰·동점·매칭 없음이면 “어떤 변화에 더 가까운가요?”와 사용자용 목적 5개를 보여준다.
4. 사용자가 고른 목적과 원문 목표 문구를 함께 저장한다.
5. 분류 결과·신뢰도·사용자 수정 여부를 계측해 사전을 개선한다.

이 방식이면 잘못된 기본값으로 미션이 생성되는 문제를 막으면서 직접 입력 자체는 유지할 수 있다.

### 결정 후 필요한 변경

- 분류 내부 결과에서 `intent`, `confidence`, `source`를 목표 생성 서비스가 받을 수 있게 한다. 점수 전체를 앱에 노출할 필요는 없다.
- `high`가 아닌 경우 바로 저장하지 않고 확인 응답을 반환하거나, 분류 미리보기 API와 확정 API를 분리한다.
- 사용자가 확정한 목적만으로 미션을 생성한다.
- 테스트 입력을 `고신뢰`, `저신뢰`, `동점`, `매칭 없음`, `금지어`로 나눈다.
- 직접 입력 원문이 로그에 남으므로 개인정보·건강정보 로그 보존 기간과 접근 범위를 확인한다.

## 3. gymboxx-lib 마이그레이션 자동화

### 현재 상태

- `main` 푸시는 npm 배포가 아니다. 현재 npm 배포는 버전 태그 푸시가 `publish.yaml`을 실행하는 방식이다.
- `main` 푸시 워크플로는 npm 캐시만 준비한다.
- `src/sqlv4`는 자동 러너가 아니라 사람이 `local → dev → 운영` 순으로 실행하는 SQL 런북이다.
- DB에는 Flyway 계열 실행 이력 테이블이 없어 어느 환경에 어떤 파일이 적용됐는지 자동 판정할 수 없다.
- 현재 작업 트리에는 SQL 파일이 109개 있고, 과거 파일에는 비멱등 `CREATE TABLE`·`ALTER TABLE`, 중복 버전 묶음, 과거 번호 정정 사례가 있다. 기존 파일 전체를 자동 재생하면 안 된다.
- npm 패키지의 `files`에는 `src/sqlv4`가 포함되지 않는다. 다만 GitHub Actions가 저장소 checkout을 기준으로 실행한다면 패키지 포함은 필수가 아니다.
- 현재 lib publish job에는 DB 네트워크 연결, AWS OIDC, DB 자격 증명, 마이그레이션 승인 단계가 없다.

### 먼저 확정할 선행 조건

| 항목 | 확인할 내용 | 완료 증거 |
|---|---|---|
| 자동화 트리거 | `main` 머지인지, `main`에서 만든 stable tag인지 | 이벤트와 환경 매핑 문서 |
| 대상 환경 | dev 자동 / prod 자동 또는 승인 후 자동 | 환경별 정책 |
| 실행 위치 | GitHub-hosted runner가 DB에 접근 가능한지, 아니면 VPC 내부 CodeBuild·ECS Task·self-hosted runner인지 | dev DB 연결 테스트 |
| 인증 | Secrets Manager 위치, 실행 역할, 최소 권한 DB 계정 | 비밀값 없는 연결 성공 |
| 기준선 | dev·prod 실제 스키마와 적용된 `sqlv4` 목록 | 환경별 baseline 승인 기록 |
| 이력 저장 | Flyway 또는 동등한 `schema_migrations` 테이블 | 버전·checksum·실행 시각·성공 여부 조회 |
| 파일 규칙 | 기준선 이후 고유하고 단조 증가하는 ID, 배포된 파일 수정 금지 | CI 중복·checksum 검사 |
| 배포 순서 | DB 확장 → lib 발행 → 소비 서버 갱신 순서 | 릴리스 흐름도 |
| 실패 정책 | MySQL DDL의 암묵적 커밋을 고려한 중단·수동 복구 | 실패 runbook과 롤백 SQL |
| 승인·책임 | prod 승인자, 실패 대응자, 알림 채널 | GitHub Environment와 담당자 |

### 권고 구조

- `main` 머지 자체보다 **main 커밋에서 만든 stable tag**를 운영 릴리스 기준으로 삼는다.
- dev는 별도 prerelease 흐름으로 자동 적용하고, prod는 GitHub Environment 승인을 받은 뒤 자동 실행한다.
- DB가 사설망이면 GitHub-hosted runner에 DB를 노출하지 말고 VPC 내부 실행기에서 마이그레이션을 실행한다.
- 기존 109개 파일을 소급 실행하지 않는다. dev·prod 스키마를 대조해 기준선을 한 번 등록하고, 기준선 이후 파일부터 자동 관리한다.
- 마이그레이션은 전용 이력 테이블과 DB advisory lock을 사용해 한 번만 실행한다. 재실행은 no-op이어야 한다.
- 신규 변경은 expand/contract 방식으로 작성한다. 컬럼·테이블을 먼저 추가하고 소비 서버가 전환된 뒤 제거를 별도 릴리스로 나눈다.
- npm 발행과 DB 변경은 같은 릴리스 상태로 묶되, 별도 job으로 둔다. 마이그레이션 실패 시 소비 서버 배포가 진행되지 않아야 한다.

### 단계별 계획

#### 0단계 — 기준선 조사

1. dev·prod `information_schema`를 엔티티 및 `sqlv4`와 대조한다.
2. 환경별 이미 적용된 파일과 부분 적용된 파일을 기록한다.
3. 앞으로 사용할 첫 자동 마이그레이션 ID와 baseline 값을 정한다.
4. “main 배포”가 stable tag 발행을 뜻하는지 확정한다.

#### 1단계 — 러너와 이력 기반 구축

1. 마이그레이션 도구를 선택한다. 표준 이력·checksum·lock을 제공하는 Flyway를 우선 검토한다.
2. VPC 내부 실행 경로와 Secrets Manager 기반 DB 인증을 구성한다.
3. dev·prod에 baseline 이력만 등록한다. 이 단계에서 기존 SQL을 재실행하지 않는다.

#### 2단계 — CI 검증

1. 중복 ID, 배포된 파일 변경, checksum 변경을 차단한다.
2. 임시 MySQL에 baseline 이후 마이그레이션을 적용해 문법과 재실행 no-op을 검증한다.
3. `DROP`, 컬럼 축소, `NOT NULL`, 대량 `UPDATE` 등 위험 변경은 별도 승인 대상으로 표시한다.

#### 3단계 — dev 자동화

1. dev 대상 새 마이그레이션을 자동 실행한다.
2. 사후 검증 쿼리와 운동 목표 스모크 테스트를 실행한다.
3. 실패 시 이후 lib·소비 서버 배포를 중단하고 알림과 실행 로그를 남긴다.

#### 4단계 — prod 승인 후 자동화

1. GitHub Environment 승인 뒤 prod 마이그레이션을 실행한다.
2. 적용된 버전·checksum·소요 시간·검증 결과를 배포 기록으로 남긴다.
3. 성공한 경우에만 소비 서버가 새 lib 버전을 사용하도록 진행한다.

### 자동화 완료 조건

- 같은 릴리스를 두 번 실행하면 두 번째 실행은 변경 없이 성공한다.
- 동시 실행 두 건 중 하나만 lock을 획득한다.
- dev·prod 각각 적용 버전과 checksum을 DB에서 조회할 수 있다.
- 마이그레이션 실패 시 npm 소비 서버 배포가 진행되지 않는다.
- prod 실행에는 명시적 승인과 담당자·실행 로그가 남는다.
- 목표 카드·미션 관련 스키마를 적용한 뒤 대표 API 스모크 테스트가 통과한다.
