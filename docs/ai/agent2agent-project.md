# 에이전트 상호작용 프로젝트 — 정리 (2026-09-04)

## 1. 출발점과 그 수정

처음 질문: "agent to agent로 의미 있는 걸 만들자, 범위 무제한."

무제한 범위 + "만들어야 한다"는 의무감 조합은 동기가 안 붙음. 실제로 몰입한 이력은
에이전트들의 사회가 아니라 그 밑의 기계 쪽(모델 풀 라우팅, 세마포어 스윗스팟,
캐시 경합, fork subagent). 이 사실을 설계 기준으로 채택.

## 2. 핵심 판단 기준

### 무엇이 하나로 접히는가
- 같은 가중치 + 같은 정보원 → 상호 비판은 메아리. 2~3라운드에 고정점.
  동의율은 오르고 정확도는 내려감 (수렴이 발전처럼 보임)
- 기존 AI Team(scout→builder→reviewer)이 여기 해당. 소유자 하나, cwd 공유,
  세션 재개로 상태 공유 → 사실상 한 모델이 순서대로 생각한 것
- **리뷰 단계가 물렁한 건 프롬프트 문제가 아니라 구조 문제**

### 무한히 도는 루프의 조건
- 에이전트 수가 아니라 **오라클(외부 심판)의 강도**가 성장률을 정함
- AlphaZero가 도는 건 에이전트 둘이라서가 아니라 게임 규칙이 심판이라서
- 고정 테스트 스위트 = 고정 천장. self-play가 오래 도는 건 상대 난이도가
  같이 올라가기 때문 → 두 번째 에이전트의 역할은 "리뷰"가 아니라 **과제 생성**

### A2A 프로토콜이 필수가 되는 조건
분리된 신뢰 경계 / 비대칭 사적 정보 / 어긋난 인센티브 / 독립적 생명주기
중 최소 둘. 로컬 두 프로세스면 JSONL 교환으로 충분 — 프로토콜은 3번째 참가자나
다른 머신이 생길 때 승격. 먼저 붙이면 문제를 프로토콜에 맞추게 됨.

### 경쟁 vs 보완
- **경쟁**: 천장까지 밀어올림. 오라클 + 커리큘럼 필요. 무한히 돌 수 있음
- **보완**: 천장 자체를 올림. 조건은 의견 차이가 아니라 **감각기관의 차이**.
  게임도 심판도 불필요. 단 무한히 돌지 않음(한 번 훑으면 끝)

## 3. 오케스트레이터 간 상호작용 (선택한 축)

서브에이전트와 달리 오케스트레이터는 **자기 정책**을 가짐 → 정책 차이가
측정 가능한 성과 차이로 나옴 → 심판이 모델이 아니라 성과. 오라클이 외부에 있음.

```ts
type Policy = {
  concurrency: number;              // 3~5 스윗스팟
  warmupThenFanout: boolean;
  modelRouting: { scout: Model; builder: Model; reviewer: Model };
  giveUp: { maxRounds: number; tokenBudget: number };
  contextStrategy: {                // ★ 이게 없으면 그냥 그리드 서치
    fileSelection: string;
    priorRounds: "full" | "summary" | "diffOnly";
    decomposition: "depth" | "breadth" | "adaptive";
  };
};
```

흡수 규칙: 라운드 후 `(정책 diff, 근거 로그)` 교환. **자동 복사 금지** —
받은 쪽이 그 변경 하나만 적용해 재현하고, 이득이 재현될 때만 채택.
(카고 컬트 방지 / 교환이 검증 가능한 태스크가 되는 지점)

붕괴 방어: diff 거리 임계 이하 시 강제 분기 / 목적 비대칭(A는 성공률, B는 토큰) /
양쪽 다 성공한 과제 유형은 풀에서 제거.

## 4. 과제 유형 — 검토와 선택

| 유형 | 오라클 | 판정 |
|---|---|---|
| 과거 버그 수정 커밋 되돌리기 | 기존 테스트 | 난이도 분포가 실제 분포. **미착수** |
| **strict 플래그 승급** | `tsc` + cost 카운트 | **착수 → 실패 (아래)** |
| 테스트 작성 | Stryker 뮤턴트 킬률 | 커버리지는 즉시 게이밍당함 |
| 신규 기능 | (사람) | 기각 — 천장이 스펙 품질로 결정 |
| 성능 개선 | (비결정적) | 기각 — 두 정책이 노이즈를 학습 |
| 리팩터링 | (동작 보존 검증 불가) | 기각 |

## 5. 구현: `score.ts` / `sweep.ts` (gymboxx-app-server)

인터페이스:
```
$ npx tsx score.ts src/modules/badge noUncheckedIndexedAccess
{ "gate": false, "errors": 2, "errorsByCode": {...}, "cost": {...} }
```

- probe tsconfig를 임시 생성(모듈만 `include`, 플래그 on, `noEmit`)
- cost 카운트는 정규식 대신 **AST** (`!`, `as`는 정규식으로 안 잡힘)
- 오라클을 에이전트가 못 만지게: 테스트/tsconfig/package.json 읽기 전용
- 검증 5항목 통과, 3회 연속 실행 결정적

### 구현 중 발견한 오염 2건
1. 레포 `incremental: true` → probe에서 `incremental/composite: false` 강제
2. probe가 임시 디렉터리에 있으면 `@types` 자동탐색이 깨져 Node 전역이 TS2580
   → `typeRoots`를 레포 `node_modules/@types`로 고정

### 성능 문제
`include`는 **루트 파일만** 정함. import로 도달하는 파일 전부가 프로그램에 들어감
→ 190회 각각이 사실상 전체 레포 타입체크(회당 3~7초).
`include` 제한은 **에러 귀속**만 격리했고 작업량은 안 줄었음.

수정 방향: 플래그당 프로그램 1개(`ts.createProgram`)만 만들고
`diag.file.fileName`으로 모듈 버킷팅 → 190회 → 5회.

## 6. sweep 결과 (38 모듈 × 5 플래그 = 190)

### 미해결 버그: baseline 미차감
`src/modules/user`가 5개 플래그 전부에서 `TS2339` 6개. `noImplicitOverride`는
TS2339를 만들 수 없음 → **플래그와 무관한 기존 에러가 섞임**.
→ 플래그 없이 1회 돌려 모듈별 baseline 진단 저장 후 매 채점에서 차집합.

### 데이터
- **147/190 이미 통과.** 실패 43개 중 대부분 에러 1~5개, 10개 이상은 11개뿐
- 그 11개 중 4개가 `user` 모듈 하나, 6개가 `exactOptionalPropertyTypes` 하나
- 에러 코드 쏠림: TS2412/2375/2379 압도적 = DTO·엔티티 옵셔널 속성.
  고치는 방법이 거의 한 가지(`?:` → `| undefined` 정리)

### 결론
문제집이 **얇고 동질적**. "플래그 4단계로 난이도 커리큘럼이 공짜로 생긴다"는
예상은 틀렸음 — 레포가 이미 거의 strict-clean이라 계단이 1~2칸.
오케스트레이터 두 개를 붙여도 이틀이면 문제집을 다 풀고 루프가 죽음.

**채점기를 먼저 만든 이유가 여기서 회수됨.** 에이전트 다 붙이고 3주 뒤에
알았으면 훨씬 비쌌음.

## 7. 상호 보완 페어 (경쟁 대신)

sweep의 에러 분포가 자리를 만들어줌. 실제로 어려운 결정은 타입 표기가 아니라:

> **이 필드는 실제로 비어 있는 적이 있나?**

`profileImage?: string` → 옵셔널 제거 vs 유지. **코드만 봐선 답이 안 나오고
DB는 답을 알고 있음.**

- **정적 에이전트**: 에러 지점, 후보 수정안, 영향받는 호출자
- **관측 에이전트**: 해당 컬럼 실제 NULL 비율, API 응답 필드 부재율, 추이

| 관측 결과 | 판단 |
|---|---|
| NULL 0% + 3년치 | 옵셔널 제거. 타입이 현실에 맞춰짐 |
| NULL 30% | 옵셔널 유지 + 호출자 방어. `!`로 뭉개면 프로덕션 버그 |
| NULL 0.01% | 가장 흥미로움 — 정합성 버그 신호 |

어느 쪽도 상대 정보를 유추 불가 → 하나로 안 접힘.
여기서 A2A가 장식이 아님(관측 쪽은 DB 권한/코드 못 봄, 정적 쪽은 반대).

**부수 효과가 본체보다 큼**: 산출물이 strict 통과가 아니라
**타입 선언과 실제 데이터의 불일치 목록**. "3년간 null이 아닌데 옵셔널로 선언된
필드 40개" 같은 표 — 마이그레이션이 끝나도 남는 스키마 진단.
