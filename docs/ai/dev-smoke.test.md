# dev 스모크 테스트 레포 구현 스펙

> 구현 에이전트용 문서. **비어 있는 `<결정 필요: ...>` 항목을 임의의 그럴듯한 값으로 채우지 말 것.**
> 값을 모르면 채우지 말고 질문으로 남긴다. 추측으로 채운 값은 이 문서의 검증 목적을 무효화한다.

---

## 1. 목적

개발자가 dev 배포 후 손으로 API를 찔러보는 작업(대략 10~15분)을 자동화한다.
사람이 머지 → dev 배포 → **배포 직후 자동으로 API를 호출하고 결과를 보고**한다.

### 이 도구가 책임지는 것

- 배포된 dev 환경에서 실제 HTTP 호출이 성공하는가
- 로컬/CI와 dev의 차이에서 오는 실패 (환경변수, 시크릿, 마이그레이션 실제 적용, DI 조립, 인그레스, 외부 의존성)
- 응답이 "그럴듯한지" (빈 배열, null 필드, 비정상적 지연 등 assert로 적기 애매한 것)

### 이 도구가 책임지지 않는 것 (비목표)

- 승인 게이트가 아니다. 머지 판단은 이미 사람이 끝냈다.
- 비즈니스 로직의 정확성 검증이 아니다. 그건 PR 리뷰와 단위/계약 테스트의 몫이다.
- 실패해도 롤백하지 않는다. dev는 깨진 채로 두고 다음 날 본다.
- 프로덕션에서 실행하지 않는다.

### 설계 원칙

1. **삭제하지 않는다.** 테스트 데이터는 지우지 않고 *구분 가능하게* 만든다. (§4)
2. **재실행 가능해야 한다.** 매 실행은 이전 실행의 잔여 상태에 의존하지 않는다.
3. **원문을 남긴다.** 요약만 있으면 아무도 믿지 않아서 결국 손으로 다시 찔러본다.
4. **통과 목록보다 미커버 목록이 중요하다.** 전자는 안심시키고 후자는 판단 재료가 된다.

## 2. 구현 전에 채워야 하는 값

구현 에이전트는 아래를 **비워둔 채로 코드를 작성하고**, 설정 파일의 필수 키로만 노출한다.
값이 없으면 실행 시점에 명확한 에러로 죽어야 한다. 기본값(fallback)을 넣지 말 것.

| 항목 | 값 |
|---|---|
| 레포 이름 | `<결정 필요>` |
| dev API base URL | `<결정 필요>` (환경변수 `API_BASE_URL`) |
| 인증 방식 | `<결정 필요>` — §5 참조 |
| 테스트 유저 이메일 도메인 | `<결정 필요>` |
| 회원가입 엔드포인트 | `<결정 필요>` |
| CI 러너 | GitHub Actions 가정. 다르면 `<결정 필요>` |
| 알림 채널 | `<결정 필요>` (Slack 채널 등) |

## 3. 레포 구조

앱 레포와 분리된 별도 레포. 앱 배포물에 포함되지 않는다.

```
.
├── src/
│   ├── client/
│   │   ├── http.ts            # fetch 래퍼. 모든 요청/응답을 recorder에 기록
│   │   ├── auth.ts            # 로그인 → 토큰 획득
│   │   └── fixtures.ts        # 테스트 유저 생성 유틸 (팀 공용, §4)
│   ├── suites/
│   │   ├── read/              # 읽기 전용 스모크
│   │   └── write/             # 쓰기 스모크 (신규 유저 필수)
│   ├── explore/               # LLM 탐색 단계 (§7.2)
│   ├── report/
│   │   ├── recorder.ts        # 요청/응답 원문 수집
│   │   └── render.ts          # 리포트 생성
│   └── config.ts              # 환경변수 로딩. 누락 시 즉시 throw
├── types/                     # 앱에서 가져온 요청/응답 타입 (§6)
└── .github/workflows/
```

기술 스택 (변경 가능, 근거만 유지):

- TypeScript + Node
- 러너: **vitest** — 스위트 구조, 병렬 제어, 리포터 커스터마이징이 필요
- 스키마 검증: **zod** — 응답 형태를 런타임에서 확인하고, 실패 시 어느 필드인지 말해줘야 함
- HTTP: 표준 `fetch`. 별도 클라이언트 라이브러리 불필요

## 4. 테스트 유저 컨벤션 (가장 중요)

### 4.1 규칙

- **쓰기 테스트는 매 실행마다 새 유저를 생성해서 사용한다.** 유저를 재사용하지 않는다.
- **유저를 포함해 어떤 데이터도 삭제하지 않는다.**
- 이메일 형식: `smoke+{YYYYMMDD}-{runId}@<결정 필요: 도메인>`
  - `runId`는 실행마다 고유한 짧은 랜덤 문자열 (예: 6자 base36)
  - 같은 날 여러 번 실행되어도 충돌하지 않아야 한다
- 닉네임/표시명에도 동일 접두사를 붙여, DB뿐 아니라 관리자 화면에서도 구분되게 한다

### 4.2 삭제를 만들지 않는 이유

삭제 로직이 위험한 것은 대상이 테스트 유저라서가 아니라, **삭제 코드가 존재하게 되기 때문**이다.
조건 하나가 어긋났을 때의 피해가 비대칭적으로 크고, 안 지워서 생기는 비용은 dev 기준 무시할 수 있다
(하루 몇 건, 1년 누적해도 수천 행).

정리가 정말 필요해지는 시점에는 **선택적 삭제가 아니라 dev DB 리셋**을 쓴다.

### 4.3 DB 가독성 대책

"테스트 데이터 때문에 DB 보기 불편하다"는 불만에 대한 대응. 삭제가 아니라 **구분**으로 해결한다.

1. **이메일 접두사 규칙** (§4.1) — 어떤 쿼리에서도 한 조건으로 걸러낼 수 있다
2. **필터링된 뷰** — 자주 조회하는 테이블에 대해 스모크 유저를 제외한 뷰를 만들고 평소엔 그걸 본다
   - 대상 테이블: `<결정 필요: 팀이 실제로 자주 보는 2~3개>`
   - 뷰 이름 규칙: `<결정 필요>`
3. **팀 공용 유틸** — `src/client/fixtures.ts`의 유저 생성 함수를 팀이 수동 테스트할 때도 쓰게 한다.
   지금도 각자 규칙 없이 회원을 만들고 있고, 실제 오염원은 그쪽이다.

`isTest` 플래그를 유저 테이블에 추가하는 안은 **보류**한다. 앱 조회 계층에 조건이 늘어나는 비용이 있고,
위 세 가지로 해결되지 않을 때 꺼낸다.

## 5. 인증

**가장 먼저 뚫어야 하는 부분.** 여기가 막히면 나머지가 전부 무의미하고, 실무적으로 이런 자동화가
중도 포기되는 지점이 대부분 여기다.

- dev 로그인 플로우를 헤드리스로 통과할 수 있어야 한다
- 소셜 로그인만 있고 우회 경로가 없다면, **앱 쪽에 dev 전용 로그인 경로가 필요**하다
  (이 경우 앱 팀과 합의 필요 — 이것도 §11에 포함)
- 토큰은 실행 단위로 획득하고 메모리에만 보관. 파일/레포에 커밋하지 않는다
- 방식: `<결정 필요>`

---

## 6. 타입 / 계약 소스

요청·응답 타입을 **복붙하지 않는다.** 복붙하면 앱 스키마가 바뀌었을 때 테스트가 조용히 통과한다.

우선순위:

1. 앱 레포가 DTO를 패키지로 내보낼 수 있으면 그걸 의존성으로 사용
2. 아니면 OpenAPI 스펙에서 타입 생성 (`openapi-typescript` 등), 생성 결과를 커밋
3. 둘 다 불가하면 zod 스키마를 손으로 유지하되, **불일치가 런타임 에러로 드러나게** 한다

이게 되면 부수 효과로 계약 변경이 테스트 레포 컴파일 에러로 뜬다.
(예: 필수 필드가 추가/변경되면 빌드가 깨진다. 사실상 공짜 계약 테스트)

## 7. 실행 모델

### 7.1 고정 스위트

`src/suites/` 아래. 결정적이고 빠른 검증.

- **read**: 인증 후 주요 조회 엔드포인트 호출. 상태 코드 + 응답 스키마 + 기본 sanity (배열이 비어있지 않은지 등)
- **write**: 신규 유저 생성 → 핵심 플로우 실행

write 스위트 주의사항:

- 각 write 테스트는 **자신만의 신규 유저**로 시작한다
- 되돌릴 수 없는 상태 전이(단방향 전이 등)를 포함하는 플로우는, 유저가 새것이므로 안전하다
- **멱등성이 정의되지 않은 엔드포인트는 반복 호출하지 않는다.** 대신 §7.2의 탐색 대상으로 넘긴다

### 7.2 탐색 단계 (LLM)

고정 스위트가 못 잡는, 사람이 눈으로 보던 부분을 담당한다.

입력:
- 이번 배포에 포함된 변경 정보 (커밋 메시지, PR 제목, 연결된 Linear 이슈 본문)
- dev base URL + 인증된 클라이언트
- 호출 가능한 엔드포인트 목록

수행:
- 변경 내용에 근거해 **어디를 찔러볼지 스스로 정하고** 호출한다
- 응답이 이슈에 기술된 내용과 부합하는지 확인한다
- dev에서만 할 수 있는 시도를 포함한다: 필수 필드 누락 요청, 경계값, 정의되지 않은 중복 호출

제약:
- **쓰기 탐색은 전용 신규 유저로만.** 고정 스위트가 쓰던 유저를 재사용하지 않는다
- 판단이 애매하면 "정상"이라고 쓰지 말고 관찰 사실만 기록한다

### 7.3 승격

탐색 단계에서 반복적으로 유의미한 항목이 나오면 고정 스위트로 옮긴다.
매번 LLM에게 판단시키는 것은 비싸고 흔들린다.

**이 자동화의 장기 산출물은 매일 도는 리포트가 아니라, 적어둘 가치가 있는 테스트가 무엇인지 알아내는 것이다.**

## 8. 리포트

### 8.1 필수 포함 항목

1. **실행 메타**: 배포된 커밋 SHA, 실행 시각, runId, 사용한 테스트 유저 이메일
2. **요청/응답 원문**: 모든 호출의 method, URL, 요청 바디, 상태 코드, 응답 바디, 소요 시간
   - 요약만 남기면 신뢰가 안 돼서 결국 손으로 다시 찔러보게 된다
   - 토큰·시크릿은 마스킹
3. **이상 징후 목록**: 실패가 아니지만 눈에 걸리는 것
   - 빈 배열 / null 필드 / 0 값
   - 비정상적으로 느린 응답
   - 이전 실행과 달라진 응답 형태
4. **미커버 목록**: 호출하지 않은 엔드포인트, 만들지 못한 상태 조합, 스킵한 이유

### 8.2 형식

- 요약은 Slack 메시지, 전문은 아티팩트(HTML 또는 마크다운)로 CI에 첨부
- 실패가 없어도 이상 징후가 있으면 알린다

## 9. 트리거

- dev 배포 완료 시점에 실행한다
- Argo CD 사용 중이므로 sync 후 훅(PostSync)에서 dispatch하거나, dev 배포 job 마지막 단계에서
  `repository_dispatch`로 이 레포 워크플로를 호출한다
- **배포 슬롯은 직렬**로 둔다. 짧은 시간에 여러 머지가 겹치면 어느 변경 때문에 깨졌는지 특정할 수 없다
  - 동시 실행이 들어오면 이전 실행을 취소하거나 큐잉한다 (GitHub Actions `concurrency` 그룹)
- 실패해도 배포를 되돌리지 않는다. 알림만 보낸다

---

## 10. 앱 레포 쪽에 필요한 변경

이 레포만으로 끝나지 않는 항목. 앱 팀과 별도 티켓 필요.

- [ ] dev 전용 로그인 경로 (§5에서 필요하다고 판명될 경우)
- [ ] DTO 패키지 export 또는 OpenAPI 스펙 노출 (§6)
- [ ] 스모크 유저 제외 뷰 (§4.3)
- [ ] 배포 완료 시 dispatch (§9)

---

## 11. 시작 전 팀 합의

구현 전에 공유한다. 규칙을 정해서 시작하면 합의된 컨벤션이고,
나중에 누가 발견해서 물어보면 남이 어지른 것이 된다. 같은 데이터인데도 그렇다.

공유할 내용: 이메일 접두사 규칙, 데이터를 지우지 않는다는 방침과 그 이유, 필터 뷰 제공, 유저 생성 유틸 공용 사용.

---

## 12. 금지 사항

- 유저 또는 유저 관련 데이터를 삭제하는 코드를 작성하지 않는다
- 설정값에 fallback 기본값을 넣지 않는다. 누락은 즉시 에러
- 프로덕션 URL로 실행 가능한 경로를 만들지 않는다 (base URL 화이트리스트 검증)
- 응답 검증에서 애매한 값을 통과시키기 위한 느슨한 assert를 쓰지 않는다
- 모르는 값을 그럴듯하게 채우지 않는다

---

## 13. 구현 순서

1. **인증 통과** — 이게 안 되면 나머지 전부 무의미
2. 설정 로딩 + HTTP 클라이언트 + recorder
3. 테스트 유저 생성 유틸 (`fixtures.ts`)
4. read 스위트 3~5개
5. CI 워크플로 + 수동 트리거로 동작 확인
6. 배포 후 자동 트리거 연결
7. 리포트 렌더링 + Slack 알림
8. write 스위트
9. 탐색 단계

1~6까지만 되어도 지금 손으로 하는 작업의 대부분을 대체한다. 나머지는 그 다음에 판단한다.
