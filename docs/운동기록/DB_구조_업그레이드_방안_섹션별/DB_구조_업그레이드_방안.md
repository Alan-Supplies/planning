## 00. 이 문서의 목표

### 0-1. 목표 정의

**DB에 쌓인 데이터를 활용해 다양한 분석이 가능하도록 DB 구조와 적재 방식을 고도화하는 것**

- 운동 목표 달성률은 분석 영역 하나일 뿐 · 운동기록·회원정보 등 전체 데이터로 해야 할 분석이 더 존재

- **작업 원칙 1** — "현행 구조로는 불가능하다"에서 멈추지 않음 · 그 분석을 하려면 무엇을 어떻게 준비해야 하는지를 산출물로 만듦

- **작업 원칙 2** — 지표의 상세 기준은 각 시스템을 만들 때 확정 · 이 문서는 어떤 기준을 택해도 성립하도록 원천을 보관하는 구조를 준비

- **작업 원칙 3** — 파생 지표는 저장하지 않고 원천을 보관 · 추정 최대 중량·달성률 같은 계산값을 원천 삼아 쌓으면 계산 기준이 바뀔 때 과거 데이터가 무효 가 됨 · 원천(무게·반복 수·시각)을 남기면 기준 변경 후 전량 재산출 가능

- **작업 원칙 4** — 수집 컬럼은 먼저 열고 강제는 나중 · 지금 안 쌓은 값은 그 시점 이전 기록에서 영구 결손이므로, 화면·규칙이 준비되기 전이라도 컬럼을 먼저 마련

- 분석 목록은 전량 구현 대상이 아님 · 방향성과 맥락을 공유해 구조 준비의 범위를 정하기 위한 것

### 0-4. 영역 2 — 랭킹 시스템

상세 기준은 랭킹 시스템을 만들 때 확정 · 이 문서는 어떤 기준을 택해도 성립하도록 원천을 보관하는 구조만 준비

#### 모집단 원칙

운동기록을 남긴 회원만 모집단 — 사용 중 회원이 39만 명이어도 기록 보유자가 4.5만 명이면 최하위가 44,970위 모집단이 계속 커지므로 순위는 시점 고정이 필요 — 스냅샷 없이는 과거 순위 재현 불가

#### 분모 3축 — 세 결과를 모두 표시

|축|예시|필요 데이터|
|---|---|---|
|전체|전체 1위|—|
|성별|여성 1위|회원 성별(405,306명 판별)|
|성별 × 연령대|30대 남성 중 1위|회원 생년(405,013명 보유)|

- ⚠ 연령은 생년을 기준으로 계산하는 시스템이 필요함 — 향후 랭킹 시스템에서 나이를 생년으로부터 계산하고 연령 구간 기준을 적용하는 방식으로 개발

#### 랭킹 종류 2가지 — 방향성

- 종목별 랭킹 — 경쟁 요소를 만드는 것이 목적("3대 500" 같은 감각)

   - 데드리프트 무게 1위 · 유산소 시간 1위 · 덤벨 무게 1위 등

   - 정렬 방향 — 무게 우선, 같은 무게면 반복 수로 비교

   - 시간·거리형 종목은 무게 대신 시간 기준

- 부위별 랭킹 — 이두근 1위 · 삼두근 1위 등

   - 기준 후보 — 추정 최대 중량 · 무게와 반복 수의 조합 · 부위 훈련량 합 판단이 필요한 지점 — 부위 강도는 종목에 종속됨(바벨 컬·덤벨 컬·케이블 컬의 수치가 서로 다름) · 어떤 기준을 택하든 종목 고정 또는 대표값 규칙이 함께 정해져야 함

   - 구조 준비의 결론 — 기준을 지금 정하지 않아도 됨 · 세트별 무게·반복 수·종목·부위 기여도를 모두 보관하고 추정값은 저장하지 않고 파생으로 두면, 기준을 바꿀 때 전량 재산출 가능

축이 섞였다는 사실이 데이터 어디에도 없으므로, 목표 달성률을 계산할 때 감량·회복 24행을 빼는 일을 사람이 매번 기억해야 함 · 화면·서버·배치가 각자 조건을 손으로 옮겨 적고 한 곳이 빠지면 그 화면만 조용히 다른 숫자를 보여줌 두 테이블로 분리하고, 계산에 쓰는 효과 축 테이블에 근력·순발력 값을 추가

|처<br>리|테이블|담는 값(한글 이름·DB 값)|예상 행수|
|---|---|---|---|
|신<br>설|`exercise_effect`—운동 효과 축·<br>계산용|근력<br>`STRENGTH`(신설) ·지구력<br>`ENDURANCE`·이완<br>`MOBILITY`·균형<br>`BALANCE`·순발력<br>`PLYOMETRIC`(신설)|기존 63행 이관 + 근력 백필 225<br>행 = 약 290행|
|정<br>리|`exercise_recommend_tag`—추천용<br>태그|감량<br>`FAT_LOSS`·회복<br>`RECOVERY`|기존 24행 이관|

감량과 회복은 분류상 다른 축이지만 쓰이는 방식이 같아(둘 다 추천 입력 전용) 한 테이블에 둠 · 오늘 어떤 쿼리도 이 둘을 구별해 읽지 않으므로 더 쪼개면 관리 비용만 늘어남 효과 축 테이블에 함께 신설하는 컬럼 4종

|컬럼|용도|왜 추천용 태그 테이블에는 두지 않는가|
|---|---|---|
|`is_primary`|주 효과 1개 + 부가 효과 여러 개 구분|감량·회복에는 주 효과·부가 개념이 없음·같은 테이블에 두면 24행이 영원히 채울 수 없는 컬럼을 들고<br>있게 됨|
|`status`|태그 해제를 물리 삭제가 아니라 비활성 처<br>리로|추천용 태그에도 유용하므로 양쪽에 둠|
|`created_at`|부여 시각|양쪽에 둠|
|`updated_at`|상태 변경 시각|양쪽에 둠|

근력 백필 대상 실측 — 근육 부위 라벨을 가진 253종 중 지구력·이완 태그가 없는 225종은 근력 부여 확정 · 나머지 28종은 검수 대상(스쿼트처럼 지구력·이 완을 겸한 종목)

### 어떻게 바꾸는가

1. 앱 코드에서 **`exercise_function`** 을 읽는 지점 전수 조사 — 테이블 분리는 기존 쿼리가 그대로 동작하지 않으므로 이 조사가 착수 전제

2. 효과 축 테이블 신설

```
CREATE TABLE exercise_effect (
  id          int unsigned NOT NULL AUTO_INCREMENT,
  exercise_id int          NOT NULL,
  effect_tag  enum('STRENGTH','ENDURANCE','MOBILITY','BALANCE','PLYOMETRIC') NOT NULL,
  is_primary  tinyint(1)   NOT NULL DEFAULT 0,
  status      enum('ACTIVE','INACTIVE') NOT NULL DEFAULT 'ACTIVE',
  created_at  timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP
                                    ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id));
```

1. 생성 열 + 부분 고유 제약 추가 — `(exercise_id, effect_tag,` 생성열 `)` 로 사용 중 1행 + 비활성 이력 여러 행을 동시에 허용

2. 추천용 태그 테이블 신설 — 값은 감량 `FAT_LOSS` · 회복 `RECOVERY` 2개만 · 구조는 효과 축 테이블과 같고 `is_primary` 만 없음

3. 데이터 이관 — 지구력·이완·균형 63행을 효과 축으로, 감량·회복 24행을 추천용으로 · 전부 사용 중 상태로 표시 · 이관 전 `exercise_function` 전체를 백업 테이블로 보존

4. 근력 백필 — 확정 225종에 근력 `STRENGTH` 행 삽입 · 검수 대상 28종은 주 효과 판정 후 부여

5. 순발력 부여 — 버피·점핑잭·스플릿 점프 등 소수 종목 · 값은 열거형에 이미 열려 있으므로 태깅은 후순위

6. 주 효과 부여 — 이관·백필 완료 후 종목별로 주 효과 1개 지정

7. 구 테이블 제거 — 앱 코드 전환 확인 후 `exercise_function` 삭제 · 백업 테이블은 유지

### 무엇이 좋아지는가

효과 축 판정이 테이블 자체로 결정됨 — 계산 규칙을 문서로 관리할 필요가 사라짐 · 계산 쿼리가 `exercise_effect` 를 읽는 순간 이미 효과 축이며, 감량·회복이 섞일 경로가 물리적으로 없음 · 열거형이 축별로 나뉘므로 효과 축 테이블에 `FAT_LOSS` 를 넣으려는 시도가 저장 실패로 거부됨 · 문서 약속이 아니라 DB 제약으로 막힘

근력 운동 세션 수 목표의 판정이 하나로 확정됨 — 현재 근력 판정에 쓸 수 있는 우회가 두 가지이고 결과가 다름

|우회 방법|근력 종목 수|섞이는 오류|
|---|---|---|
|태그가 없으면 근력으로 간주|230종|폼롤링 7종이 근력으로 잡힘—태그가 아예 없기 때문|
|근육 부위 라벨이 있으면 근력으로 간주|253종|스쿼트처럼 지구력·이완 태그를 겸한 30종이 섞임|

어느 우회를 쓰는지에 따라 23종이 갈리고, 화면·서버·배치가 각자 다른 우회를 쓰면 같은 회원의 근력 세션 수가 달라짐 · 근력 `STRENGTH` 명시 값이 있으면 이 분기가 사라짐

유산소 운동 시간 목표가 계산 가능해짐 — 현재 지구력 태그 25종에 트레드밀·사이클·로잉 같은 유산소 기구와 런지 6종·푸시업 2종·스쿼트가 함께 들어 있음 · 25종을 모두 세면 워킹 런지 20분이 유산소 20분으로 계상되어 시간이 부풀려짐 · 주 효과만 세면 기구 유산소만 남음 · 지금은 규칙을 정해도 DB가 그 규칙을 표현할 수 없는 상태

균형 운동 세션 수 목표도 같은 구조로 판정 — 균형 태그 20종 중 주 효과 적격이 2종인데, 주 효과 구분 컬럼이 없으면 이 2종을 구별해 셀 수 없음 신규 등록 시 태깅 누락을 잡을 수 있음 — "태그 없으면 근력" 규칙에서는 태깅을 빠뜨린 운동이 자동으로 근력이 되어 누락과 근력을 구별할 방법이 없음 · 명시 값이면 효과 축 행이 없는 종목을 감사 쿼리로 검출 가능

감량·회복 태그 24행이 보존됨 — 두 값은 틀린 값이 아니라 다른 축의 값 · 감량 태그는 회원의 운동 목적(감량·근력 증가·지구력 향상 등)과 매칭하는 추천에, 회복 태그는 회복일 운동 추천에 계속 사용 · 삭제하면 추천 근거가 사라짐 태그 정정 작업의 비용이 사라짐 — 균형 태그 부적격 9종 제거 작업에서 백업 테이블·롤백 명령·정합 검증을 별도로 만들어야 했음 · 상태 컬럼이 있으면 비활성 처리 한 번으로 끝나고 원본이 그대로 남음 회귀 원인 추적 가능 — 2026-07 분류 정정 4건이 한 달 만에 되돌아갔을 때, 물리 삭제 구조라 언제 되돌아갔는지 알 수 없어 원인 배포를 찾지 못했음 · 부여 시각과 상태 변경 시각이 남으면 시점으로 역추적 가능 축이 늘어날 때 기존 테이블을 건드리지 않음 — 새 축이 생기면 테이블을 하나 더 만들면 됨 · 한 컬럼에 값을 더 넣는 방식이면 축이 늘 때마다 기존 계산 조건을 전부 다시 확인해야 함

### 주의

## 02. 부위 라벨 사전에 축 구분 컬럼 추가

부위 사전 8행에 축 구분을 넣어 유산소·스트레칭이 부위 집계에 섞이는 경로를 차단하는 작업

### 무엇을 바꾸는가

`body_part` 테이블에 축 구분 컬럼 **`axis`** 추가(값 2종 — 근육 부위 / 운동 성격) · 8행 갱신 · 테이블명은 이번에 변경하지 않음 이 테이블은 이름이 "부위 마스터"지만 실제 내용은 운동 분류 라벨 사전이며, 8종 라벨이 273개 운동을 겹침 없이 분할

|축|라벨|연결 운동|하위 세부부위|
|---|---|---|---|
|근육 부위|가슴·등·어깨·팔·하체·코어 6종|253종|21종|
|운동 성격|유산소·스트레칭 2종|20종(13 + 7)|0종|

### 어떻게 바꾸는가

1. `axis enum('MUSCLE','MODALITY') NOT NULL` 추가

2. 8행 갱신 — 근육 부위 6종은 `MUSCLE` · 유산소·스트레칭 2종은 `MODALITY`

3. 조회 규칙 전환 — 현재 `body_part_id BETWEEN 1 AND 6` 방식을 `axis='MUSCLE'` 조건으로 교체

4. 테이블명 변경은 별도 작업으로 분리 — 외래키 5개( `body_part_detail` · `exercise_body_part` · `machine_body_part` · `user_exercise_session_body_part` · `exercise_recommendation_log_body_part` )와 앱·어드민 코드 참조가 걸려 코드 배포와 동시에 해야 함

### 무엇이 좋아지는가

새 부위를 추가할 수 있게 됨 — 지금은 구조적으로 막혀 있음 · 현재 부위 조회 조건이 식별자 범위(1~6)인데, 식별자 7·8이 유산소·스트레칭이므로 전완·목 같은 새 부위는 9번부터 시작함 · 그러면 조건이 연속 범위가 아니게 되어 `IN (1,2,3,4,5,6,9,10)` 같은 열거가 되고, 그 열거가 앱·서버·배치에 흩어져 있 어 부위 하나 추가에 전수 수정과 배포가 필요하며 한 곳을 빠뜨리면 조용히 틀린 값이 나옴 · 축 컬럼이면 어드민에서 행 하나 추가로 앱 필터와 집계에 자동 반영

부위별 운동량 목표 집계가 안전해짐 — 8종 전체를 부위로 집계하면 유산소 13종·스트레칭 7종이 부위 운동량에 섞임 · 축 조건 하나로 자동 제외 앱 부위 배지·필터가 데이터로 결정됨 — 현재 클라이언트에 6개가 하드코딩돼 있어 부위 추가·명칭 변경이 앱 배포를 요구 분류 오염의 재발 차단 — 유산소·스트레칭이 부위 칸에 들어올 수 있었던 원인이 "성격을 담을 자리가 없어서"였음 · 축이 선언되면 신규 등록 시 같은 일이 반복되지 않음

### 주의

- 식별자 순서에 의미를 부여하는 방식은 대리키 특성상 위험 — 데이터 이관·재생성으로 순서가 바뀌면 범위 조건이 조용히 깨짐 위키에는 " **`body_part`** 는 **`exercise_label`** 처럼 활용" 으로 반영 완료(진입점 문서·프로파일·카탈로그 3곳) · 테이블명 부채는 태그 사전 통합 시점에 함께 처리

## 03. 유산소 강도 컬럼 신설

피로도 컬럼에서 유산소 강도를 떼어내 추천 알고리즘 변경이 달성률을 흔들지 않게 하는 작업

### 무엇을 바꾸는가

`exercise` 테이블에 유산소 강도 컬럼 신설(값 2종 — 중강도 / 고강도) · 값은 기존 피로도 컬럼에서 복사한 뒤 독립 운영

### 어떻게 바꾸는가

1. `cardio_intensity enum('MODERATE','VIGOROUS') NULL` 추가 — 유산소가 주 효과인 종목만 필수

2. 피로도 기준 일괄 부여 — 피로도 4 이상은 고강도, 3 이하는 중강도 · 유산소 13종 중 11종이 이 규칙으로 확정 3. 경계 2종(점핑잭·일립티컬)만 트레이너 검수 — 신규 조사 0건

피로도 값이 이미 강도 순서를 담고 있음

|피로도|종목|판정|
|---|---|---|
|5|로잉 머신·버피·스텝밀|고강도|
|4|인클라인 트레드밀·트레드밀 런·래더밀|고강도|
|3|일립티컬·점핑잭·핸드 바이크|경계|
|2|트레드밀 워크·좌식 사이클·입식 사이클·스탭퍼|중강도|

### 무엇이 좋아지는가

유산소 운동 시간 목표의 환산 계수가 생겨 계산이 성립함 — 목표가 "중강도 시간 + 고강도 시간 × 2 = 주 150분"인데, 곱할 계수를 결정할 컬럼이 없어 계 산 자체가 불가능한 상태 추천 알고리즘 변경이 달성률을 흔들지 않게 됨 — 피로도 컬럼은 운동 추천·플랜 알고리즘도 읽는 값 · 누군가 추천 품질을 개선하려고 트레드밀 런의 피로도 를 4에서 3으로 낮추면 회원이 이미 본 유산소 달성률이 전부 바뀜 · 강도 컬럼이 따로 있으면 추천은 피로도를 조정하고 달성률은 영향받지 않음 경계 사례를 교정할 자리가 생김 — 점핑잭을 고강도로 올리려면 지금은 피로도를 건드려야 하고 그러면 추천이 흔들림 비유산소 종목의 오독 방지 — 데드리프트의 피로도 5는 근육 피로이며 심박 부하가 아님 · 피로도를 직접 읽는 방식이면 "유산소일 때만 읽는다"는 조건을 화면·서버·배치에 각각 복제해야 하고, 한 곳이 빠지면 근력 운동이 유산소 시간에 계상됨

### 주의

- 난이도 컬럼은 강도 대체 불가 — 트레드밀 런의 난이도가 1이고 일립티컬이 3으로 강도와 역순 · 피로도 1~5 전 구간에서 난이도 평균이 2.83~4.33으로 평탄 · 난이도는 "동작을 배우기 어려운가"의 답 복사 후 독립이므로 피로도 변경이 강도에 자동 반영되지 않음 · 신규 유산소 종목 등록 시 강도 필수 입력 규칙이 필요

## 04. 측정 방식 선언 컬럼 신설

세트 값의 의미를 운동 마스터 조인 없이 확정하고 서버 검증의 근거를 만드는 작업

### 무엇을 바꾸는가

`exercise` 테이블에 측정 방식 선언 컬럼 신설(값 3종 — 무게+횟수 / 횟수만 / 시간) · 현재는 단위 컬럼과 무게 보유 여부 컬럼의 조합에서 매번 추론(실측 조합 12종)

### 관련 테이블 구조

`exercise                          ←` 측정 방식 컬럼 신설 `(` 운동 정의 `) id · name · unit · has_weight │ user_exercise_session             ←` 세션 `:` 출입 `1` 건당 `1` 개 `·` 세션 강도 보유 `access_history_id · rpe · started_at · end_at │ user_exercise_session_history     ←` 그 세션에서 수행한 운동 `1` 건 `exercise_id · machine_id · is_done │ user_exercise_set_history         ←` 세트 `1` 개 `set_number · count · weight`

문제의 핵심은 세트 테이블의 `count` 컬럼 · 컬럼 주석이 실제로 "횟수 or 초" 이며, 세트 행만 봐서는 `count=30` 이 30회인지 30초인지 알 수 없어 운동 마 스터까지 조인해 추론해야 함 어떻게 바꾸는가

1. `measure_type enum('WEIGHT_REPS','REPS','DURATION') NOT NULL` 추가

2. 단위 × 무게 보유 여부 조합 12종을 매핑해 일괄 부여

3. 서버 검증을 이 컬럼 조회에서 도출 — 하드코딩 금지

|값|**`count`**의 의미|**`weight`**|서버 검증|
|---|---|---|---|
|무게+횟수|횟수|필수|무게 없으면 요청 거부|
|횟수만|횟수|없어야 함|무게가 오면 요청 거부|
|시간|초|없어야 함|무게가 오면 요청 거부|

### 무엇이 좋아지는가

세트 데이터를 단독으로 해석할 수 있게 됨 — 현재는 세트 값의 의미를 알기 위해 상위 두 테이블을 조인해야 하며, 데이터 웨어하우스 적재 시 이 추론이 파이프라인마다 반복됨

오염 데이터 유입 차단 — 맨몸 풀업에 무게가 들어온 세트가 1,621건 · 유일한 검증이 클라이언트 한 곳이었고 어시스트 머신 중량과 추가 중량이 섞여 총부하와 1회 최대 반복 중량 추정을 오염시킴 · 선언 컬럼에서 규칙을 도출하면 운동 유형이 늘어도 검증이 자동 확장 입력 화면이 데이터로 결정됨 — 무엇을 입력받을지가 컬럼 하나로 정해지므로 클라이언트의 폴백 추론 코드를 삭제할 수 있음 · 현재 그 코드가 밴드·구조물 종목을 오판 계산 가능 범위가 명확해짐 — 총부하와 1회 최대 반복 중량 추정은 무게+횟수 종목에서만 성립 · 지금은 대상 판별이 추론이라 계산이 조용히 잘못된 종목을 포함할 수 있음

### 주의

- 거리 측정은 이번에 제외 — 현재 해당 종목 0건이고 저장 컬럼도 없음 · `count` 에 미터를 넣으면 한 컬럼이 횟수·초·거리 3중 의미가 되어 문제가 커짐 · 트레드밀 거리 기록을 실제로 도입할 때 저장 컬럼과 함께 추가

```
UPDATE exercise_body_part_detail d
  JOIN (SELECT exercise_id, MAX(load_ratio) mx
          FROM exercise_body_part_detail WHERE status='ACTIVE'
         GROUP BY exercise_id) m ON m.exercise_id = d.exercise_id

 WHERE d.status = 'ACTIVE';
```

2. `load_ratio` 원값은 그대로 유지

절대 기준이 성립하지 않는 이유 — 부하율은 운동별 합계가 1.0인 분배율이므로, 부위를 몇 개 등록했는지가 값을 자동으로 끌어내림 · 절대 0.5를 쓰면 부위 를 자세히 등록한 운동일수록 주 부위가 사라짐(부위 5개 등록 운동 10종의 최댓값은 0.30까지 내려감) · 반대로 절대 0.3까지 내리면 직접이 399행으로 늘 어 부위 5개 운동은 사실상 전부 직접이 되어 직접·보조 구분이 무의미해짐

상대 기준의 판정 결과 — 직접 부위가 1개인 운동 230종 · 2개 16종 · 3개 2종 · 직접이 없는 운동 0종 · 다부위 운동의 복수 주 부위를 허용하면서 과도하게 번지지 않음

### 무엇이 좋아지는가

부위별 운동량 목표의 분모와 분자 단위가 일치함 — 목표선 "세부부위당 주 4세트"는 근육군 세트 수 단위인데, 현재 분자는 분배율 가중값이라 단위가 다름 · 직접 1.0 / 보조 0.5 척도로 바꾸면 둘이 같은 단위가 됨

같은 운동의 기여도가 등록 부위 수에 흔들리지 않음 — 위 데드리프트 예에서 둔근 목표 4세트분을 채우는 데 스미스는 10세트, 바벨은 40세트가 필요함 · 같 은 운동인데 4배 차이가 나는 것이 사라짐

다관절 운동이 불리해지는 역전 해소 — 실제로는 여러 근육에 볼륨을 쌓는 운동인데 합계 1.0 제약 때문에 각 부위 값이 작아져 반대로 계산되고 있음 원값 보존으로 되돌릴 수 있음 — 부하율은 15개 값(0.05~1.0)을 가지므로, 2택으로 덮어쓰면 0.1과 0.3의 구분이 영구 소멸 · 원값을 남기면 임계값 사후 조 정과 3단계 척도 전환이 가능

### 주의

- 상대 기준은 값 하나만 보고 판정할 수 없음 — 그 운동의 부위 전체를 봐야 하므로, 판정 결과를 직접 / 보조 값으로 컬럼에 굳혀 저장해야 함 · 조회 시점 계산으로 두면 매 쿼리가 운동 단위 최댓값을 다시 구해야 함 부하율을 수정하면 그 운동의 기여도를 재산출해야 함 — 원값이 남아 있으므로 재산출은 언제든 가능하지만, 운영 절차에 "부하율 변경 시 기여도 재산 출" 단계가 들어가야 함

- 기여도는 운동별 합계 제약 없음 — 한 세트가 여러 근육에 각각 계상되는 것이 정상

## 09. 무게 단위 환산 구조 정비

단위와 무게 값이 다른 테이블에 있어 생기는 랭킹 오류를 세트 행 안에서 완결시키는 작업

#### FIG 4 무게 단위와 무게 값의 저장 위치

현행 — 단위와 값이 다른 테이블 변경 후 — 세트 행 안에서 완결 **`user_exercise_session_history user_exercise_set_history`** `weight_type` lb `weight` 100.0 매 집계마다 조인 **`weight_unit`** lb (상위 행에서 복사) **`weight_kg`** 45.3592 (생성 열) **`user_exercise_set_history`** `weight` 100.0 생성 열은 같은 행의 컬럼만 참조 가능 — 단위 복사가 전제 환산 무게에 인덱스 부여 — 최고 중량 조회가 정렬 스캔에서 인덱스 조회로 전환 표시용 원값과 계산용 환산값을 분리 보관 — 회원 화면에는 입력 원값 그대로 조인이 빠지면 100파운드(45.4kg)가 100킬로그램으로 오독 — 약 2.2배 과대평가 파운드 기록 9,507건 · 전체 세트의 7.1%

### 무엇을 바꾸는가

회원은 킬로그램·파운드 중 원하는 단위로 입력하고 그대로 저장 · 활용 계층에서 자동 환산 · 이를 위해 세트 테이블에 단위 컬럼과 환산 무게 컬럼을 추가 현행 구조의 문제는 값이 아니라 위치

|데이터|저장 위치|
|---|---|
|무게 단위(<br>`kg`·<br>`lb`)|운동 단위 테이블|
|무게 값|세트 단위 테이블|

실측 — 파운드 기록 9,507건, 킬로그램 124,276건 · 전체의 7.1%

### 어떻게 바꾸는가

1. 세트 테이블에 단위 컬럼 추가 — 운동 단위 테이블의 값을 복사해 채움

2. 세트 테이블에 환산 무게 컬럼을 생성 열로 추가 — 단위가 파운드면 0.45359237을 곱해 킬로그램으로 환산 · 킬로그램이면 그대로

3. 표시용 원값과 계산용 환산값을 분리 보관 — 회원 화면에는 입력 원값과 원단위를 그대로 되돌려 표시

4. 환산 계수를 한 곳에 고정 — 애플리케이션 코드 여러 곳에 상수를 두지 않음

- 생성 열을 쓰는 이유 — 데이터베이스가 값을 보장하므로 저장 경로가 여러 개여도 값이 어긋나지 않음 · 일반 컬럼에 애플리케이션이 계산해 넣는 방식은 경 로 하나가 빠지면 값이 비거나 틀림 · 단, 생성 열은 같은 행의 컬럼만 참조 가능하므로 단위 컬럼을 세트 테이블로 가져오는 1번 작업이 전제

### 무엇이 좋아지는가

랭킹이 성립함 — 단위를 무시하고 무게를 비교하면 파운드 기록이 약 2.2배 과소평가됨 · 100파운드(45.4kg)를 든 회원이 100킬로그램으로 오독되면 1위 가 되고, 반대로 실제 파운드 사용자는 순위에서 밀림 · 랭킹은 1건의 오류가 최상위를 만들기 때문에 다른 분석보다 오염에 민감

집계에서 조인이 사라짐 — 지금은 훈련량을 계산할 때마다 세트에서 운동 단위 테이블로 조인해 단위를 확인해야 함 · 세트에 환산값이 있으면 조인 없이 합 산 가능하고 환산 무게에 인덱스를 걸 수 있음(최고 중량 조회가 정렬 스캔에서 인덱스 조회로 바뀜) 환산 누락 경로가 사라짐 — 환산을 조회 시점에만 하면 랭킹·훈련량·추정 최대 중량·리포트 등 계산 경로마다 같은 로직을 복제해야 하고, 한 곳이 빠지면 그 화면만 조용히 틀린 값을 보여줌

표시 정합성 유지 — 파운드로 입력한 회원에게 환산값을 되돌려 보여주면 반올림 때문에 입력값과 다른 숫자가 표시됨 · 원값 보존으로 이 문제가 발생하지 않음

### 주의

- 반올림 정책 확정 필요 — 환산 무게의 소수 자리와 반올림 방향 · 랭킹 동점 판정에 영향 무게가 비어 있는 세트가 11,985건(전체 296,176건 중 4.0%) — 맨몸 종목이 정상 · 환산 컬럼도 비워 두고 계산에서 제외 파운드 입력은 계속 허용하기로 확정(2026-08-21) · 따라서 환산은 과거 9,507행을 정리하는 1회성 작업이 아니라 입력이 계속 들어오는 상시 경로 · 조 회 시점 계산이 아니라 저장 시점 생성 컬럼으로 두어야 하는 근거가 됨

## 10. 세트 테이블에 대리키·수행 시각 추가

세트에 안정된 식별자와 수행 시각을 부여해 시간 흐름 분석을 여는 작업

### 무엇을 바꾸는가

세트 테이블에 대리키와 세트 수행 시각을 추가하고, 저장 방식을 삭제 후 재삽입에서 갱신 방식으로 전환

현행 세트 테이블 — 컬럼 4개(운동 기록 식별자 · 세트 번호 · 횟수 · 무게) · 기본키가 자연키 복합(운동 기록 식별자 + 세트 번호) · 시각 컬럼 없음 · 301,572 행(2026-08-21 실측 · 문서 최초 작성 시점 296,176행에서 증가)

### 어떻게 바꾸는가

1. 대리키 추가 후 기본키 이관 — 기존 자연키 복합 기본키는 고유 제약으로 유지

2. 세트 수행 시각 컬럼 추가 — 회원이 그 세트를 마친 시각 · 클라이언트가 전달

3. 기록 저장 시각·수정 시각 추가 — 서버 기준

4. 저장 방식 전환 — 현재는 세트를 고칠 때 해당 운동의 세트를 전부 지우고 다시 넣는 방식이라 시각이 매번 재작성됨 · 갱신 방식으로 바꾸지 않으면 시각 컬럼을 추가해도 값이 무의미

5. 세트 시작 시각은 후속 — 타이머 화면이 준비될 때 추가

전환 범위 확정(2026-08-21) — 두 항목의 적용 범위를 다르게 둠

|항목|적용 범위|근거|
|---|---|---|
|대리키 부여|전건(301,572행)|값 자체에 의미가 없어 소급 부여가 안전·최고 기록의 근거 세트 참조가 과거 기록에도 필요|
|수행 시각|신규 기록만·과거는 빈 값 유지|과거 세트의 실제 수행 시각을 알 근거가 없음|
|저장 방식(갱신 전환)|신규 기록만|과거 기록을 갱신 방식으로 소급 전환할 대상이 없음|

과거 기록에 시각을 채우지 않는 이유 — 세션의 시작·종료 시각으로 보간하면 추정치가 원천 테이블에 실측값처럼 들어감 · 그러면 세트 간 휴식 분석이 보간 으로 만들어낸 균등 간격을 실제 휴식 패턴으로 오해 · 작업 원칙 3(파생 지표는 저장하지 않고 원천을 보관)에 정면으로 어긋남 수행 시각과 저장 시각을 나누는 이유 — 휴식 시간 분석은 회원이 실제로 세트를 마친 시각이 필요함 · 저장 시각은 화면을 벗어날 때 한꺼번에 기록될 수 있 어 세트 간 간격을 나타내지 못함

### 무엇이 좋아지는가

세트 간 휴식 시간을 산출할 수 있음 — 다음 세트 수행 시각에서 이전 세트 수행 시각을 빼면 휴식 간격이 나옴 · 지금은 세트에 시각이 전혀 없어 이 분석이 원천적으로 불가능하고, 운동 단위 시각만으로는 세트 간격을 알 수 없음 세션 내 시간 흐름 분석이 열림 — 운동 효율성 리포트(시간당 훈련량·준비 대기 시간·운동이 길어지는 원인)와 수행 품질 리포트(세트 후반 지연)가 이 값에 의존

개인 최고 기록의 근거를 참조할 수 있음 — 현재 기본키가 자연키 복합이라 같은 (운동, 세트 번호)가 다른 값으로 재삽입되면 참조가 다른 기록을 가리킴 · 대 리키가 있으면 "이 최고 기록은 이 세트에서 나왔다"를 안정적으로 남길 수 있고, 나중에 오염 기록이 발견되면 그 최고 기록만 무효화 가능 세트 수정 이력이 보존됨 — 삭제 후 재삽입 방식은 회원이 무게를 고칠 때 이전 값을 지움 · 갱신 방식으로 바꾸면 수정 시각이 남아 비정상 입력 패턴을 탐지 할 수 있음

### 주의

- 저장 방식 전환이 이 항목의 실질 — 컬럼만 추가하고 저장 방식을 그대로 두면 시각 값이 매 저장마다 갱신되어 분석에 쓸 수 없음 과거 기록에는 수행 시각을 소급 채울 수 없음 · 운동 단위 생성 시각으로 근사하면 세트 간격이 모두 0이 되므로 비워 두고 분석 대상 기간을 이후로 한정 시각 기반 분석의 표본이 전환 시점 이후로 한정됨 — 초기 몇 개월은 세트 간 휴식·세션 내 시간 흐름 분석의 표본이 부족함 · 리포트에 수집 시작 시점을 반드시 표시해야 하고, 표시하지 않으면 휴식 시간 평균이 전체 기간 평균으로 오해됨 대리키 추가 시 기존 자연키 조합을 고유 제약으로 남겨야 함 · 같은 운동에 같은 세트 번호가 두 번 들어오는 것은 여전히 차단 대상

## 11. 세트 단위 강도 컬럼 신설

세션 1개 값으로는 보이지 않는 세트 후반 품질 하락을 볼 수 있게 하는 작업

### 무엇을 바꾸는가

세트 테이블에 강도 컬럼을 신설하고 값 없음을 허용 · 컬럼만 먼저 열고 입력 강제는 화면이 준비된 뒤

현행 — 강도는 세션 단위 1개 값 · 컬럼은 `user_exercise_session.rpe` · 자각 강도 1~10 정수 척도

|항목|실측(2026-08-21)|
|---|---|
|전체 세션|327,844건|
|강도 값이 있는 세션|188,095건(57.4%)|
|값 분포|1~10 전 구간 사용·최빈값 5(66,412건) ·기본값이 박힌 것이 아니라 회원이 실제로 고르는 값|

### 어떻게 바꾸는가

1. 세트 테이블에 강도 컬럼 추가 · 값 없음 허용

2. 척도는 세션과 같은 자각 강도 1~10으로 확정(2026-08-21) · 세트 컬럼도 세션과 동일한 정수 척도

3. 값의 정의를 규약 문서에 고정 — 회원마다 다르게 이해하면 비교가 성립하지 않음

4. 계산 우선순위 규칙 명문화 — 노력 충족 판정은 세트 강도 우선, 없으면 세션 강도 · 두 값이 공존하므로 규칙 없이는 화면마다 다른 답이 나옴 5. 입력 강제와 화면은 후속

자각 강도 1~10을 택한 이유 — 세션 값과 직접 비교·롤업이 가능함 · 세트 평균과 회원이 신고한 세션 값을 대조해 입력 신뢰도를 검증할 수 있고, 다른 척도 를 쓰면 이 대조가 불가능 · 회원이 이미 쓰고 있는 척도라 학습 비용이 없고 기존 18만여 건과 시계열이 끊기지 않음 여유 반복 수를 버리는 것은 아님 — 두 값은 배타적이지 않으므로, 추정 최대 중량 환산 정밀도가 필요해지는 시점에 컬럼을 하나 더 추가하면 됨 · 지금 하나 만 고른다면 이미 쌓여 있는 쪽

### 무엇이 좋아지는가

세트 후반 품질 하락을 볼 수 있음 — 세션 값 하나로는 "총량이 늘었는데 품질도 좋아졌나"를 구분할 수 없음 · 세트별 값이 있으면 첫 세트와 마지막 세트의 차이, 세트가 진행될수록 여유가 줄어드는 속도를 볼 수 있음 정체 원인을 유형으로 나눌 수 있음 — 같은 중량에서 강도가 오르는 패턴은 회복 부족, 강도가 낮은데 성과가 없는 패턴은 자극 부족 · 세션 값만으로는 이 구 분이 불가능해 정체를 "성장 없음"으로만 표시하게 됨 노력 충족 목표가 성립함 — 마지막 세트에 여유 반복을 2~3개 남기는 수준을 목표로 삼는 계산이 가능해짐 지금 열어두면 이후 기록부터 쌓임 — 강도는 소급 입력이 불가능한 값 · 화면이 나중에 준비되더라도 컬럼이 먼저 있으면 준비된 시점부터 즉시 수집 시작

### 주의

- 세트마다 강도를 기록하고 싶어 하는지 사용자 의견 취합이 선행 필요 — 운동을 많이 하고 운동기록을 자주 쓰는 회원이 세트 단위 강도 입력을 실제로 원 하는지 확인되지 않음 · 원하지 않는다면 컬럼은 열어두더라도 화면은 만들지 않는 편이 낫고, 세션 단위 값(현재 57.4% 수집)으로 유지하는 선택도 성립 함 · 구조 준비와 별개로 화면 설계 착수 전 의견 취합을 조사 항목으로 등록 입력 부담이 기록률을 깎을 수 있음 — 세트마다 값을 요구하면 기록 자체를 포기할 위험 · 마지막 세트만 묻는 방식 등 입력 범위는 의견 취합 결과와 화면 설계에서 결정

- 세션 값 수집률 57.4%가 기준선 — 세트 단위 수집률이 이보다 크게 떨어지면 화면 설계가 실패한 것으로 판정 가능 값 없음이 대부분인 기간에는 표본 편향 — 강도를 입력한 회원만 분석되므로 전체 대표성이 없음 · 리포트에 수집률을 함께 표시

- 세션 값과 세트 값의 합산 금지 — 척도는 같지만 단위(세션 1건 대 세트 여러 건)가 달라 섞으면 의미가 어긋남 · 계산 우선순위 규칙으로만 사용하고, 세 트 평균과 세션 값의 대조는 검증 목적으로만

## 12. 개인 최고 기록 이력 테이블 신설

정체 구간과 최고 기록 달성 수 산출의 전제가 되는 이력 테이블을 신설하는 작업

### 무엇을 바꾸는가

회원×종목 단위로 최고 기록의 이력을 쌓는 테이블 신설 · 갱신할 때 기존 행을 고치지 않고 행을 추가 부위별 최고 기록은 저장하지 않음 — 부위 강도는 종목에 종속되므로 종목 단위 기록에 부위 매핑을 적용해 파생으로 계산 · 작업 원칙 3에 따름

### 어떻게 바꾸는가

기록 종류를 열거형이 아니라 참조 테이블로 관리하기로 확정(2026-08-21)

1. 기록 종류 참조 테이블 신설 — 종류 코드 · 한글 표기명 · 값의 단위 · 유효 범위 · 적용되는 측정 방식 · 정렬 순서 · 상태

2. 최고 기록 이력 테이블 신설 — 회원 · 종목 · 기록 종류 참조 · 기록 값 · 환산 무게 · 반복 수 · 근거 세트 참조 · 달성 시각 · 근사값 여부

3. 갱신 시 행 추가 · 현재 최고값은 부분 고유 제약 또는 조회 뷰로 구분

4. 근거 세트 참조는 세트 대리키(§10)가 전제 — 자연키 복합 기본키를 참조하면 세트가 재삽입될 때 다른 기록을 가리킴

5. 과거 기록으로 초기 적재 — 기존 세트에서 종목별 최고값을 계산해 1건씩 생성 · 달성 시각은 운동 단위 생성 시각으로 근사하고 근사값임을 표시

### 무엇이 선행이고 무엇이 선행이 아닌가

기록 종류 목록 확정은 선행이 아님 — 확정을 선행 조건에서 빼기 위해 참조 테이블을 택하는 것 · 열거형으로 고정하면 종류 목록이 곧 컬럼 정의가 되므로 목록이 확정되기 전에는 테이블을 만들 수 없음 · 참조 테이블이면 그 선후 관계가 끊어지고 종류 추가가 행 삽입으로 끝남

선행 1 — 기록 값을 담는 모양 · 종류를 다 몰라도 결정 가능

|종류|값의 형태|단위|
|---|---|---|
|최고 중량|숫자 1개|킬로그램|
|최고 반복 수|숫자 1개|회|
|단일 세트 최고 훈련량|숫자 1개|킬로그램·회|
|세션 최고 훈련량|숫자 1개|킬로그램·회|
|최장 지속 시간|숫자 1개|초|

선행 2 — 측정 방식 선언(§4) · 어느 종류가 어느 종목에 성립하는지를 규칙으로 담으려면 종목별 측정 방식이 먼저 정해져 있어야 함 · 유산소 종목에 "최고 중량" 기록이 생기는 것을 막는 장치가 여기서 나옴 · 강제 순서 §4 → §12

시작 종류는 실측으로 정함 (세트 기록 301,572행 · 2026-08-21)

|---|---|---|
|무게가 0보다 큰 세트|288,798행|95.8%|

최장 지속 시간은 지금 만들지 않음 — 시간 값이 있는 원천은 루틴 계열 44,230행 중 2,061행(4.7%)뿐이고 세트 테이블에는 시간 컬럼이 아예 없음 · 열거형 이었다면 이 종류를 넣을지를 지금 결정해야 했으나, 참조 테이블이면 시간 수집이 정비된 뒤 행 하나 넣으면 됨

### 무엇이 좋아지는가

정체 구간을 산출할 수 있음 — "몇 주째 최고 기록이 갱신되지 않았나"는 최고 기록의 달성 시점이 있어야 계산됨 · 현재값만 알면 정체 여부를 알 수 없음 최고 기록 달성 수를 목표로 쓸 수 있음 — 주간·월간 리포트의 "이번 달 달성한 최고 기록" 항목과 개인 최고 기록 갱신 목표가 이 테이블에 의존 랭킹 조회가 가벼워짐 — 종목별 순위를 낼 때마다 29만 건의 세트를 스캔하는 대신 회원별 최고값만 읽으면 됨 · 모집단 4.5만 명 규모에서 응답 시간 차이가 큼

오염 기록을 사후에 무효화할 수 있음 — 맨몸 종목에 무게가 들어온 세트처럼 잘못된 기록이 최고 기록을 만든 경우, 근거 세트 참조가 있으면 그 최고 기록만 골라 무효 처리 가능 · 참조가 없으면 전량 재계산이 유일한 방법 기준 변경에 강함 — 추정 최대 중량의 계산식이나 반복 수 상한이 바뀌어도, 근거 세트의 무게·반복 수가 남아 있으므로 이력을 다시 만들 수 있음 측정 방식별로 성립하는 기록 종류를 규칙으로 표현할 수 있음 — 종류 참조 테이블에 "적용되는 측정 방식"을 메타로 두면, 새 종목이 등록될 때 그 종목에 어 떤 최고 기록이 생기는지를 사람이 판단하지 않고 규칙이 결정 · 열거형으로는 이 메타를 붙일 자리가 없음 종류를 늘려도 회원 기록 테이블의 정의를 바꾸지 않음 — 최고 기록 이력은 회원 수에 비례해 계속 커지는 테이블이므로, 종류를 하나 늘릴 때마다 이 테이블 의 열거형을 확장하는 것은 대량 테이블 정의 변경을 반복하는 것

### 주의

- 갱신 방식을 수정으로 하면 목적이 사라짐 — 현재값만 남으면 달성 시점과 정체 기간을 알 수 없음 추정 최대 중량은 파생값이므로 계산식과 함께 기록 — 어떤 규칙으로 만든 값인지 남기지 않으면 규칙 변경 후 과거 값과 비교가 불가능 초기 적재분의 달성 시각은 근사값 · 근사 여부를 구분하는 표시가 필요

- 참조 테이블의 한계 — 값이 종류에 맞는지 DB가 보장하지 못함 · 값 모양을 일반화했으므로 "최고 반복 수" 기록에 무게 값이 들어가도 숫자로는 유효함 · 종류 테이블의 단위 · 유효 범위 를 근거로 서버가 검증해야 하며, 이는 열거형 + 종류별 전용 컬럼만큼 강한 보장은 아님 · "종류를 나중에 늘릴 수 있음"과 "값이 종류에 맞는지 DB가 보장함"을 맞바꾼 선택

- 종류 참조 테이블에도 상태 컬럼 필요 — 잘못 등록된 종류를 물리 삭제하면 그 종류로 쌓인 이력이 고아 행이 됨

`4` 측정 방식 선언 `──` 필수 선행 `──→  12` 최고 기록 이력 `(` 종류별 성립 규칙 `) 4` 측정 방식 선언 `──` 선행 `──→        5` 장비 `12` 종 `· 6` 부위 기여도 `10` 세트 대리키 `·` 시각 `──` 필수 선행 `──→  12` 최고 기록 이력 `(` 근거 세트 참조 `)`

   - 4 → 12 — 어느 기록 종류가 어느 종목에 성립하는지를 종류 참조 테이블에 담으려면 종목별 측정 방식이 먼저 정해져 있어야 함 · 없으면 유산소 종목에 최고 중량 기록이 생기는 것을 막을 수 없음 10 → 12 — 세트가 자연키 복합 기본키인 상태에서 근거 세트를 참조하면 세트 재삽입 시 다른 기록을 가리킴

#### 라. 관계도 표기 규칙

- 신설 개체 — 굵은 테두리 + 신설 표시

- 변경 개체 — 변경된 컬럼만 별도 표기하고 미변경 컬럼은 생략 제거 개체 — 점선 테두리 + 이관 방향 화살표( `exercise_function` → 두 신설 테이블)

- 외래키 연결 — 실선

- 논리 연결(값 복사·값 대조) — 점선 · 17-4-다의 5건 · 실선과 반드시 구분해야 함(외래키로 오해하면 참조 무결성이 있다고 착각)

- 강제 순서 — 화살표에 순서 번호 표기( `4 → 12` · `10 → 12` · `9 → 12` ) 행수 구간 — 개체 하단에 표기하고 30만 행 이상은 강조(변경 작업의 잠금 위험 지점)

#### 마. 관계도에 반드시 드러나야 할 4가지

1. **`exercise_function`** 하나가 두 테이블로 갈라지는 것 — 이번 개편의 핵심이며, 효과 축은 계산 경로에 연결되고 추천용은 연결되지 않는다는 사실

2. 분류 매핑(B)과 회원 기록(C)이 직접 연결되지 않고 **`exercise`** 를 경유하는 것 — 부위별 랭킹·부위 커버리지가 3단 조인이 되는 이유

3. 무게 단위가 상위 행에, 무게 값이 세트 행에 있는 현행 구조와 단위를 세트로 복사하는 변경 — 랭킹 오류의 원인이자 생성 열 제약의 결과

4. 최고 기록이 세트 대리키를 참조하는 것 — 대리키가 없으면 이 연결이 성립하지 않는다는 것이 강제 순서의 근거
