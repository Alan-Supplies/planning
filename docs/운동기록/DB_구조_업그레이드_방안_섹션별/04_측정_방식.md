# 04. 측정 방식 선언 — 불리언 플래그 3종

> [전체 목차](README.md) · [통합 원문](../DB_구조_업그레이드_방안.md)
>
> 2026-09-03 변경 — `measure_type enum(3종)` 신설을 **취소**하고 `exercise` 불리언 플래그 3종으로 대체 · `count` / `duration_second` 분리는 이미 완료됨 · 근거: [최고 기록 종류 enum 변경 명세](최고기록_종류_enum_변경_명세.md)

세트 값의 의미를 운동 마스터 조인 없이 확정하고 서버 검증의 근거를 만드는 작업

## 무엇을 바꾸는가

`exercise` 테이블에 측정 방식 플래그 3종을 둔다 — `has_weight`(기존) · `has_duration`(신설) · `has_reps`(신설). 현재는 단위 컬럼과 무게 보유 여부 컬럼의 조합에서 매번 추론한다(실측 조합 12종).

**종전 안(`measure_type enum('WEIGHT_REPS','REPS','DURATION')`)은 취소했다.** enum 단일값은 "무게도 있고 시간도 있는" 종목(웨이티드 플랭크 등)을 표현하지 못하고, 성립 조건을 AND 로 쓸 수도 없다. 플래그 3종은 둘 다 된다.

## 관련 테이블 구조

|테이블|이번 작업과의 관계|
|---|---|
|`exercise`|플래그 2종 신설 · `id` · `name` · `unit` · `has_weight` 보유|
|`user_exercise_session`|세션 — 출입 1건당 1개 · 세션 강도 보유(`rpe`)|
|`user_exercise_session_history`|그 세션에서 수행한 운동 1건|
|`user_exercise_set_history`|세트 1개 · `set_number` · `count` · `weight` · `duration_second`|

종전에 문제의 핵심이었던 것은 세트 테이블의 `count` 컬럼이 "횟수 or 초" 겸용이라 세트 행만 봐서는 `count=30` 이 30회인지 30초인지 알 수 없다는 점이었다. **이 부분은 `duration_second int unsigned NULL` 분리로 이미 해결됐다**(개발 DB 반영 완료). 다만 `count` 주석대로 **과거 행에는 초값이 그대로 남아 있어** 시간 종목의 과거 세트를 횟수로 읽으면 오염된다.

## 어떻게 바꾸는가

`has_weight` 는 이미 있으므로 2개만 추가한다.

```sql
ALTER TABLE exercise
  ADD COLUMN has_duration tinyint(1) NOT NULL DEFAULT 0
    COMMENT '시간 측정 여부(세트의 duration_second 를 채우는 종목)' AFTER has_weight,
  ADD COLUMN has_reps tinyint(1) NOT NULL DEFAULT 0
    COMMENT '반복 수 측정 여부(세트의 count 를 횟수로 채우는 종목)' AFTER has_duration;
```

백필과 검수가 끝난 뒤 CHECK 제약을 건다. **이번 배포에는 넣지 않는다(보류 · 2026-09-03)** — 검수 중 값 수정이 제약에 막히기 때문이며, 그때까지 "셋 다 0" 을 막는 것은 서버 검증뿐이다.

```sql
ALTER TABLE exercise
  ADD CONSTRAINT chk_measure CHECK (has_weight + has_duration + has_reps >= 1);
```

이 제약이 플래그 전환의 **유일한 퇴보를 막는 장치**다. `measure_type` 은 `NOT NULL` 단일값이라 "아무것도 측정하지 않는 종목"이 구조적으로 불가능했으나, 불리언 3개로 쪼개면 셋 다 0인 행이 만들어진다. 그런 종목은 세트에 채울 값이 없고 최고 기록도 성립하지 않는다.

초기 부여는 `unit` 을 근거로 한다. **컬럼 추가와 같은 배포에서 반드시 함께 실행한다** — `DEFAULT 0` 이므로 컬럼만 추가하면 전 행이 0 이 되어 "모든 종목이 아무것도 측정하지 않음" 상태가 되고, 그러면 최고 기록 종류가 어느 종목에도 성립하지 않는다([12](12_개인_최고_기록_이력.md)).

```sql
-- (A) 기존 선언(unit)을 플래그로 1:1 이관
UPDATE exercise
   SET has_duration = (unit <=> 'MINUTE'),
       has_reps     = (unit <=> 'SET');

-- (B) 세트 실측 보강 — duration_second 가 실제로 쌓인 종목은 unit 과 무관하게 시간 종목
UPDATE exercise e
   SET e.has_duration = 1
 WHERE e.has_duration = 0
   AND EXISTS (SELECT 1
                 FROM user_exercise_session_history h
                 JOIN user_exercise_set_history s
                      ON s.user_exercise_session_history_id = h.id
                WHERE h.exercise_id = e.id
                  AND s.duration_second IS NOT NULL);
```

**`=` 가 아니라 NULL-safe `<=>` 를 쓴다.** `exercise.unit` 은 `varchar(30) NULL` 이라(`V4_26_0__exercise.sql`) NULL 행에서 `unit = 'MINUTE'` 의 결과가 NULL 이 되고, `NOT NULL` 컬럼에 NULL 을 대입해 strict mode 에서 실패한다. 개발 DB 에는 NULL 이 0건이지만 컬럼이 허용한다.

(A) 는 **오늘 DB 가 실제로 담고 있는 정보를 그대로 옮기는 것이고 새로 추정하는 것이 없다** — `unit` 은 이 스키마의 유일한 측정 방식 선언이고, `V4_31_2` 의 `duration_second` 백필도 `e.unit = 'MINUTE'` 을 조건으로 썼다. (B) 는 `unit` 이 NULL 이거나 `SET` 인데 시간이 쌓인 종목을 건진다.

역방향(`count` 가 쌓였으니 `has_reps = 1`)은 하지 않는다 — `count` 는 과거 행에 초값이 그대로 남아 있어서 `count > 0` 이 횟수 종목의 근거가 되지 못한다.

**(A) 가 만들 수 없는 것은 "둘 다 1" 조합이다.** `unit` 이 단일값이라 그 정보가 애초에 DB 에 없다. 해당 종목 확정은 트레이너 검수로 넘기고, 검수 후 그 종목만 `UPDATE` 로 올린다 — 마이그레이션을 되돌릴 필요는 없다.

서버 검증은 이 플래그 조회에서 도출한다 — 하드코딩 금지.

|플래그 조합|`count` 의 의미|`weight`|`duration_second`|서버 검증|
|---|---|---|---|---|
|`has_weight=1` · `has_reps=1`|횟수|필수|없어야 함|무게 없으면 요청 거부|
|`has_reps=1` 단독|횟수|없어야 함|없어야 함|무게가 오면 요청 거부|
|`has_duration=1` 단독|사용 안 함|없어야 함|필수|무게가 오면 요청 거부|
|`has_weight=1` · `has_duration=1`|사용 안 함|필수|필수|웨이티드 플랭크 등 · enum 으로는 표현 불가했던 조합|

## 무엇이 좋아지는가

세트 데이터를 단독으로 해석할 수 있게 된다 — 현재는 세트 값의 의미를 알기 위해 상위 두 테이블을 조인해야 하며, 데이터 웨어하우스 적재 시 이 추론이 파이프라인마다 반복된다.

오염 데이터 유입 차단 — 맨몸 풀업에 무게가 들어온 세트가 1,621건이며 유일한 검증이 클라이언트 한 곳이었다. 어시스트 머신 중량과 추가 중량이 섞여 총부하와 1회 최대 반복 중량 추정을 오염시킨다. 플래그에서 규칙을 도출하면 운동 유형이 늘어도 검증이 자동 확장된다.

입력 화면이 데이터로 결정된다 — 무엇을 입력받을지가 플래그로 정해지므로 클라이언트의 폴백 추론 코드를 삭제할 수 있다. 현재 그 코드가 밴드·구조물 종목을 오판한다.

계산 가능 범위가 명확해진다 — 총부하와 1회 최대 반복 중량 추정은 `has_weight = 1 AND has_reps = 1` 종목에서만 성립한다. 지금은 대상 판별이 추론이라 계산이 조용히 잘못된 종목을 포함할 수 있다.

**최고 기록 종류의 성립 조건을 AND 로 쓸 수 있다** — `MAX_SET_VOLUME` 은 `has_weight = 1 AND has_reps = 1` 이다([12](12_개인_최고_기록_이력.md) 참조). enum 단일값으로는 표현할 자리가 없었다.

## 주의

- 검수 지점 — `unit='MINUTE'` 23종 중 횟수도 세는 종목(인터벌·서킷 계열)이 있으면 `has_duration` 과 `has_reps` 이 모두 1이 된다. 그 종목이 존재하는지가 [12](12_개인_최고_기록_이력.md) `MAX_SET_VOLUME` 정의의 전제다.
- 플래그 3종이 전부 0인 행은 위 `chk_measure` CHECK 제약이 막는다. 다만 "무게+시간" 처럼 조합이 실제 종목과 맞는지는 DB 가 판정하지 못하므로 트레이너 검수와 주기 감사 쿼리가 필요하다.
- **플래그 이름은 `has_` 접두로 통일했다** — `has_weight` 의 직계 형제이고 같은 축(값 컬럼을 채우는가)이기 때문이다. `is_repeatable` 을 검토했으나 "세트를 여러 번 할 수 있는"으로 읽혀 모든 운동에 해당하게 되고, 값 보유에 `is_` 를 쓰는 전례가 이 스키마에 없다(개발 DB 전수 조회 결과 `has_` 4건 · `is_` 42건은 전부 상태·분류).
- 남는 불일치 — 플래그는 `has_reps` 인데 세트의 값 컬럼은 `count` 다. `has_count` 로 맞추지 않는 이유는 `count` 자체가 나쁜 이름이기 때문이다(SQL 함수명과 겹쳐 백틱 필요 · 횟수와 초를 겸용했던 이력). 그 이름을 플래그로 전파하는 대신 `count` → `reps` 개칭을 별건으로 남긴다([15](15_남은_결정_조사_항목.md)).
- 축이 겹치는 컬럼이 `unit` · `training_type` · `weight_role` 과 플래그 3종이 된다. 어느 것이 판정 근거인지 정리가 필요하다([15](15_남은_결정_조사_항목.md)).
- 거리 측정은 이번에 제외 — 현재 해당 종목 0건이고 저장 컬럼도 없다. `count` 에 미터를 넣으면 한 컬럼이 횟수·초·거리 3중 의미가 되어 문제가 커진다. 트레드밀 거리 기록을 실제로 도입할 때 저장 컬럼과 함께 추가한다.
