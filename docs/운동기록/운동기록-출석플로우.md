# 운동 기록 출석 플로우 — 조사 종합

> 조사일: 2026-08-11 · 환경: dev · 대상 계정: user_id 51758(Alan), gym_id 494
>
> "USER APP 출석 → PASS 앱 바코드 스캔 → 앱 소켓 수신"까지의 전 과정을 코드 근거와 함께 정리한다.
> **이 문서는 이해·지도용**이고, **실제 재현 실행 매뉴얼과 curl은 [운동기록.probe](운동기록.probe)**,
> **자동 재현 스크립트는 [replay-workout-flow.js](replay-workout-flow.js)** 에 있다.

## 왜 이 문서가 필요했나

`plan/habit-OS/운동기록플로우계선.md`의 테스트 흐름 3~4번(소켓으로 앱에 성공 전달 → 출석 상태 전환)을
**정확히 아는 사람이 없었고**, 앱 로그인 때문에 반복 테스트가 번거로웠다. 이 둘을 코드로 역추적해
확정하고, 앱·PASS 기기 없이 재현 가능하게 만드는 것이 목표였다.

## 시스템 지도

| 역할 | 저장소 | 형태 | 비고 |
|---|---|---|---|
| USER APP 서버 | `gymboxx-app-server` | NestJS, prefix `/app` | 로그인·바코드 생성 |
| PASS 기기 서버 | `gymboxx-pass-server` | NestJS, prefix `/pass` | 바코드 검증·출석 기록·소켓 트리거 |
| 앱 소켓 | `app-web-socket` | Serverless (API GW WebSocket + Lambda + DynamoDB) | 실제 소켓 push |
| ~~admin 소켓~~ | ~~`web-socket-server`~~ | NestJS | **이 흐름과 무관** — admin 웹 전용(주문·PT·머신) |

> ⚠️ 함정 1: `web-socket-server`를 먼저 열면 출석 관련 코드가 하나도 없어 헤맨다. 앱으로 가는 소켓은
> `app-web-socket`이다. (`web-socket-server`의 게이트웨이 이벤트는 `refresh`/`food-order`/`pt-*`뿐)

### 엔드포인트 (dev)

```text
APP  : https://dev1.supp.fitness/app
PASS : https://dev1.supp.fitness/pass
소켓 REST (today-workout 트리거) : https://kun6eu8mq0.execute-api.ap-northeast-2.amazonaws.com/dev
소켓 WS   (앱이 붙는 곳)         : wss://bq6ert948k.execute-api.ap-northeast-2.amazonaws.com/dev
```

소켓 주소 두 개는 같은 serverless 서비스가 만든 **서로 다른 API**다(REST=트리거, WebSocket=앱 접속).
REST 주소는 eks_dev `default/env` configMap의 `APP_WEB_SOCKET_ENDPOINT`, WS 주소는
`app-web-socket/env.yml`의 `WEB_SCOKET_ENDPOINT`에 있다.

## 전체 흐름과 코드 위치

```text
[USER APP] 로그인 → access_token
[USER APP] 출석하기 = 바코드 생성 → { barcode }        ※ 60초 후 INACTIVE
[USER APP] WebSocket 연결 (출석 알림 수신 대기)
[PASS APP] 기기 로그인 → device token
[PASS APP] 바코드 스캔 = 출석 처리
    └ access_history INSERT
    └ pingWebSocketServer()  ─── HTTP GET ──▶ [APP-WEB-SOCKET] today-workout
                                                  └ DynamoDB 에서 connectionId 조회
                                                  └ postToConnection → 앱 수신 (출석 상태 전환)
```

| 단계 | 위치 | 핵심 |
|---|---|---|
| 로그인 | `app-server` `user.controller.ts` `/pin`, `/pin/validation`, `/refresh-token` | access_token(2h)/refresh_token(365d) |
| 바코드 생성 | `app-server` `user.service.ts:1280` `createUserBarcode` | 13자리 난수, 생성 후 60초 뒤 INACTIVE |
| 바코드 검증 | `pass-server` `user.dao.ts:109` `getUserBarcode` | `status=ACTIVE` and `user.status=ACTIVE`만 확인 |
| 출입 판정 | `pass-server` `user.service.ts:64` `identifyUserByBarcode` | 바코드 앞 2자리 분기(10=PASS/SUBSCRIBE, 11=ONE_DAY, VIP, 마케팅) |
| 출석 기록 | `pass-server` `user.service.ts:317` `handleAccessHistory` | `ACCESS`/`REVISIT`에서만 소켓 ping |
| 소켓 트리거 | `pass-server` `user.service.ts:421` `pingWebSocketServer` | today-workout HTTP GET, 실패는 try/catch로 삼킴 |
| 소켓 전송 | `app-web-socket` `message-to-one.ts:40` `postToConnection` | DynamoDB scan → 해당 connectionId로 push |
| 소켓 연결 | `app-web-socket` `onconnect.ts` | `user_id`/`gym_id` 쿼리만 확인, **인증 없음** |

### 소켓 전송 경로 상세 (2단계)

3번 "소켓으로 앱에 전달"은 소켓 emit이 아니라 **서버 간 HTTP + Lambda**의 2단계다.

1. **트리거** — `pass-server` `pingWebSocketServer`(`user.service.ts:421`)가
   `GET {APP_WEB_SOCKET_ENDPOINT}/today-workout/{userId}?access_history_id=&gym_id=` 호출.
   `ACCESS`/`REVISIT`일 때만 불리고(`user.service.ts:329,334`), 실패해도
   `console.log('소켓 서버 ping 실패')`만 찍고 barcode-access는 200 반환.
2. **전송** — `app-web-socket` `message-to-one.ts`:
   - `findConnection`(`:57`) DynamoDB(`DevWebsocketConnections`)를 `userId`로 scan.
     **못 찾으면 조용히 200 반환**(`:29`).
   - `apigwManagementApi` endpoint = `config.websocket.endpoint`(`:32`) = env.yml `WEB_SCOKET_ENDPOINT`(`bq6ert948k`).
   - `postToConnection`(`:40`)으로 push.

### 소켓 payload

```json
{
  "type": "ACCESS",
  "access_history_id": 12345,
  "access_date": "2026-08-10T03:00:00.000Z",
  "gym_id": 494,
  "current_gym_workout": { "CHEST": 0.2, "BACK": 0.1, "SHOULDER": 0, "ARM": 0, "LEG": 0.7, "CARDIO": 0 },
  "all_gym_workout": []
}
```

`all_gym_workout`은 `utils.ts`에서 통째로 주석 처리돼 항상 빈 배열.

### payload의 `gym_id`는 어디서 오나

payload의 `gym_id`는 **소켓 연결 시 넘긴 값이 아니라 PASS 기기의 소속 지점**이다. 재현 시
스크립트의 `gymId`(WebSocket 연결 쿼리용)를 5로 바꿔도 payload에는 494가 나오는데, 경로가 다르기
때문이다.

```text
스크립트 gymId  ─▶  WebSocket 연결 쿼리(?gym_id=)에만 쓰임. 소켓은 user_id로만 매칭 → 결과 무관
PASS device     ─▶  device_id = gym_unique_id = gym.id  ← payload의 gym_id는 여기서 결정
```

1. barcode-access는 device 토큰의 `gym_unique_id`를 읽는다 — `identifyUserByBarcode`
   (`pass-server` `user.service.ts:68`): `const { device: { gym_unique_id } } = header`.
2. 그 값으로 gym을 조회해 `gym.id`를 소켓에 넘긴다 — `handleAccessHistory`
   (`pass-server` `user.service.ts:320,329`):
   `getGymByUniqueId(gymUniqueId)` → `pingWebSocketServer(userId, gym.id, ...)`.
3. today-workout이 그 `gym_id`를 그대로 payload에 실는다 — `app-web-socket` `message-to-one.ts:23,36`.

따라서 **실제 출석 지점은 PASS 기기가 결정**한다. 테스트에 쓴 device_id `9000000000004940`이
gym_unique_id `000134`(= gym 494)에 묶여 있어 payload가 494로 나온다. 다른 지점으로 출석시키려면
`gymUniqueId`와 `deviceId`를 그 지점 소속 값으로 바꿔야 한다(스크립트의 `gymId`만으로는 안 됨).

## 테스트 로그인을 편하게 — 3가지 경로

`GET /app/user/{userId}/barcode`는 `JwtAuthGuard` + `UserInterceptor` 대상이라 access_token이 필요하다.

| 방법 | 준비물 | 근거 | 상태 |
|---|---|---|---|
| 1. 테스트 토큰 자체 발급 | 없음 | `refreshUserToken`이 만료 토큰을 서명 검증 없이 디코드 | **채택 (스크립트 기본)** |
| 2. 실제 refresh_token 재사용 | PIN 로그인 1회 | 정상 경로, 취약점 미사용 | 대안 |
| 3. pass-server 토큰 재사용 | — | secret은 같지만 `UserInterceptor`가 막음 | **불가** |

- **방법 1** — `refreshUserToken`(`app-server` `user.service.ts:379`)은 만료된 refresh_token을
  `decodeTokenWithoutVerify`(= `jwtService.decode`, 서명 검증 없음)로 열어 `user_id`만 읽고,
  DB 저장값과 대조하지 않는다. 따라서 `{ user_id, device_id, exp:과거 }`를 **아무 키로나 서명한
  JWT**를 무인증 `PUT /app/user/refresh-token`에 던지면 정상 access_token이 나온다.
  → 이건 편의이자 **인증 우회 취약점**이다(아래 보안 이슈).
- **방법 2** — DB `user.refresh_token`은 bcrypt 해시(`user.dao.ts:1000`,
  `hashSync(getTokenSignature(token), 10)`)라 거기서 원본을 꺼내 재사용하는 건 불가능하다.
  PIN 로그인 1회로 refresh_token을 받아두면 이후 무기한 갱신된다.
- **방법 3** — JWT secret은 실제 동일(두 서버가 eks_dev `default`의 같은 `env` configMap +
  `credentials` secret 공유). 그래서 서명은 통과하지만 `UserInterceptor`
  (`app-server` `common/interceptor/user.interceptor.ts:50`)가 `user.user_id !== +params.userId`를
  검사한다. pass 토큰엔 `user_id`가 없어 `403 userId not matched`(401 아님 = secret 동일의 증거).

## 함정 모음 (테스트 전 반드시 알 것)

1. **바코드 수명 60초** — `app-server` `user.service.ts:1280`, `setTimeout(..., 60000)`.
   주석은 `// TODO: 나중에 15초로 다시 변경해야함.`, 함수명은 `...After15Seconds`인데 실제는 60초.
2. **그 타이머는 프로세스 메모리에만 존재** — 파드 재시작 시 타이머가 사라져 해당 바코드가 영구
   ACTIVE로 남는다. dev에서 옛 바코드가 아직 먹히는 이유.
3. **`barcode` 테이블에 만료 시각 컬럼 없음** — `id/number/status/created_at/user`뿐. 검증도 시간을
   안 본다. → DB에 행을 직접 넣으면 만료 없는 테스트 바코드를 만들 수 있다.
4. **REENTER는 소켓 push 없음** — `ACCESS`/`REVISIT`만 ping. 같은 날 두 번째 스캔부터 조용해진다.
   테스트 반복 시 여기 걸린다.
5. **ping 실패가 조용히 묻힘** — barcode-access는 소켓 실패와 무관하게 200. 응답만으로 판단 불가.
6. **소켓 무인증** — `$connect`/`today-workout` 모두 인증 없음. 그래서 앱·PASS 기기 없이 재현 가능.
7. **응답 필드명이 `status`** — barcode-access 응답은 `access_type`이 아니라 `status`로 내려온다
   (`pass-server` `user.serializer.ts:46`). 스크립트가 `access_type`을 봐서 undefined가 났던 원인.

## 보안 이슈 (테스트와 분리해 처리)

방법 1은 정식 취약점이다. `refreshUserToken`이 만료 refresh_token을 서명 검증 없이 열고 DB 대조도
하지 않아, **아무 키로나 서명한 `{ user_id: <임의> }` 토큰으로 임의 회원의 access_token을 발급받을
수 있다.** dev·prod 동일 코드.
관련: `app-server` `user.service.ts:379`, `auth.service.ts:55`(`decodeTokenWithoutVerify`).

부차: 바코드 번호는 `Math.floor(1000000000000 + Math.random()*9000000) + 2000`으로 생성되고 중복
검사가 없다. 번호 공간 약 900만이라 충돌 가능(2000 미만은 VIP·마케팅 예약).
