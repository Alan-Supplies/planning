# 토큰 전파 vs Gateway 헤더 아키텍처 리뷰

## 배경

order-server 인증 방식에 대해 두 가지 접근이 논의되었다.

| 방식 | 설명 |
|---|---|
| **토큰 전파 (현재)** | APISIX에서 JWT 서명 검증 → 토큰을 그대로 NestJS에 전달 → decode만 수행 |
| **Gateway 헤더** | APISIX에서 JWT를 풀어서 `X-Store-Id` 같은 헤더로 변환 → NestJS는 헤더를 신뢰 |

토큰 전파 방식을 선택한 이유: 관리 코드와 Swagger 처리의 편의성.

---

## 1. 파라미터 변조 우려

### 팀원 의견

> storeId를 파라미터로 넘겨주는 상황에서 token과 불일치하거나, 파라미터 변조로 데이터 조작이 발생할 수 있다.

### 판단

우려 자체는 유효하다. 실제로 `sales.service.ts`의 `getDailySales`에서 `branchIds`가 query param으로 들어오면 토큰 검증 없이 그대로 쿼리에 사용되는 코드가 존재한다.

```typescript
// sales.service.ts — branchIds가 비어있을 때만 토큰 폴백
let branchIds = query.branchIds
if (!branchIds || branchIds.length === 0) {
  if (user?.is_all_store_access) { ... }
  else if (user?.store_ids) { branchIds = user.store_ids }
}
// branchIds가 있으면 검증 없이 사용됨
```

**그러나 이 문제는 "Gateway 헤더 vs 토큰 전파" 선택과 무관하다.**

어느 방식이든 파라미터로 `storeId`를 받으면 동일한 취약점이 발생한다. 파라미터 변조를 막는 것은 인증 방식이 아니라 **"storeId를 인증 컨텍스트에서만 가져온다"는 설계 규칙**이다.

```typescript
// 해결: 커스텀 데코레이터로 토큰에서만 추출
@StoreIds() storeIds: number[]  // req.user.store_ids
```

## 2. Gateway 우회 가능성

### 우려

> Pod에 직접 접근하면 게이트웨이 인증을 우회할 수 있다.

### 확인 결과

**외부에서 게이트웨이 우회는 불가능하다.**

- Service 타입: `ClusterIP` (외부 노출 없음)
- `kubectl get svc` 실제 조회로 확인: `preppers-order` selector를 가리키는 Service는 ClusterIP 하나뿐
- NodePort, LoadBalancer, HostNetwork, HostPort 모두 없음

| 시나리오 | 가능 여부 | 비고 |
|---|---|---|
| 외부에서 Pod 직접 접근 | 불가 | ClusterIP, 외부 노출 없음 |
| 외부에서 APISIX 우회 | 불가 | 유일한 진입점이 APISIX |
| 내부자 kubectl 접근 | 가능 | 인프라 보안 영역 (앱 레벨 방어 범위 밖) |
| 클러스터 내 다른 Pod 접근 | 가능 | NetworkPolicy로 방어 가능 |

## 3. KC → KS → OS 토큰 전파

### 흐름

```text
Kiosk Client(KC) → Kiosk Server(KS) → Order Server(OS)
```

KC의 토큰을 OS까지 전파하는 것은 안티패턴인가?

### 판단: 안티패턴 아님

| 조건 | 현재 상태 |
|---|---|
| KS 역할 | Gateway/전달 역할 (독자적 비즈니스 로직 미미) |
| OS가 필요한 정보 | KC 토큰의 `store_ids` (전파하면 자연스럽게 전달) |
| 외부에서 OS 직접 접근 | 불가 (ClusterIP) |

안티패턴이 되는 조건:

- KS가 독자적 비즈니스 로직으로 요청을 변형/거부하고, OS가 그 판단을 신뢰해야 하는 경우
- KS가 KC 없이 자체적으로 OS를 호출해야 하는 경우 (정산, 스케줄링 등)
- KC 토큰의 scope가 OS에 의도치 않은 권한을 부여하는 경우

### 토큰 전파 vs 토큰 분리

| 기준 | 토큰 전파 | 토큰 분리 (S2S 별도 인증) |
|---|---|---|
| 구현 복잡도 | 낮음 | 높음 (토큰 교환 서버 필요) |
| 장애 포인트 | KC 토큰 하나 | KC 토큰 + S2S 토큰 |
| End-User 추적 | 토큰에 자연스럽게 포함 | 별도 user context 전달 필요 |
| 파라미터 변조 | 토큰에서 storeId를 읽으므로 변조 불가 | storeId를 파라미터로 넘겨야 하므로 변조 가능성 발생 |

토큰 분리는 오히려 팀원이 우려한 파라미터 변조 문제를 만들어낸다. 토큰 전파가 더 단순하고 안전하다.

## 4. 결론

### Gateway 헤더 vs 토큰 전파

두 방식의 보안 효과는 동일하다. 차이는 "누가 decode하는가"일 뿐이다.

| | Gateway 헤더 (`X-Store-Id`) | 토큰 전파 (`req.user.store_ids`) |
|---|---|---|
| 신뢰 출처 | Gateway가 설정한 헤더 | Application이 decode한 토큰 |
| 파라미터 변조 방어 | storeId 파라미터를 안 받으면 해결 | storeId 파라미터를 안 받으면 해결 |
| Swagger/관리 편의성 | 헤더 관리 코드 필요 | 불필요 |
| 다중 매장 권한 표현 | 헤더 하나로 배열 표현 어려움 | `store_ids: number[]` 자연스러움 |
| Gateway 우회 시 | 헤더 조작 가능 | 토큰 서명이 보호 (APISIX 검증 완료) |

### 실질적으로 필요한 것

방식 선택과 무관하게 **Authorization Guard**가 필요하다:

```typescript
if (user.is_all_store_access) return true
if (!user.store_ids?.includes(requestedStoreId)) {
  throw new ForbiddenException('해당 매장에 대한 권한이 없습니다.')
}
```

이 검증 로직이 있으면 어떤 인증 방식을 쓰든 안전하고, 없으면 어떤 방식이든 취약하다.
