# 테스트 모범 사례 — 우리 코드에서 뽑은 실제 예시 (세션 추가 자료)

> `archive/2026-07-테스트세션/테스트-세션.md`의 부록을 보완하는 자료다. 외부 블로그 예제가 아니라 **우리 `test/` 디렉터리에서 그대로 가져온 코드**로 좋은 패턴과 안티패턴을 대조한다.
> 세션에서는 낭독하지 않는다. PR 리뷰 때 "이 문서의 N번 패턴 참고"처럼 기준으로 쓴다.

## 1부. 모범 사례 — 이미 우리 코드에 있는 좋은 패턴

### 1. 테스트 이름만으로 조건 + 기대 결과가 읽힌다

`test/customer-order/create-customer-order.e2e-spec.ts:428`

```ts
it('cardCompany가 있고 installment가 없으면 00을 저장한다', async () => {
  const createDto = createOrderDto({
    orderAmount: 10000,
    payment: { amount: 10000, cardCompany: '신한카드', approvedAt: new Date() },
  })
  const response = await createOrder(createDto).expect(201)
  const payment = await paymentRepo.findOne({ where: { orderId: response.body.id } })
  expect(payment?.installment).toBe('00')
})
```

- 이름 = 조건("cardCompany가 있고 installment가 없으면") + 기대 결과("00을 저장한다").
- 실패 메시지에 이 이름이 그대로 찍히므로, 어떤 비즈니스 규칙이 깨졌는지 코드를 열지 않고도 안다.
- Arrange(3줄) → Act(1줄) → Assert(2줄)가 한눈에 보이고, 한 테스트가 규칙 하나만 다룬다.

### 2. "오늘"에 의존하는 로직은 fake timer로 고정한다

`test/sales/monthly-sales-by-year.e2e-spec.ts:225`

```ts
it('올해 조회 시 지난 달까지만 포함한다 (이번 달 제외)', async () => {
  // 2026-02-15 12:00 KST → 올해 2026이면 1월 말까지만 조회
  vi.useFakeTimers()
  vi.setSystemTime(new Date('2026-02-15T03:00:00.000Z')) // 12:00 KST

  const response = await authRequest()
    .get('/sales/monthly/year')
    .query({ year: '2026', branchIds: String(TEST_STORE_ID) })
    .expect(200)

  vi.useRealTimers()

  const branch = response.body.data.find((b) => b.branch_id === TEST_STORE_ID)
  expect(branch.monthly_sales).toHaveLength(1)
  expect(branch.monthly_sales[0].year_month).toBe('2026-01')
})
```

- "이번 달", "오늘 이전"처럼 현재 시각에 의존하는 규칙은 시스템 시간을 고정하지 않으면 **달이 바뀌는 순간 조용히 무의미해지거나 깨진다** (안티패턴 2 참조).
- `finally` 또는 `beforeEach(vi.useRealTimers)`로 타이머 누수를 막는 것까지가 한 세트다. (`test/customer-order/mysql-kds-order.e2e-spec.ts:129` 참고)

### 4. 파일명 해시로 테스트 데이터를 격리한다

`test/customer-order/setup.ts:48`

```ts
export function getTestStoreId(filename: string): number {
  let hash = 0
  for (let i = 0; i < filename.length; i++) {
    hash = ((hash << 5) - hash) + filename.charCodeAt(i)
    hash |= 0
  }
  return 99000 + Math.abs(hash % 1000)
}
```

- 스펙마다 `getTestStoreId(__filename)`으로 자기만의 storeId 대역을 받아 다른 스펙과 데이터가 겹치지 않는다. `afterAll`에서 `paymentRepo.delete({ storeId: TEST_STORE_ID })` 한 줄로 정리가 끝나는 것도 이 덕분이다.
- 참조 데이터 ID도 `getTestIdBase(__filename)`로 파생시켜 쓴다 (`create-customer-order.e2e-spec.ts:19`).
- **주의**: 이 규칙을 무시하고 ID를 하드코딩하면 격리가 깨진다 (안티패턴 4).

## 2부. 안티패턴 — 우리 코드에서 실제로 발견된 것

### 1. 회귀가 났던 필드를 단언하지 않는다 ← 세션 데모 사례와 직결

`test/refund/refund.e2e-spec.ts:334` (922줄 전체에 `approvedAt`/`transactedAt` 단언 0건)

```ts
const refundPayment = refundPayments[0] // 최신 (환불)
expect(refundPayment.platform).toBe(PLATFORM_V2.PREPPERS)
expect(refundPayment.serviceType).toBe(SERVICE_TYPE.HALL)
expect(refundPayment.device).toBe(DEVICE.KIOSK)
// ← transactedAt / approvedAt 단언 없음
```

- 소스 규칙(`src/module/customer-order/refund.service.ts:141` 부근): `platform/serviceType/device`는 부모 결제에서 **복사**하고, `transactedAt/approvedAt`은 환불 트랜잭션 **고유 값**을 써야 한다.
- 테스트는 복사돼야 하는 3개 필드는 검증하면서, 실제 회귀가 났던 시간 필드는 검증하지 않는다. **회귀가 재발해도 922줄짜리 스위트가 전부 통과한다.**
- 교훈: 커버리지가 넓다 ≠ 회귀를 잡는다. 버그가 났던 바로 그 필드에 단언을 남겨야 한다 (세션 문서 F-1: "버그 수정 PR에는 재현 테스트").

### 2. 현재 날짜에 의존해 조용히 무의미해진 테스트

`test/sales/daily-sales.e2e-spec.ts:173`

```ts
it('이번 달 집계 시 1일과 오늘 이전 일자만 daily_sales에 포함되고 말일(미래)은 제외되어야 합니다', async () => {
  const yearMonth = '2026-02' // 작성 시점엔 "이번 달", 지금은 과거
  // ...

  expect(lastDay).toBeUndefined()

```

- 작성 시점(2026년 2월)에는 02-28이 미래라 제외됐지만, 3월 1일부터는 2월 전체가 과거다. 서비스가 "데이터 있는 날짜만" 반환하는 덕에 **지금도 통과는 하지만**, 02-28에 데이터가 없어서 통과할 뿐 "미래 날짜 제외" 로직(`sales.service.ts:218`)이 깨져도 잡지 못한다.
- 실패하며 깨지는 테스트보다 나쁘다 — **통과하면서 아무것도 지키지 않는다.** 모범 사례 2처럼 `vi.setSystemTime`으로 "오늘"을 고정해야 한다.

### 4. 격리 규칙을 무시한 매직 ID 하드코딩

`test/customer-order/customer-order.e2e-spec.ts:152`

```ts
await kdsDataSource.query(`
  INSERT IGNORE INTO food (id, ...) VALUES (101, ...), (102, ...)
`)
await kdsDataSource.query(`
  INSERT IGNORE INTO menu (id, food_id, ...) VALUES (8001, 101, ...), (8002, 102, ...)
`)
```

- 다른 스펙은 `getTestIdBase`로 900000+ 대역을 쓰는데 이 파일만 101/8001을 하드코딩했다. 공유 테이블(food/menu)이라 다른 스펙이 같은 ID를 쓰는 순간 간섭한다.
- `INSERT IGNORE`는 "이미 있으면 그 행을 조용히 재사용"하므로, 잘못된 기존 데이터 위에서 테스트가 도는 걸 숨긴다.
- 같은 계열: "존재하지 않는 지점" 값이 파일마다 `99999`/`999999`/`999999999`로 제각각인데, `99999`는 `getTestStoreId` 대역(99000~99999) 안이라 실제 스펙과 충돌할 수 있다.

## 3부. PR 리뷰 체크리스트 (이 문서 기준 요약)

테스트가 포함된 PR을 리뷰할 때 아래만 본다:

1. **이름**: 조건 + 기대 결과가 이름에 있는가? (모범 1)
2. **회귀 필드**: 버그 수정 PR이라면, 버그가 났던 바로 그 필드/값에 단언이 있는가? (안티 1)
3. **시간**: `new Date()`/"오늘"에 의존하면 `vi.setSystemTime`으로 고정했는가? KST/UTC가 주석으로 명시됐는가? (모범 2·3, 안티 2)
4. **격리**: `getTestStoreId`/`getTestIdBase` 대역을 쓰는가? 하드코딩 ID는 없는가? `afterAll` 정리가 있는가? (모범 4, 안티 4)
5. **단언**: 관심 필드만 `toMatchObject`로 보는가? 레코드를 정렬 순서가 아니라 의미로 조회하는가? (모범 5, 안티 3)
6. **관찰 가능성**: mock 호출 횟수/인자가 아니라 응답·DB 상태를 검증하는가? (모범 6, 안티 7)
7. **위생**: `console.log`, 죽은 주석, 복붙 셋업이 없는가? 공용 헬퍼(setup/test-kit)를 썼는가? (안티 5·6·8)
