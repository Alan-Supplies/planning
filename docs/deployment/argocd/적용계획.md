## 1. 배경 & 목적

현재 Preppers는 **AWS CodeBuild + CodePipeline** 기반의 **push형 CI/CD**로 배포한다
(`docs/deployment/파이프라인구축.md` 참고, 명명 규칙 `{domain}-{server/client}-{env}`, 예 `preppers-order-server-prod`).

이 방식의 한계:
- 배포 상태(원하는 상태 vs 실제 클러스터 상태)가 **코드로 관리되지 않음** → drift를 감지·복구할 방법이 없음
- 파이프라인이 클러스터에 직접 `kubectl apply` 하는 구조라 **누가/언제/무엇을 바꿨는지 추적**이 어렵고 롤백이 번거로움
- 환경별(dev/prod) 매니페스트가 표준화되어 있지 않음

**목표: GitOps(pull형) 전환.** Git repo를 단일 진실 공급원(SSoT)으로 두고, ArgoCD가 클러스터 상태를 Git과 지속적으로 대조·수렴시킨다.
- 선언적 배포 상태를 Git에서 리뷰/롤백
- drift 자동 감지 및 (정책에 따라) self-heal
- 환경별 구조 표준화

## 3. 대상 범위 (Scope)

### 3.1 서비스
백엔드 5개 서버 + 클라이언트 3종 (`docs/preppers/ARCHITECTURE.md`):
- 서버: `KDS_SERVER`, `ORDER_SERVER`, `POS_SERVER`, `KIOSK_SERVER`, `AUTH_SERVER`
- 클라이언트: `KDS`, `POS`, `KIOSK`

### 3.2 환경 / 클러스터 (`kubectl config get-contexts` 기준)
| 환경 | context / cluster | 용도 | 도입 순서 |
|---|---|---|---|
| dev | `supplies-eks-dev` | 개발/검증 (현재 POC 진행 중) | **1순위** |
| (구)운영 | `preppers-cluster` | 기존 클러스터 — 위치/역할 확인 필요 | 조사 후 결정 |
| prod | `eks_prod` | 운영 | **마지막** (dev 안정화 후) |

> ⚠️ `preppers-cluster`의 실제 역할(레거시/운영/스테이징 여부)은 롤아웃 전에 확인 필요 — **[결정 필요 #1]**

### 3.3 범위 밖 (이번 사이클)
- 기존 CodePipeline **완전 폐기**는 범위 밖. 전환 기간 동안 병행하다가 서비스별로 순차 컷오버.
- App-of-Apps / ApplicationSet 대규모 자동화는 dev 검증 이후 별도 검토.

## 4. 단계별 롤아웃 계획

각 단계는 하위 이슈와 매핑된다. **설계(4-A) → dev 파일럿(4-B) → 확산(4-C) → 운영(4-D)** 순.

### 4-A. 설계 확정 (하위 이슈)
1. **TECH-147 환경별 구조 잡기** — Helm vs Kustomize overlay 결정 및 repo 디렉토리 구조 작성.
   → *다른 설계의 전제라 먼저 확정 권장.*
2. **TECH-145 App Project 설계** — AppProject 단위로 소스 repo·대상 네임스페이스·클러스터 범위(RBAC 경계) 정의.
3. **TECH-146 배포 정책** — auto-sync / self-heal / drift 처리 정책. **vince와 상의** 필요.

### 4-B. dev 파일럿
- 4-A에서 정한 구조로 **파일럿 서비스 1개**(예: `AUTH_SERVER` — 의존성 적고 다른 서비스가 참조)를 `supplies-eks-dev`에 ArgoCD로 배포.
- 웹훅(TECH-127) 정식화: ngrok → **Ingress/LB 고정 도메인**으로 교체.
- 성공 기준(§6) 충족 시 확산 진행.

### 4-C. dev 전체 확산
- 나머지 서버/클라이언트를 dev에 순차 온보딩.
- 서비스별 CodePipeline → ArgoCD **컷오버 체크리스트** 작성·적용.

### 4-D. prod 적용
- dev 안정화 후 `eks_prod`에 동일 구조 적용.
- prod는 배포 정책을 보수적으로(예: auto-sync off 또는 manual sync 승인) — TECH-146에서 확정.

## 6. 성공 기준

- Git 커밋 → (웹훅) → 대상 클러스터에 **수동 개입 없이** 반영됨
- 클러스터에서 수동 변경(drift) 발생 시 정책대로 감지/복구됨
- 롤백 = Git revert로 수렴됨
- 환경(dev/prod)별 차이가 매니페스트 구조로 명확히 분리됨

## 8. 리스크

- **prod 오동작**: 설정 실수 시 self-heal이 잘못된 상태로 계속 되돌릴 수 있음 → prod는 manual sync부터 시작
- **웹훅 임시 노출(ngrok)**: URL 변동·보안 → Ingress/LB 정식화 전까지 파일럿 한정 사용
- **이중 배포 경로**: CodePipeline과 ArgoCD가 같은 리소스를 동시에 건드리면 충돌 → 서비스별 컷오버 시 한쪽만 소유
