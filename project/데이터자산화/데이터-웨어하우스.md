# 데이터 Warehouse 장기 플랜

> 상태: 방향 수립 · 프로덕션 구축 착수 대기  
> 현재 우선순위: TECH-396 ArgoCD 운영 배포 경로 단일화  
> 상위 정본: [데이터 자산화 기획안](../../project/데이터자산화/supplies-data-plan.md)

## 1. 목적

운영 DB와 행동 이벤트를 별도 분석 저장소에 보존하고, 고객·방문·주문·운동을 일관된 기준으로 연결해 신뢰할 수 있는 지표와 향후 세그먼트 활성화의 기반을 만든다.

이 계획의 목표는 운영 DB 전체를 복사하는 것이 아니다. 우선순위가 높은 질문 하나를 원천 적재부터 지표 검증까지 끝까지 통과시키고, 같은 방식으로 도메인을 확장할 수 있는 운영 가능한 Warehouse를 만드는 것이다.

## 2. 착수 원칙

- ArgoCD 완료는 관리형 Warehouse 서비스의 기술적 선행조건은 아니지만, 담당자 용량을 보호하기 위한 프로덕션 착수 게이트다.
- TECH-396이 끝나기 전에는 도구 조사, 데이터 계약, 비용 추정처럼 되돌리기 쉬운 설계만 진행한다.
- 신규 클라우드 리소스, 상시 적재 잡, 프로덕션 권한과 비밀정보 구성은 ArgoCD 작업 종료 후 착수한다.
- 운동 데이터는 운동기록 원천 계약이 안정화되기 전까지 Raw 적재만 허용하고 `fact_workout`을 지표 정본으로 공개하지 않는다.
- 첫 MVP가 운영되기 전에는 전 테이블 적재나 전사 대시보드 구축으로 범위를 넓히지 않는다.

## 3. 목표 구조

```text
운영 MySQL ── CDC 또는 배치 ──┐
                              ├─▶ Raw ─▶ Staging ─▶ Core dim/fact ─▶ Mart/Metric
Firebase 이벤트 ─ BigQuery ──┘
```

| 계층 | 책임 | 변경 원칙 |
| --- | --- | --- |
| Raw | 원천 보존, 재처리 기준점 | 원천 의미를 임의로 고치지 않음 |
| Staging | 타입·시간대·enum·중복 정리 | 정제 규칙과 실패 행을 추적 |
| Core | `dim_*`, `fact_*` 공통 모델 | 그레인과 키를 코드 리뷰로 변경 |
| Mart/Metric | 도메인 지표와 소비용 모델 | 용어사전·검증 쿼리와 1:1 연결 |

## 4. 초기 범위

### 우선 도메인

1. 고객·지점
   - `dim_user`
   - `dim_gym`
   - `dim_date`

   - 운동기록 개선의 데이터 계약 안정화 후 공개
5. 행동
   - `fact_engagement`
   - Firebase BigQuery Export의 이벤트

### 후속 도메인

- 목표 진행률
- 푸시 발송·도달·열람
- CDP 세그먼트와 캠페인 효과
- 정지 통계·유령 테이블 정리

### 초기 범위 밖

- 모든 운영 테이블의 무차별 복제
- 실시간 스트리밍 보장
- CDP 제품 선정과 캠페인 자동 실행
- ML 추천 플랫폼
- 운영 결제 테이블의 물리적 재설계

## 5. 핵심 데이터 모델

| 모델 | 그레인 | 주요 질문 | 공개 조건 |
| --- | --- | --- | --- |
| `dim_user` | 고객 1명 또는 고객 상태 버전 1건 | 누구인가 | 현재 상태와 이력 보존 방식 확정 |
| `fact_visit` | 출입 1건 | 언제 어느 지점에 왔나 | KST와 중복·NULL 정책 확정 |
| `fact_order` | 주문 또는 주문 품목 1건 | 무엇을 얼마에 샀나 | 주문 그레인과 환불 표현 확정 |
| `fact_workout` | 운동 세션 1건 | 무엇을 얼마나 했나 | 운동기록 개선 Phase 4 통과 |
| `fact_engagement` | 이벤트 1건 | 앱에서 무엇을 했나 | 이벤트 ID·사용자 ID·중복 규칙 검증 |

모델 이름은 구현 도구에 따라 뷰, 테이블 또는 증분 모델이 될 수 있다. 중요한 것은 물리 형식보다 그레인과 계산 규칙이다.

## 6. 데이터 처리 원칙

### 고객 식별

- 회원 거래는 `user_id`를 통해 `dim_user`에 연결한다.
- 키오스크 G오더와 비회원 일일권은 결측으로 단정하지 않고 `identity_type`으로 구분한다.
- 익명 거래를 임의의 회원에게 귀속하지 않는다.
- 공통 `UNKNOWN` 행 사용, `user_key` NULL, 별도 `guest_key` 중 어떤 방식을 쓸지는 사용 사례를 확인한 뒤 결정한다.
- 전화번호·이메일을 이용한 사후 연결은 법적 근거와 오매칭 기준 없이 수행하지 않는다.

### 시간

- 원천 시각과 변환된 KST 일자를 함께 추적한다.
- 일·주 경계는 용어사전의 단일 정의를 사용한다.
- 적재 시각과 비즈니스 발생 시각을 구분한다.

### JSON

- Raw에서는 네이티브 JSON과 JSON 문자열을 원본 그대로 보존한다.
- 핵심 지표에 반복 사용하는 값은 Staging 또는 Core에서 타입이 지정된 컬럼으로 추출한다.
- JSON이라는 이유만으로 분석 불가로 판정하지 않는다.
- 키 변경, 타입 혼재, 단위 혼재, 유효하지 않은 JSON을 데이터 품질 규칙으로 감지한다.

### 변경과 삭제

- Raw는 재처리가 가능한 기간 동안 원천 변경 이력을 보존한다.
- soft delete와 hard delete를 구분한다.
- 지연 도착 데이터와 재실행을 고려해 적재 잡을 멱등하게 만든다.
- 원천 스키마 변경은 조용히 누락시키지 않고 실패 또는 경고로 드러나게 한다.

## 7. 단계별 실행

### Gate A. 현재 집중 작업 종료

진입 조건:

- TECH-396의 운영 배포 경로 단일화 완료
- 전환 직후 운영 관찰과 후속 작업량 확인
- Warehouse에 투입할 수 있는 주당 용량 합의

Gate A 이전 허용 작업:

- 비즈니스 질문 목록
- 도구 비교 기준
- 데이터 분류와 PII 목록
- 원천 테이블·이벤트 인벤토리
- 읽기 전용 검증 쿼리

### Phase 0. 결정과 운영 책임

결정할 항목:

- 첫 번째 비즈니스 질문과 지표
- 데이터 최신성: 일배치, 시간배치, 준실시간
- 저장소와 변환 도구
- 리전, 보존기간, 암호화, 개인정보 국외 이전
- 비용 상한과 경보
- 장애 대응·재처리·온콜 소유자
- 개발·스테이징·운영 환경

종료 조건:

- Architecture Decision Record
- 월 비용 추정과 중단 기준
- 데이터 소유자와 승인자
- 첫 세로 단면의 범위와 DoD

### Phase 1. 첫 세로 단면

권고 대상: `access_history → fact_visit → 주간 방문`

선정 이유:

- 운동 원천 안정화를 기다리지 않고 시작할 수 있음
- 고객·지점·날짜 차원의 최소 구조를 검증할 수 있음
- 북극성 지표 후보를 원천과 대사할 수 있음

구현 범위:

- 원천 스냅샷 또는 증분 적재
- Raw와 Staging 모델
- `dim_user`, `dim_gym`, `dim_date` 최소 버전
- `fact_visit`
- KST 주간 방문 지표 1개
- 원천 건수와 Warehouse 건수 대사

종료 조건:

- 같은 입력을 재처리해도 중복이 생기지 않음
- 신규·수정·삭제 처리 규칙이 테스트됨
- 원천 대비 건수와 지표가 합의된 허용 오차 안에서 일치
- 적재 실패와 스키마 변경을 알림으로 확인 가능
- 운영자가 재실행할 수 있는 런북이 있음

### Phase 2. 주문과 익명 고객

작업:

- `payment_history`, `food_order`, 일일권 주문 Raw 적재
- 결제 유형을 주문 도메인으로 매핑
- 구매와 환불의 표현 규칙 확정
- 회원, 키오스크 G오더, 비회원 일일권 분리
- `fact_order`의 주문/품목 그레인 결정
- 금액·건수·조인 실패 대사

종료 조건:

- 운영 결제 합계와 도메인별 Warehouse 합계가 대사됨
- 의도된 익명과 식별 실패가 다른 상태로 표현됨
- 매핑되지 않은 신규 결제 유형이 자동 탐지됨
- 원본 주문과 연결되지 않는 결제 ID가 품질 지표로 보임

### Phase 3. 운동

선행 조건:

- 운동기록 개선의 핵심 데이터 계약 확정
- `started_at`, `source`, 무게·시간 단위, 완료·자동 마감 정의 고정
- 신규 데이터 오염 차단 확인

작업:

- 운동 세션 3층 Raw 적재
- 운동·세트 값을 세션 그레인으로 집계
- `fact_workout`과 필요한 하위 세트 모델 작성
- GYM·OUTSIDE 분리
- 기록 보유 세션, 운동 시간, 총 무게, 완료율 구현

종료 조건:

- 동일 픽스처가 앱·운영 DB·Warehouse에서 같은 값을 냄
- 과거 의미 전환 경계가 쿼리에 반영됨
- 자동 마감과 사용자 완료가 구분됨
- 지표가 용어사전의 검증 쿼리와 일치함

### Phase 4. 행동 이벤트와 지표 레이어

작업:

- Firebase BigQuery Export의 이벤트 Raw 보존
- 이벤트 중복·지연 도착·사용자 ID 규칙 확정
- `fact_engagement`
- 지표를 코드로 관리하고 PR 리뷰 적용
- 도메인 마트와 BI 소비 모델 구성

종료 조건:

- 정의된 이벤트의 수신 누락과 enum 드리프트 감지
- 운영 데이터와 이벤트를 고객 또는 익명 ID 기준으로 연결
- 같은 지표가 대시보드마다 다르게 계산되지 않음
- 지표 변경 이력과 영향 범위를 추적 가능

### Phase 5. 운영화와 활성화

작업:

- 비용·지연·실패율·데이터 신선도 모니터링
- 백필과 재처리 런북
- 접근 권한과 감사 로그
- Warehouse 세그먼트를 푸시 발송 원천으로 연결

CDP 연결은 Warehouse 운영 안정화 이후 별도 승인으로 진행한다.

## 8. 첫 MVP의 완료 정의

Warehouse MVP는 별도 저장소가 생성된 시점이 아니라 다음을 모두 만족한 시점이다.

- 원천 하나가 자동으로 증분 적재됨
- Raw에서 지표까지 변환 경로가 코드로 관리됨
- 재실행이 멱등함
- 원천과 건수·지표 대사가 자동화됨
- 스키마 변경과 적재 실패를 탐지함
- 비용과 데이터 신선도를 확인할 수 있음
- 운영 런북과 소유자가 있음
- 실제 의사결정에 사용하는 지표 하나가 공개됨

## 9. 도구 선택 기준

특정 제품을 먼저 정하지 않고 다음 기준으로 비교한다.

| 기준 | 확인할 내용 |
| --- | --- |
| 기존 환경 정합성 | AWS RDS와 Firebase BigQuery 양쪽 연결 비용 |
| 운영 난이도 | 한 사람이 장애 대응·재처리할 수 있는가 |
| 비용 | 저장, 조회, CDC, 네트워크 전송, BI 비용 |
| 데이터 위치 | 리전과 개인정보 국외 이전 |
| 변환 | SQL 기반 증분 모델과 테스트 지원 |
| 확장 | 이벤트와 DB를 함께 처리할 수 있는가 |
| 종속성 | 제품을 바꿀 때 SQL·모델을 얼마나 재사용할 수 있는가 |

도구 선택보다 데이터 계약과 검증 쿼리를 먼저 만든다.

## 10. ArgoCD와의 경계

- Warehouse가 관리형 서비스라면 모든 리소스를 Kubernetes에 올릴 필요는 없다.
- Kubernetes에서 실행하는 적재·변환 잡이 생길 경우 배포 소유권과 비밀정보 주입 방식을 ArgoCD 정책에 맞춘다.
- Terraform, GitOps, Warehouse SQL 중 무엇이 어떤 리소스의 정본인지 명확히 한다.
- ArgoCD 미완료 상태에서 임시 수동 배포 경로를 추가해 세 번째 배포 체계를 만들지 않는다.

## 11. 용량과 병렬 작업 정책

- 운동기록 개선 기간에는 Warehouse를 첫 세로 단면 또는 설계 작업으로 제한한다.
- 운동기록 DDL 주간에는 Warehouse 프로덕션 변경을 잡지 않는다.
- 주당 가용 용량의 20~30%를 넘겨 Warehouse에 배정하려면 운동기록 일정 조정 또는 추가 담당자가 필요하다.
- Backend·DBA·인프라·Data를 한 사람이 모두 수행하는 상태에서 Phase 2 이상을 약속하지 않는다.
- 각 Phase 종료 시 계속 진행, 일시 정지, 인력 보강 중 하나를 명시적으로 결정한다.

## 12. 주요 미결

- BigQuery, Redshift 또는 다른 저장소 중 무엇을 선택할 것인가
- DB 적재를 CDC와 배치 중 어디서 시작할 것인가
- `dim_user`가 현재 상태만 담을지 변경 이력을 담을지
- 키오스크·일일권 익명 고객을 어떤 키로 표현할지
- `fact_order`의 그레인을 주문과 주문 품목 중 어디에 둘지
- 개인정보와 신체정보의 보존기간 및 리전
- 허용 가능한 데이터 지연과 월 비용
- Warehouse 운영과 지표 승인 책임자를 분리할 수 있는가
