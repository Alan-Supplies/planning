# 운동기록 DW 인프라 스택 구현 — 이슈 8건

Linear 발행용 초안. 이슈 ID는 Linear가 자동 발행하므로 여기서 부여하지 않는다. 아래 번호는 이 문서 안에서 선행관계를 가리키기 위한 순번일 뿐이다. 담당자는 아직 배정 전이며, 배정되는 대로 각 이슈의 담당자 항목을 채운다.

대상 데이터는 `user_exercise_session_history`·`user_exercise_set_history` 두 테이블이고, 환경은 `gymboxx-dev`의 합성/테스트 데이터다. 스택은 MySQL → AWS DMS(CDC) → S3(Glue Catalog) → Athena → Airflow+dbt core → BigQuery(Warehouse) → Airflow+dbt core → Mart 순이다. 두 테이블의 dev 반영 자체는 별도 트랙에서 진행 중이라 이 목록에 포함하지 않는다.

진행 순서는 **스택 설치를 먼저 끝내고 그다음에 데이터 작업**으로 잡는다. 1번(도입 방식 결정)과 2번(설치·구축)이 스택 설치에 해당하는 선행 2건이고, Warehouse·Mart 작업은 그 위에서 진행한다. 3번(DMS)과 4번(Glue/Athena)은 Airflow와 무관한 AWS 쪽 배관이라 1·2번과 병렬로 진행할 수 있다.

`스택결정.md`에 "transformer (airflow + dbt core)"가 두 번 적혀 있는 것은 데이터 흐름상 **변환 단계가 두 번**이라는 뜻이지 Airflow나 dbt를 두 벌 두라는 뜻이 아니다. **Airflow 인스턴스 하나, dbt 프로젝트 하나로 Warehouse와 Mart를 모두 만든다.** dbt 프로젝트 안에서 `models/staging/`과 `models/marts/`로 디렉토리만 나누면 `ref()`가 모델 간 의존 그래프를 만들어주므로 빌드 순서는 dbt가 스스로 지킨다.

## 1. Airflow + dbt core 도입 방식 결정 (스파이크)

담당자: 미정. 선행: 없음.

스택을 설치하기 전에 무엇을 어떻게 설치할지 먼저 정한다. Airflow 호스팅 후보는 기존 EKS 클러스터에 self-hosted로 올리는 방식, 로컬 docker-compose, AWS 관리형 MWAA, GCP 관리형 Cloud Composer 네 가지다. 각각의 초기 구축 비용, 월 운영 비용, PoC 종료 후 운영 전환 가능성, 그리고 AWS(S3/Athena)와 GCP(BigQuery) 양쪽에 접근해야 하는 크로스클라우드 인증 처리 난이도를 비교해 하나를 고른다.

같이 정해야 할 것이 몇 가지 더 있다. dbt core를 Airflow와 같은 환경에 둘지 별도 컨테이너로 분리할지, dbt 프로젝트 소스를 어느 저장소에 둘지, Airflow가 dbt를 어떤 방식으로 호출할지(BashOperator로 `dbt run` 단순 호출 / Cosmos 같은 통합 패키지로 모델 단위 태스크 분해)를 결정한다. 모델 단위로 쪼개면 실패 지점 파악과 재시도가 쉬워지지만 셋업이 무거워지므로, PoC 규모에서는 단순 호출로 시작하는 편이 낫다.

완료 기준은 위 항목들의 선택 결과와 근거가 문서로 남는 것이다. 이 이슈는 2번의 선행이고 2번은 다시 5·6·7·8번의 선행이므로, 전체 일정에서 가장 먼저 착수해야 한다.

## 2. Airflow + dbt core 설치·구축

담당자: 미정. 선행: 1번.

1번에서 정한 방식대로 스택을 실제로 설치한다. Airflow를 배포하고 웹 UI와 스케줄러가 정상 동작하는지 확인한 뒤, AWS와 GCP 커넥션을 등록한다. 이 커넥션 등록이 이 이슈에서 가장 손이 많이 가는 부분이며, GCP 서비스 계정 키와 AWS IAM 역할을 어떻게 주입할지가 핵심이다. 이후 dbt 프로젝트를 스캐폴딩하고 BigQuery를 타깃으로 하는 프로파일을 설정한다.

이 단계에서는 실제 데이터를 다루지 않는다. 완료 기준은 세 가지다. 첫째로 Airflow에서 간단한 DAG 하나가 스케줄대로 실행되어 성공한다. 둘째로 `dbt debug`가 BigQuery 연결 확인까지 통과한다. 셋째로 Airflow 태스크에서 dbt 명령이 호출되어 성공한다. 이 세 가지가 되면 스택 설치는 끝난 것이고, 이후 이슈들은 배관이 아니라 데이터만 다루면 된다.

## 3. DMS 지속 CDC 구성: gymboxx-dev MySQL → S3

담당자: 미정. 선행: 없음(1·2번과 병렬 진행 가능).

AWS DMS로 `gymboxx-dev` MySQL의 대상 두 테이블을 S3로 복제한다. Full Load 1회가 아니라 **지속 CDC 복제**로 구성한다는 점이 이 이슈의 핵심이다. 소스 엔드포인트의 binlog 설정 확인, 타깃 S3 엔드포인트와 출력 포맷(Parquet 권장) 결정, 복제 인스턴스 규격 산정이 포함된다.

완료 기준은 최초 Full Load가 S3에 떨어지는 것에 더해, 소스 MySQL에 INSERT/UPDATE를 발생시켰을 때 그 변경분이 S3에 증분으로 반영되는 것까지 확인하는 것이다. 대상 테이블의 dev 반영이 선행이지만 그건 별도 트랙에서 진행되므로, 착수 시점에 테이블 존재 여부만 확인하면 된다.

## 4. Glue Catalog 등록 + Athena 조회 확인

담당자: 미정. 선행: 3번.

DMS가 S3에 적재한 산출물을 Glue Catalog에 테이블로 등록하고 Athena에서 SQL로 조회되는지 확인한다. 크롤러로 스키마를 자동 추론할지 DDL을 직접 작성할지 정하고, 파티션 구성(예: 적재일자 기준)을 결정한다. CDC 산출물이라 INSERT/UPDATE/DELETE 연산 구분 컬럼이 붙어 나오므로, 이를 Athena 쿼리에서 어떻게 다룰지도 여기서 함께 정리한다.

완료 기준은 Athena에서 두 테이블을 조회해 소스 MySQL과 행 수·샘플 값이 일치하는 것을 확인하는 것이다.

## 5. S3 → BigQuery raw 테이블 적재 (Airflow만, dbt 없이)

담당자: 미정. 선행: 2번, 4번.

Lake(S3)의 데이터를 BigQuery로 옮겨 raw 테이블까지 만든다. **이 단계에는 dbt core가 관여하지 않는다.** dbt core는 웨어하우스 안에서 SQL을 돌려 모델을 만드는 도구일 뿐 시스템 간 데이터 이동 기능이 없으므로, 적재는 Airflow 오퍼레이터가 담당한다(`S3ToGCSOperator` → `GCSToBigQueryOperator`, 또는 `BigQueryInsertJobOperator`). BigQuery Omni나 Storage Transfer Service는 채택하지 않는다.

2번에서 커넥션이 이미 등록되어 있으므로 인증 문제는 여기서 다시 풀지 않는다. 이 이슈는 적재 대상 경로와 스키마 매핑, 증분 적재 방식(전체 덮어쓰기 / append / merge)을 정하는 데 집중한다.

완료 기준은 BigQuery raw 테이블에서 두 테이블이 조회되고, 행 수와 샘플값이 Athena 쪽과 일치하는 것이다. 이 시점에 MySQL부터 BigQuery까지 배관이 관통했다는 사실이 dbt 모델링과 무관하게 증명된다.

## 6. dbt Warehouse 모델: staging / fact

담당자: 미정. 선행: 5번.

BigQuery raw 테이블 위에 dbt core로 staging·fact 모델을 만든다. 2번에서 dbt 프로젝트와 프로파일이 이미 구성되어 있고 5번에서 배관이 검증되어 있으므로, 이 이슈는 순수하게 데이터 모델링만 다룬다.

staging 레이어에서 컬럼명 정규화와 타입 캐스팅, CDC 연산 컬럼을 이용한 최신 상태 추출을 처리하고, fact 레이어에서 세션과 세트를 분석 가능한 형태로 정리한다. 완료 기준은 `dbt run`으로 staging·fact 모델이 생성되고, 결과가 raw 테이블과 대조해 일치하는 것이다.

## 7. dbt Mart 모델: 일별 세션당 평균 세트 완료율

담당자: 미정. 선행: 6번.

PoC의 성공 기준이 되는 지표를 Mart 레이어에 구현한다. 지표는 "일별 세션당 평균 세트 완료율"이며, 6번에서 만든 fact 모델을 `ref()`로 참조해 계산한다. 데이터가 BigQuery 안에서만 움직이므로 여기엔 크로스클라우드 인증 문제가 없다.

먼저 "세트 완료"의 정의를 확정해야 한다. 어떤 컬럼·상태값을 완료로 볼 것인지, 세션에 세트가 하나도 없는 경우를 분모에 포함할 것인지 같은 판단이 필요하며, 이 정의가 지표값 자체를 좌우하므로 착수 전에 합의하고 문서에 남긴다.

완료 기준은 Mart 테이블에서 일자별 지표값이 조회되고, 같은 값을 소스 MySQL에서 직접 계산한 결과와 대조해 일치하는 것이다.

## 8. Airflow 오케스트레이션 + E2E 검증

담당자: 미정. 선행: 7번.

지금까지 개별적으로 만든 단계들을 Airflow DAG로 묶어 자동 실행되게 한다. 실행 주기, 단계 간 의존관계, 실패 시 재시도와 알림 정책을 정한다. 적재(5번)와 dbt 변환(6·7번)이 하나의 DAG 안에서 순서대로 이어지도록 구성하며, dbt는 `ref()` 의존 그래프를 스스로 해석하므로 Airflow 쪽에서 모델 단위 순서를 다시 정의할 필요는 없다.

완료 기준은 E2E 실측이다. `gymboxx-dev` MySQL에 합성 데이터를 삽입한 뒤 그것이 Mart 지표에 반영될 때까지 걸리는 시간을 측정해 기록한다. 이 지연시간 수치가 이번 PoC의 최종 산출물이며, 이후 운영 전환 여부를 판단하는 근거가 된다.
