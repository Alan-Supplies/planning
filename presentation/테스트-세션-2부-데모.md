# 테스트 세션 2부 — 라이브 데모 대본 (20분)

> `docs/테스트-세션.md` 2부의 확정본. 진행자 전용 문서다.
> 소재: **환불 시각 필드 회귀** (`payments.approved_at`·`transacted_at`이 원결제 값을 복사) — 실제로 겪은 회귀다.
>
> **코드 현황 (2026-07-14 확인)**: 현재 `refund.service.ts`의 두 환불 경로(`refund`, `refundSuccessTx`)는 모두 올바르다 —
> `transactedAt = new Date()`(환불 시점), `approvedAt = 요청값`. 그래서 이 데모는 버그 커밋을 체크아웃하는 방식이 아니라,
> **회귀를 그 자리에서 다시 심는** 방식으로 진행한다. 그리고 핵심 반전: 922줄짜리 refund 테스트 스위트에
> 이 두 필드에 대한 단언이 **0건**이라, 회귀를 심어도 스위트가 전부 통과한다. 이 "거짓 초록"이 데모의 심장이다.

## 데모가 증명해야 하는 것 (딱 두 가지)

1. **테스트가 없으면(부족하면) 회귀는 조용히 통과한다** — 화면상 환불은 성공, 스위트도 초록, 그러나 정산 데이터는 이미 틀어짐.
2. **재현 테스트 1개면 같은 회귀가 다시는 조용히 지나갈 수 없다** — 빨강이 뜨는 순간을 직접 보여준다.

## ① 상황 설명 (0–2분)

말로만 한다. 코드를 아직 열지 않는다.

> "실제로 있었던 일입니다. 포스에서 환불을 하면 환불 결제 row가 하나 생기는데, 어느 시점부터 그 row의
> `approved_at`이랑 `transacted_at`에 **환불한 시각이 아니라 원래 결제했던 시각**이 들어가기 시작했어요.
> 환불 자체는 잘 됐습니다. 화면에서도 성공이라고 떴고요. 어제 결제한 걸 오늘 환불하면, 오늘 환불이
> 어제 일어난 걸로 기록된 것뿐이죠. 매출 집계는 이 시각들 기준으로 도니까 일별 정산 숫자가 조용히
> 틀어졌습니다. 언제부터였는지는… 한참 뒤에 알았습니다."

포인트: **"환불은 성공했다"**를 강조한다. 기능이 죽은 게 아니라 데이터가 조용히 틀어진 사례라는 것.

> 꽤 많이 검증하고 있어요."

전부 초록으로 끝나는 걸 보여준다. **"우리 환불 로직은 테스트로 보호받고 있다"는 인상을 일부러 만든다.** 다음 단계에서 뒤집기 위해서다.

## ③ 회귀 재주입 (5–8분)

`src/module/customer-order/refund.service.ts`의 `refundSuccessTx` (347행 부근)를 연다. 현재 코드:

```ts
const transactedAt = new Date()
// ...
this.paymentsService.create({
  // ...
  transactedAt,
  // ...
  approvedAt: refundData.approvedAt,
  // ...
  platform: originalPayment.platform,     // 원결제에서 복사
  serviceType: originalPayment.serviceType,
  device: refundData.device,
}),
```

여기서 실제 회귀와 같은 모양의 변경을 **라이브로** 한다 (딱 2줄):

```ts
  transactedAt: originalPayment.transactedAt,   // ← 변경
  // ...
  approvedAt: originalPayment.approvedAt,       // ← 변경
```

변경하면서 말한다:

> "이 변경, 이상해 보이나요? 바로 아래에 `platform`, `serviceType`을 원결제에서 복사하는 줄들이 있죠.
> '환불 결제는 원결제의 속성을 따라간다'는 맥락에서 보면 시각도 복사하는 게 오히려 **일관성 있어 보입니다.**
> 리뷰에서도 충분히 통과할 수 있는 diff예요."

그리고 다시 실행:

```bash
npx vitest run --project e2e test/refund/refund.e2e-spec.ts
```

**전부 초록.** 여기가 데모의 첫 번째 충격 포인트다. 결과 화면을 띄워둔 채 잠시 말을 멈춘다.

> "방금 저는 실제로 정산 사고를 냈던 것과 같은 버그를 다시 심었습니다. 922줄짜리 테스트가 방금 다 통과했고요."

## ④ ★개입 질문 — 반드시 멈춘다 (8–10분)

세션 전체에서 가장 중요한 2분. **진행자가 답을 말하지 않는다.** 팀에게 묻고 기다린다:

> **"이거, 지금 테스트 없이 어떻게 확인하실 거예요?"**

예상 답변과 받아치기:

- "포스에서 환불 눌러보고 DB 봐야죠" → "매 배포마다요? 누가요? 시각 필드까지 눈으로 보실 건가요?"
- "리뷰에서 잡아야죠" → "방금 그 diff, 복사 필드들 옆에 있어서 자연스러워 보였잖아요."
- "QA가…" → "QA 화면에서 환불은 **성공**으로 보입니다. 틀어진 건 시각 필드뿐이에요."

"일일이 눌러봐야죠"가 나오는 순간이 목표 지점이다. **그들 입으로** 수동 확인의 비용이 말해졌다.

## ⑤ 재현 테스트 추가 → 빨강 (10–15분)

`test/refund/refund.e2e-spec.ts`의 `refund-success` describe 블록에 아래 테스트를 추가한다.
(라이브 타이핑은 위험하니 **미리 준비한 스니펫을 붙여넣고, 한 줄씩 소리 내어 해설**한다.)

```ts
it('환불 payment의 transactedAt·approvedAt은 원결제 시각이 아니라 환불 시점 값이어야 한다', async () => {
  // 준비: 어제 결제된 주문 (원결제 시각을 하루 전으로 밀어둔다)
  const order = await createTestOrder({ orderAmount: 15000, payment: { amount: 15000 } })
  const paymentRepo = kdsDataSource.getRepository(PaymentEntity)
  const originalPayment = await paymentRepo.findOneOrFail({
    where: { orderId: order.id, transactionType: TRANSACTION_TYPE.PAYMENT },
  })
  const paidAtUtc = new Date('2026-07-13T03:00:00Z') // 어제 12:00 KST
  await paymentRepo.update(originalPayment.id, {
    approvedAt: paidAtUtc,
    transactedAt: paidAtUtc,
  })

  // 실행: 오늘 14:00 KST에 포스 서버가 환불 성공을 알려온다
  const refundApprovedAtUtc = new Date('2026-07-14T05:00:00Z')
  await requestCustomerOrders.refundSuccess(order.id, {
    amount: 15000,
    device: DEVICE.POS,
    approvedAt: refundApprovedAtUtc.toISOString(),
  }).expect(201)

  // 검증: 환불 row의 시각은 "환불" 시점이어야지, "원결제" 시점이면 안 된다
  const refundPayment = await paymentRepo.findOneOrFail({
    where: { orderId: order.id, transactionType: TRANSACTION_TYPE.REFUND },
  })
  expect(refundPayment.approvedAt?.getTime()).toBe(refundApprovedAtUtc.getTime())
  expect(refundPayment.transactedAt?.getTime()).not.toBe(paidAtUtc.getTime())
})
```

해설 포인트 (붙여넣은 뒤 한 줄씩):

- 이름부터: 코드를 몰라도 규칙이 읽힌다 — "환불 시각은 환불 시점 값이어야 한다".
- 준비/실행/검증 3단 구조를 손으로 짚는다 (사전 자료에서 읽고 온 그 구조).
- "어제 결제, 오늘 환불" — 회귀가 실제로 드러났던 상황 그대로를 데이터로 만든 것.
- 시각은 초 단위 고정값 사용 (MySQL DATETIME은 ms를 버리므로 `Date.now()` 비교는 플레이키해진다).

실행:

```bash
npx vitest run --project e2e test/refund/refund.e2e-spec.ts
```

**빨강.** 실패 메시지를 반드시 같이 읽는다:

> "expected approvedAt이 14:00인데 실제로는 어제 12:00이 들어있다 — 테스트 이름이랑 실패 메시지만으로
> 뭐가 깨졌는지 바로 보이죠. 로그 뒤질 필요도, 어느 커밋인지 찾을 필요도 없습니다. **방금 변경이 범인입니다.**"

## ⑥ 구현 원복 → 초록 (15–18분)

③에서 바꾼 2줄을 되돌린다 (`git checkout -- src/module/customer-order/refund.service.ts` 또는 수동 복구). 재실행 → 전부 초록.

> "이제 이 테스트는 스위트에 남습니다. 누가 언제 이 필드를 다시 건드려도 — 저처럼 그럴듯한 리팩터링으로라도 —
> 배포 전에 30초 만에 빨간불이 뜹니다. 같은 사고는 두 번 안 납니다."

**테스트 추가는 실제 PR로 올린다** (데모 후 그대로 커밋). "데모용 쇼"가 아니라 오늘 스위트가 실제로 강해졌다는 것을 보여주는 마무리.

## 이 데모에서 하지 말 것

- ③에서 회귀를 심을 때 "이건 나쁜 코드죠?"라고 묻지 않는다 — 그럴듯해 보인다는 게 포인트다.
- ④에서 침묵이 어색해도 먼저 답하지 않는다. 5초 기다리면 누군가 말한다.
- 테스트 문법(vitest, supertest) 설명에 시간을 쓰지 않는다. "포스트맨 대신 코드가 요청을 보낸다" 한 문장이면 충분하다. 문법은 사전 자료와 모범사례 문서로 넘긴다.
- 커버리지, 단위/통합/E2E 구분 이야기를 꺼내지 않는다. 질문이 나오면 "부록에 있다, 세션 후에 보자"로 미룬다.

## 예상 질문 대응

- **"이건 원래 코드가 고쳐져 있으니까 가능한 데모 아닌가요?"** → "맞아요. 그런데 고칠 때 재현 테스트를 안 남겼기 때문에 방금처럼 누구든 다시 깨뜨릴 수 있었죠. 오늘 그 테스트를 남겼으니 이제 못 깨뜨립니다. 이게 버그 수정 PR에 재현 테스트를 같이 넣자는 이유예요."
- **"모든 필드를 이렇게 다 단언해야 하나요?"** → "아니요. 사고가 났던 필드, 틀어지면 아픈 필드부터요. 이 테스트도 단언은 딱 2줄입니다."
- **"E2E라 느린데 이걸 늘려도 되나요?"** → "좋은 질문인데 오늘 범위 밖이라 부록 D(범위 선택)로 미룰게요. 원칙만: 아픈 규칙부터, 전체 실행 시간은 우리가 계속 지켜봅니다."
