# 테스트 코드 작성 및 활용

## 프레젠테이션 목적

1. 테스트 코드는 개발 속도를 늦추는 부가 작업이 아니라, 변경 비용을 낮추는 안전장치라는 공감대를 만든다.
2. 현재 프로젝트(`preppers-order-server`)의 테스트 작성·실행 방법을 함께 따라 해 본다.
3. 발표 이후 바로 적용할 수 있는 최소 테스트 작성 기준을 합의한다.

## 대상과 핵심 메시지

- 대상: 테스트 작성 경험이 적거나, 일정 압박 때문에 테스트를 생략해 온 개발자
- 핵심 메시지: **테스트의 목적은 버그가 전혀 없는 코드를 만드는 것이 아니라, 변경의 결과를 빠르고 반복 가능하게 확인하는 것이다.**
- 발표 후 기대 행동: 기능 추가 또는 버그 수정 시 핵심 비즈니스 규칙을 검증하는 테스트를 최소 1개 이상 함께 작성한다.

## 1. 왜 테스트 코드가 필요한가

### 테스트 코드가 없을 때 발생하는 문제

1. 의도하지 않은 변경을 늦게 발견한다.
   - 수정한 기능은 정상이어도 연관 기능이 깨질 수 있다.
   - 문제가 운영에서 발견되면 어느 커밋에서 발생했는지 추적하기 어렵다.
   - 이전 변경에서 만들어진 오류를 다음 작업자가 떠안게 된다.
2. 같은 기능을 사람이 반복해서 확인한다.
   - 배포 전마다 동일한 시나리오를 수동으로 재현해야 한다.
   - 사람마다 확인 범위와 결과가 달라진다.
3. 리팩터링을 피하게 된다.
   - 기존 동작을 보장할 수 없어 구조 개선보다 코드 덧붙이기를 선택하게 된다.
   - 시간이 지날수록 변경 범위와 유지보수 비용이 커진다.
4. 비즈니스 규칙이 코드 곳곳에 암묵적으로 남는다.
   - 신규 참여자가 정상·예외 케이스를 파악하기 어렵다.
   - 기획 의도와 실제 구현이 달라져도 비교할 기준이 없다.

### 테스트 코드가 주는 효과

1. 변경으로 인한 사이드 이펙트를 개발 단계에서 탐지한다.
2. 버그를 재현하는 테스트를 남겨 같은 문제가 다시 발생하는 것을 막는다.
3. 리팩터링 후에도 기존 동작이 유지되는지 빠르게 확인한다.
4. 테스트 케이스가 실행 가능한 비즈니스 규칙 문서 역할을 한다.
5. 반복적인 수동 검증을 자동화해 장기적인 검증 비용을 줄인다.
6. 실패 시점이 명확해져 원인 후보가 최근 변경 범위로 좁혀진다.

## 2. 자주 나오는 반론과 보완 방법

### “테스트를 작성하면 개발 시간이 늘어난다”

- 초기 작성 시간은 증가한다.
- 대신 반복 검증, 장애 원인 추적, 회귀 버그 수정 시간을 줄일 수 있다.
- 모든 코드를 테스트하기보다 실패 비용이 큰 비즈니스 규칙부터 작성한다.

### “기능을 바꾸면 테스트도 깨져 유지보수 비용이 든다”

- 요구사항이 바뀌었다면 테스트 수정은 필요한 작업이다.
- 구현 세부 사항이 아니라 외부에서 관찰 가능한 동작을 검증하면 불필요하게 깨지는 테스트를 줄일 수 있다.
- 테스트가 실패하면 원인을 먼저 구분해 대응한다.
  - **요구사항 변경**으로 기대 결과가 달라진 경우: 변경된 요구사항에 맞게 테스트를 수정한다.
  - 코드 변경으로 **기존의 정상 동작이 의도치 않게 깨진 경우(회귀)**: 테스트는 유지하고 잘못된 구현을 수정한다.

### “AI가 테스트를 대신 작성할 수 있다”

- AI는 테스트 초안, 경계값 후보, 반복 코드 작성 시간을 줄이는 데 유용하다.
- 하지만 AI가 만든 테스트가 잘못된 요구사항이나 현재 구현을 그대로 정답으로 고정할 수 있다.
- 개발자는 테스트 이름, 입력값, 기대 결과, 누락된 예외 케이스를 반드시 검토한다.
- 원칙: **작성은 AI의 도움을 받을 수 있지만, 테스트의 의도와 기대 결과에 대한 책임은 개발자에게 있다.**

## 3. 무엇을 테스트할 것인가

우선순위는 코드 커버리지 수치보다 실패했을 때의 영향으로 정한다.

1. 주문 상태 전이, 결제·취소·환불 등 핵심 비즈니스 규칙
2. 금액, 수량, 시간대처럼 오류 영향이 큰 계산
3. 권한, 매장 범위, 사용자 입력값 검증
4. 장애가 발생했던 버그의 재현 케이스
5. 외부 시스템·DB 연동 경계와 실패 처리
6. 자주 수정되거나 구조가 복잡한 코드

단순한 프레임워크 동작, getter/setter, 구현 내부 호출 횟수처럼 가치가 낮거나 변경에 취약한 검증은 우선순위를 낮춘다.

## 4. 좋은 테스트의 기준

- 테스트 이름만 읽어도 조건과 기대 결과를 알 수 있다.
- Arrange(준비) → Act(실행) → Assert(검증) 흐름이 드러난다.
- 한 테스트는 하나의 행동 또는 규칙을 명확하게 설명한다.
- 실행 결과가 환경이나 실행 순서에 따라 달라지지 않는다.
- 실패 메시지만으로 어떤 규칙이 깨졌는지 추적할 수 있다.
- 구현 방식보다 사용자가 관찰하는 결과를 검증한다.
- 테스트 데이터 생성과 정리 방법이 일관적이다.

## 5. 테스트 범위 선택

| 구분 | 검증 대상 | 장점 | 주의점 |
| --- | --- | --- | --- |
| 단위 테스트 | 함수·클래스의 핵심 규칙 | 빠르고 원인 파악이 쉽다 | 실제 DB·연동 오류는 찾기 어렵다 |
| 통합 테스트 | 모듈, DB, 외부 경계의 연결 | 실제 구성에 가까운 문제를 찾는다 | 설정과 데이터 정리가 필요하다 |
| E2E 테스트 | API 요청부터 응답까지의 주요 흐름 | 사용자 관점의 신뢰도가 높다 | 느리고 실패 원인 범위가 넓다 |

모든 경우를 E2E로 작성하지 않는다. 핵심 규칙은 빠른 단위 테스트로, DB 쿼리·트랜잭션·API 계약처럼 연결이 중요한 부분은 통합 또는 E2E 테스트로 검증한다.

## 6. `preppers-order-server` 적용 방법

현재 프로젝트의 테스트 규칙은 다음과 같다.

1. 테스트는 `/test/{도메인}` 폴더에 작성한다.
2. 구현 전에 테스트 플랜을 케이스 목차로 먼저 작성한다.
3. 테스트 데이터의 날짜와 SQL 시간대는 UTC+9 기준을 명시한다.
4. 여러 속성을 검증할 때는 중요한 값만 `toMatchObject` 등으로 비교한다.
5. 같은 쿼리를 사용하는 동일 행동은 불필요하게 테스트를 쪼개지 않는다.
6. KDS DB가 필요한 경우 기존 `test/customer-order/setup.ts`의 `createTestAppWithKds` 패턴을 참고한다.
7. E2E 테스트는 DB 연결과 프로세스 종료 권한을 포함한 실행 환경이 필요하다.
8. 테스트 데이터는 다른 테스트와 충돌하지 않게 만들고, `afterAll`에서 정리한다.

> 실제 발표 전 프로젝트의 `package.json`, 테스트 설정 파일, CI 설정을 확인해 아래 실행 명령과 환경 변수 이름을 확정한다.

### 권장 작성 순서

1. 요구사항을 정상·예외·경계값 케이스로 나눈다.
2. 가장 중요한 실패 시나리오 하나를 테스트로 작성한다.
3. 테스트가 의도한 이유로 실패하는지 확인한다.
4. 코드를 구현하거나 수정한다.
5. 새 테스트와 기존 테스트가 모두 통과하는지 확인한다.
6. 중복된 픽스처와 설정을 정리하고 테스트 이름을 다시 검토한다.

## 7. 데모 시나리오

예시: 주문 상태 변경 또는 픽업 주문 강제 완료 규칙

1. **상황 설명**: 기존 정상 동작과 변경할 요구사항을 한 문장으로 설명한다.
2. **테스트 없이 수정**: 수정 지점만 보면 정상처럼 보이지만 연관 케이스의 영향을 알기 어렵다는 점을 보여준다.
3. **회귀 테스트 작성**: 기존에 반드시 유지되어야 할 동작을 테스트로 고정한다.
4. **기능 수정**: 요구사항을 반영하고 테스트 실패를 확인한다.
5. **테스트와 구현 보정**: 의도한 동작이 되도록 구현한 뒤 전체 테스트를 실행한다.
6. **결과 비교**: 수동 확인 항목, 실패 발견 시점, 원인 추적 범위가 어떻게 달라졌는지 정리한다.

참고 후보: `preppers-server`의 픽업 주문 강제 완료 수정 커밋 `f776e4a646d8413be098af678ba13761517decea`. 발표 대상 저장소가 `preppers-order-server`이므로 실제 데모에 적합한지 사전에 확인한다.

### 발표 전 채워야 할 데모 정보

- 실행 명령: `[package.json 확인 후 입력]`
- 필요한 환경 변수 및 DB: `[테스트 환경 확인 후 입력]`
- 대상 테스트 파일: `[경로 입력]`
- 기능 변경 커밋 또는 PR: `[링크 입력]`
- 예상 실행 시간: `[측정 후 입력]`

## 8. 팀 적용 제안

처음부터 높은 커버리지를 목표로 하지 않고 아래 기준부터 적용한다.

1. 버그 수정 PR에는 버그를 재현하는 테스트를 함께 추가한다.
2. 신규 기능 PR에는 핵심 정상 케이스와 실패 비용이 큰 예외 케이스를 추가한다.
3. PR 리뷰에서 테스트 이름만으로 요구사항을 이해할 수 있는지 확인한다.
4. 테스트 실패의 원인에 따라 수정 대상을 결정한다.
   - 요구사항이 변경된 경우에는 테스트의 기대 결과를 수정한다.
   - 기존 기능이 의도치 않게 깨진 회귀인 경우에는 테스트가 아니라 구현을 수정한다.
5. 반복적으로 느리거나 불안정한 테스트는 방치하지 않고 원인을 기록해 개선한다.

### 적용 효과 확인 지표

~~- 버그 수정 시 재현 테스트가 추가된 비율~~
  PR 라벨 및 템플릿 정도로만 기록
~~- PR 또는 배포 전에 발견된 회귀 버그 수~~
- 전체 테스트 실행 시간과 불안정한 테스트 수
~~- 장애 발생 후 원인 커밋을 찾고 수정하는 데 걸린 시간~~

커버리지는 누락 영역을 찾는 참고 지표로만 사용하며, 목표 수치 자체를 테스트의 품질로 판단하지 않는다.

## 9. 마무리

- 테스트는 추가 업무가 아니라 변경 결과를 자동으로 확인하는 장치다.
- 모든 것을 테스트할 필요는 없지만, 핵심 비즈니스 규칙과 장애 재발 방지 테스트는 남겨야 한다.
- AI로 작성 속도는 높일 수 있지만 기대 결과와 누락 케이스는 개발자가 검증해야 한다.
- 작은 기준부터 꾸준히 적용하면 리팩터링과 배포에 대한 신뢰가 쌓인다.

### 발표 후 바로 할 일

1. 각자 최근 수정한 기능에서 가장 중요한 규칙 하나를 선택한다.
2. 해당 규칙의 정상 또는 예외 테스트 한 개를 작성한다.
3. 실행하면서 막힌 설정과 공통 패턴을 문서에 추가한다.
