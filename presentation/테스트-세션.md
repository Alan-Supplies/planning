# 테스트 코드 작성 및 활용 (팀 세션)

## 이 세션의 목적

한 문장: **"테스트가 도움이 된다"를 말로 설득하는 게 아니라, 데모로 체감하게 한다.**

- 대상: 테스트 작성 경험이 적거나, 일정 압박으로 테스트를 생략해 온 개발자
- 핵심 메시지: **테스트의 목적은 버그 없는 코드가 아니라, 변경의 결과를 빠르고 반복 가능하게 확인하는 것이다.**
- 세션 후 기대 행동: 각자 자기 코드에서 테스트할 규칙 1개를 그 자리에서 고른다.

> **진행 원칙**
> - 이 세션의 90%는 2부(라이브 데모)다. 1부는 "왜"만 빠르게 못 박고 넘어간다.
> - 3·4·5·6·8장은 세션에서 낭독하지 않는다. 슬라이드로 스치고 "문서로 읽어라"로 처리한다 (→ 부록).
> - 죄책감을 주지 않는다. "왜 테스트 안 쓰세요?"로 열지 않는다. 방어적 변명 대회가 된다.

## 진행 순서 (약 35분)

| 시간 | 구성 | 목표 |
| --- | --- | --- |
| 5분 | 1부. 왜 지금 이 이야기를 하는가 | "동의"가 아니라 "불편함"을 건드린다 |
| 20분 | 2부. 라이브 데모 (7장, 별도 작성) | 빨강→초록을 눈으로 보게 한다 |
| 5분 | 3부. 즉석 착수 | 각자 규칙 1개 선정, 그 자리에서 |
| 5분 | 예비/질의 | 반론 대응(2장 카드) 꺼내 쓰기 |

---

## 1부. 왜 지금 이 이야기를 하는가 (5분)

> **진행 가이드**: 아래를 다 읽지 않는다. "겪어본 장면"을 하나 던지고 고개를 끄덕이게 만드는 게 목표다.

### 테스트가 없을 때 우리가 반복하는 장면

1. **의도하지 않은 변경을 늦게 발견한다.** 수정한 기능은 멀쩡한데 연관 기능이 조용히 깨지고, 운영에서 터진 뒤에야 어느 커밋인지 뒤진다. 이전 변경의 오류를 다음 작업자가 떠안는다.
2. **같은 시나리오를 사람이 매번 다시 눌러본다.** 배포 전마다 수동 재현. 사람마다 확인 범위가 다르다.
3. **리팩터링을 피한다.** 기존 동작을 보장할 수 없으니 구조 개선 대신 코드를 덧붙인다. 유지보수 비용이 계속 커진다.
4. **비즈니스 규칙이 코드 곳곳에 암묵적으로 흩어진다.** 신규 참여자가 정상·예외 케이스를 못 읽고, 기획 의도와 구현이 갈라져도 비교 기준이 없다.

### 테스트가 바꾸는 것 (데모에서 직접 볼 것)

- 변경으로 인한 사이드 이펙트를 **개발 단계에서** 잡는다.
- 실패 시점이 명확해져 원인이 **최근 변경 범위로** 좁혀진다.
- 버그 재현 테스트를 남겨 **같은 문제가 다시 나는 것**을 막는다.
- 테스트가 **실행 가능한 비즈니스 규칙 문서**가 된다.

> **1부 마무리 멘트**: "이거 다들 아는 얘기죠. 근데 아는데 왜 안 하게 될까요? 지금 그걸 코드로 직접 보겠습니다." → 바로 2부로.

---

## 2부. 라이브 데모 (20분) — 별도 작성

> 데모 시나리오·실행 명령·대상 커밋은 `preppers-order-server` 기준으로 **별도 문서에서 확정**한다.
> 이 세션의 성패는 여기서 갈린다. 데모가 매끄럽지 않으면 "역시 테스트는 귀찮다"는 반대 인상만 남는다.

### 데모에 반드시 심을 개입 포인트 (딱 하나)

연관 기능이 조용히 깨진 지점에서 **멈추고** 팀에게 묻는다:

> "이거, 지금 테스트 없이 어떻게 확인하실 거예요?"

팀원이 "일일이 눌러봐야죠"라고 답하는 순간, 다음에 등장할 테스트의 가치가 **내 입이 아니라 그들 입으로** 정당화된다. 이 한 번의 질문이 20분 데모 전체의 설득력을 만든다.

---

## 3부. 즉석 착수 (5분)

> **진행 가이드**: 세션이 끝나면 아무도 안 한다. 반드시 "그 자리에서" 시작시킨다.

1. 각자 **최근 수정한 기능에서 가장 중요한 규칙 1개**를 고른다.
2. 채팅/보드에 한 줄로 적는다: "나는 `______` 규칙의 `정상/예외` 케이스를 테스트하겠다."
3. 이번 주 자기 PR에 그 테스트 1개를 붙인다. 막힌 설정·공통 패턴은 문서에 추가한다.

# 부록 — 문서로 읽는 참고자료

> 세션에서는 낭독하지 않는다. 데모 후 각자 읽고, PR 리뷰 때 기준으로 쓴다.

## A. 자주 나오는 반론과 대응 카드

> 질의응답에서 실제로 나오면 꺼내 쓴다. 세션 중 시간 남으면 1개만 소리 내어 짚는다.

**"테스트를 작성하면 개발 시간이 늘어난다"**
- 초기 작성 시간은 는다. 대신 반복 검증·장애 원인 추적·회귀 수정 시간이 준다.
- 모든 코드가 아니라 **실패 비용이 큰 비즈니스 규칙부터** 작성한다.

**"기능을 바꾸면 테스트도 깨져 유지보수 비용이 든다"**
- 요구사항이 바뀌었다면 테스트 수정은 필요한 작업이다.
- 구현 세부가 아니라 **외부에서 관찰 가능한 동작**을 검증하면 불필요하게 깨지는 테스트가 준다.
- 실패하면 원인부터 구분한다:
  - **요구사항 변경**으로 기대 결과가 달라진 경우 → 테스트를 수정한다.
  - **회귀(기존 정상 동작이 의도치 않게 깨짐)** → 테스트는 유지하고 구현을 고친다.

**"AI가 테스트를 대신 작성할 수 있다"**
- AI는 초안·경계값 후보·반복 코드에 유용하다.
- 하지만 잘못된 요구사항이나 현재 구현을 그대로 정답으로 고정할 수 있다.
- 개발자는 테스트 이름·입력값·기대 결과·누락 예외를 반드시 검토한다.
- 원칙: **작성은 AI의 도움을 받되, 의도와 기대 결과에 대한 책임은 개발자에게 있다.**

## B. 무엇을 테스트할 것인가

우선순위는 커버리지 수치가 아니라 **실패했을 때의 영향**으로 정한다.

1. 주문 상태 전이, 결제·취소·환불 등 핵심 비즈니스 규칙
2. 금액·수량·시간대처럼 오류 영향이 큰 계산
3. 권한, 매장 범위, 사용자 입력값 검증
4. 장애가 났던 버그의 재현 케이스
5. 외부 시스템·DB 연동 경계와 실패 처리
6. 자주 수정되거나 구조가 복잡한 코드

단순 프레임워크 동작, getter/setter, 내부 호출 횟수처럼 가치가 낮거나 변경에 취약한 검증은 우선순위를 낮춘다.

## C. 좋은 테스트의 기준

- 이름만 읽어도 조건과 기대 결과를 알 수 있다.
- Arrange(준비) → Act(실행) → Assert(검증) 흐름이 드러난다.
- 한 테스트는 하나의 행동/규칙을 설명한다.
- 실행 결과가 환경·순서에 따라 달라지지 않는다.
- 실패 메시지만으로 어떤 규칙이 깨졌는지 추적된다.
- 구현 방식보다 관찰 가능한 결과를 검증한다.
- 데이터 생성·정리 방법이 일관적이다.

## D. 테스트 범위 선택

| 구분 | 검증 대상 | 장점 | 주의점 |
| --- | --- | --- | --- |
| 단위 | 함수·클래스의 핵심 규칙 | 빠르고 원인 파악 쉬움 | 실제 DB·연동 오류는 못 잡음 |
| 통합 | 모듈·DB·외부 경계의 연결 | 실제 구성에 가까운 문제 발견 | 설정·데이터 정리 필요 |
| E2E | API 요청→응답 주요 흐름 | 사용자 관점 신뢰도 높음 | 느리고 실패 원인 범위 넓음 |

모든 경우를 E2E로 짜지 않는다. 핵심 규칙은 빠른 단위로, DB 쿼리·트랜잭션·API 계약처럼 연결이 중요한 부분은 통합/E2E로 검증한다.

## E. `preppers-order-server` 적용 규칙

1. 테스트는 `/test/{도메인}` 폴더에 작성한다.
2. 구현 전에 테스트 플랜을 케이스 목차로 먼저 작성한다.
3. 테스트 데이터의 날짜와 SQL 시간대는 UTC+9 기준을 명시한다.
4. 여러 속성 검증 시 중요한 값만 `toMatchObject` 등으로 비교한다.
5. 같은 쿼리를 쓰는 동일 행동은 불필요하게 테스트를 쪼개지 않는다.
6. KDS DB가 필요하면 `test/customer-order/setup.ts`의 `createTestAppWithKds` 패턴을 참고한다.
7. E2E는 DB 연결과 프로세스 종료 권한을 포함한 실행 환경이 필요하다.
8. 테스트 데이터는 다른 테스트와 충돌하지 않게 만들고 `afterAll`에서 정리한다.

### 권장 작성 순서

1. 요구사항을 정상·예외·경계값 케이스로 나눈다.
2. 가장 중요한 실패 시나리오 하나를 테스트로 작성한다.
3. 테스트가 의도한 이유로 실패하는지 확인한다.
4. 코드를 구현/수정한다.
5. 새 테스트와 기존 테스트가 모두 통과하는지 확인한다.
6. 중복 픽스처·설정을 정리하고 테스트 이름을 다시 검토한다.

## F. 팀 적용 제안

처음부터 높은 커버리지를 목표하지 않고 아래 기준부터 적용한다.

1. 버그 수정 PR에는 버그를 재현하는 테스트를 함께 추가한다.
2. 신규 기능 PR에는 핵심 정상 케이스와 실패 비용이 큰 예외 케이스를 추가한다.
3. PR 리뷰에서 테스트 이름만으로 요구사항을 이해할 수 있는지 확인한다.
4. 실패 원인에 따라 수정 대상을 정한다: 요구사항 변경 → 기대 결과 수정 / 회귀 → 구현 수정.
5. 느리거나 불안정한 테스트는 방치하지 않고 원인을 기록해 개선한다.

**적용 효과는 이것만 본다**: 전체 테스트 실행 시간과 불안정한 테스트 수.
커버리지는 누락 영역을 찾는 참고 지표로만 쓰고, 목표 수치 자체를 품질로 판단하지 않는다.

## G. 한 줄 요약

- 테스트는 추가 업무가 아니라 변경 결과를 자동으로 확인하는 장치다.
- 모든 걸 테스트할 필요는 없지만, 핵심 비즈니스 규칙과 장애 재발 방지 테스트는 남긴다.
- AI로 속도는 높이되, 기대 결과와 누락 케이스는 개발자가 검증한다.
- 작은 기준부터 꾸준히 적용하면 리팩터링과 배포에 대한 신뢰가 쌓인다.
