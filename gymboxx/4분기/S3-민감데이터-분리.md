## 한 줄 요약

**10/1에 막았다고 판정한 여권 사진이 다른 경로로 지금도 공개돼 있다.**
버킷 하나에 공개 이미지와 신분증·서류가 섞여 있고, CloudFront와 객체 ACL로 버킷 전체가 열려 있어서
사고가 날 때마다 경로를 하나씩 막는 방식이 됐다. 민감 데이터를 공개 경로에서 **구조적으로** 분리한다.

## 배경

### 10/1 조치

  `DenyPassportReadOutsideAccount`(그 경로만 Deny) 추가, CloudFront 무효화 후 403 확인 → "마무리"

### 구조적 원인

1. **CloudFront OAC가 버킷 전체(`gymboxx-prod/*`) 읽기 허용** → 버킷 안 모든 파일이 CloudFront 주소로 공개
2. **객체 ACL 허용**(`BucketOwnerPreferred`) → 파일마다 public-read가 붙어 S3 직접 주소로도 공개.
   버킷 정책 기준 점검(`IsPublic`)에는 '비공개'로 나온다
3. **공개 이미지와 민감 서류가 한 버킷에 혼재** → 경로 단위 Deny로만 막을 수 있고, 경로가 바뀌거나 늘면 빠진다

## 목표

### 반드시 (4분기 완료 판정 기준)

- **민감 데이터 익명 접근 0** — 신분증·여권·사업자등록증·지원서 등으로 분류된 모든 경로가 S3 직접·CloudFront
  모든 주소에서 403. 주 1회 자동 점검으로 유지 확인
- **민감 데이터가 공개 CloudFront·ACL이 붙은 버킷에 0** — 전용 비공개 버킷으로 이관, 접근은 서버 presigned URL
- **버킷 대장 100%** — 113개 전부 소유자·용도·민감도·공개 방식·IaC 여부 기입
- **민감 파일 열람 기록** — presign 발급마다 누가·어떤 파일을 열람했는지 남긴다. 지금은 알 방법이 없다

### 확장 (여유가 있으면, 미달해도 실패 아님)

- 객체 ACL 비활성화(`BucketOwnerEnforced`) 전환 버킷 수
- 죽은 버킷 삭제 수 (dev2, `*-new`, 폐기된 서비스 배포 버킷 등)
- 정적 웹 호스팅 24개의 CloudFront OAC 전환 → 계정 단위 Block Public Access 활성화
- 버킷 표준 Terraform 모듈과 생성 요청 PR 경로

## 열린 질문

- **개인정보 노출 대응 절차** — 1년 이상 공개돼 있던 여권·사업자등록증에 대해 회사 차원의 판단(신고 필요 여부 등)을
  누가 하는가. 기술 조치와 별개로 보고가 필요하다
- **여권 사진 보관 필요성** — 인증 후에도 원본을 계속 보관해야 하는가. 보관 근거가 없다면 이관보다 삭제가 맞다
- 2025-04-14 업로드 경로 변경이 어떤 배포였는지 (app-server 커밋 확인)
- 조회 화면이 쓰는 URL 형태 — 10/29 코드 검색 기준 업로드·열람 위치는 아래와 같다
  - 여권: 업로드 `gymboxx-web`(international get-info) → `gymboxx-app-server` `international-user`, 열람 HQ
    (`gymboxx-headquarter-server` 회원 응답에 `passportImage` 포함). 옛 경로 `user/passport`는 `gymboxx-web services/s3.ts`
  - 트레이너 지원서·사업자등록증: 업로드 `gymboxx-web` → `gymboxx-app-server` `gym`, 열람 HQ
    (`gymboxx-headquarters-client`, `supplies-backoffices` `gymboxx-hq-legacy`·`gymboxx-hq`)
- presigned URL 발급의 인가 — 열람자가 HQ 직원뿐이므로 현재 HQ 인증으로 먼저 만들고, 판정·감사 로그를 한 자리에 모아
  나중에 supplies-auth gymboxx 직원 realm으로 교체할 수 있게 한다 (supplies-auth 의존을 3단계 일정에 넣지 않는다)
- 액세스 로그 보관 여부 — 옛 경로가 실제로 외부에서 조회된 적이 있는지 확인 가능한가

## 리스크

- 민감 경로를 조회하는 화면이 CloudFront 주소를 직접 쓰고 있으면, 차단과 동시에 화면이 깨진다 → 0단계 전에 확인
- DB에 전체 URL(`${bucket_url}/${s3_key}`)이 저장된 경로는 코드뿐 아니라 데이터 갱신이 필요하다
- 버킷 정책 변경 권한이 PS-Admin에만 있어 실행이 사람 대기에 묶인다

## 다음 단계 — 열람 권한을 회사 표준 인증 위로

이 업무가 끝나면 민감 파일은 **HQ 직원만** presigned URL로 열람하고, 열람 기록이 남는다.
남는 문제는 그 "HQ 직원"을 판정하는 토큰이다. 지금 HQ 토큰은 짐박스 자체 대칭키로 발급되고, 회사 원칙
(발급은 supplies-auth 한 곳, 비대칭 서명)과 어긋난다.

| 순서 | 문제 | 해결 |
| --- | --- | --- |
| 1 | 여권이 누구에게나 열려 있다 | 민감 데이터 분리 — **이 문서** |
| 2 | 누가 볼 수 있는지 정해야 한다 | presign + 권한 판정 + 열람 기록 — 이 문서 3단계 |
| 3 | 판정이 짐박스 자체 대칭키 토큰에 기대고 있다 | HQ 직원을 supplies-auth로 수렴 |

3단계에서 권한 판정을 한 자리에 모아 두는 것이 다음 단계로 넘어가는 이음매다 — 그 자리만 새 토큰으로 교체하면 된다.
supplies-auth 작업을 이 업무의 일정에 의존시키지는 않는다.
