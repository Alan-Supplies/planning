# 운동 목표 · 미션 시스템 설계 컨텍스트

Linear: TECH-600 (상위) / TECH-601 (목표 문구) / TECH-602 (미션 생성) / TECH-1382 (달성률 계산)
프로젝트: Gymboxx Habit-OS 1단계

이 문서는 PO 문서 3건을 읽고 정리한 설계 결론이다. PO 문서가 정본이며, 이 문서와 충돌하면 Linear 쪽을 따른다.

---

## 1. 도메인 개념

**목표(Goal)** — 회원이 선택하는 생활형 문구. 활성 목표는 회원당 항상 1개.

**미션(Mission)** — 목표에 딸린 슬롯 최대 5개. 미션 1개 = 축(부위/효과/성격/출석) + 볼륨 수치.

핵심 제약:
- **미션끼리 합산·평균하는 지표가 없다.** 미션 1개 = 홈 게이지 1개. 종합 달성률을 만들지 말 것 (TECH-602 §1-1)
- 슬롯마다 독립 생애주기. 슬롯 A가 100% 도달해도 B~E는 그대로
- 볼륨은 부여 시점에 계산해 **스냅샷 고정**. 이후 기준 테이블이 바뀌어도 진행 중 미션은 불변

---

## 2. 신규 테이블

`goal`, `member_mission` 2개. 스키마는 `goal-mission-schema.dbml` 참조.

마스터 4종(`mission_baseline`, `mission_count_rule`, `body_part_priority`, `goal_phrase`)은 TECH-602 §5에서 "DB 마스터 테이블 또는 코드 내 상수 어느 쪽이든" 허용. 행 수가 20~56행이라 상수로 시작 가능하나, `goal_phrase`(40종)는 문구 수정 요청이 잦을 것이므로 테이블 권장.

### 스냅샷 원칙 (중요)

`member_mission.target_total`은 `mission_baseline`에서 계산된 결과값을 복사 저장한 것이다.
**조회 로직에서 `mission_baseline`을 조인해 현재값을 다시 읽으면 안 된다.** 스냅샷 원칙이 깨진다.

실제 FK는 2개뿐:
- `goal.goal_phrase_id → goal_phrase.id`
- `member_mission.goal_id → goal.id`

`mission_baseline`, `workout_session`과의 관계는 FK가 아니다. 전자는 값 복사 관계이고(참조 키도 불완전 — `age_band`/`sex`를 미션이 갖고 있지 않음), 후자는 축 기반 집계 관계로 조인 키가 없다.

## 3. 미션 생성 (TECH-602)

```
① 파라미터 확보(연령·성별·목적·슬롯 회차)
② 개수 배분 (§7-1)
③ 축 값 배정 (§7-2 우선순위 로테이션)
④ 볼륨 산출
⑤ 검증
⑥ 슬롯 배정·저장 (스냅샷)
```

볼륨 공식 (§6):
```
target_total = per_visit_amount × 10 × frequency_factor
```

### 우선순위 로테이션

우선순위 리스트는 **목적 × 성별** 단위로 하나 존재하며, 그 목적의 모든 부위 슬롯이 **공유**한다. 슬롯별 리스트가 따로 있는 게 아니다.

초기 배정은 리스트 앞에서부터 필요한 개수만큼 (§7-5). 교체 시 한 칸 이동하고, **다른 슬롯이 점유 중인 값과 겹치면 한 칸 더 이동** (§4-1 ③).

> 미해결: 슬롯의 현재 리스트 위치를 별도 컬럼으로 저장할지, `target_param`으로 `indexOf` 역산할지.
> 역산도 성립하나 우선순위 리스트를 운영 중에 변경하면(§5-3에서 데이터 관리 명시) 진행 중 목표의 다음 배정이 달라진다. Alan 검토 중.

`slot_generation`은 교체 횟수 기록이며, §13 볼륨 상향 계수(PO 미확정)의 입력이 될 수 있다.

## 4. 달성률 계산 (TECH-1382)

### 전량 재산출 — 가장 중요한 설계 결정

누적 가산이 **아니다**. 트리거마다 원천 기록 전체를 다시 집계한다 (§2 원칙 7).

결과:
- **멱등키가 필요 없다.** 같은 이벤트가 두 번 와도 재집계 결과가 같다 (§8-1 검증 8)
- 기록 수정·삭제에도 항상 정답이 나온다
- "카운트 +1" 증분 모델로 구현하지 말 것

### 트리거

- 운동 기록 종료·수정 (`end_at` 확정)
- 미션 부여·교체 (`assigned_at` 갱신)
- 목표 상태 변경 (완료·변경 클릭)

### 집계 필터 (§4 공통)

- 해당 회원
- **그 미션의 `assigned_at` 이후** 기록만 (이월 없음을 물리적으로 보장)
- 종료된 세션 (`end_at IS NOT NULL`)
- 삭제/INACTIVE 제외
- 외부 운동 (`source='OUTSIDE'`) 포함

미션마다 자기 `metric_type`/`target_param`에 맞는 기록만 긁는다. 가슴만 운동한 세션은 가슴 관련 미션만 오르고 나머지는 변동 0이어야 한다.

### 분자 계산 예 — `가슴 40세트분` (§4-1)

| 운동 | 수행 | 가슴 기여도 | 실적 |
|---|---|---|---|
| 머신 체스트 프레스 | 4세트 | 중간가슴 직접 1.0 | 4.0 |
| 덤벨 인클라인 벤치 | 4세트 | 윗가슴 1.0 + 중간가슴 보조 0.5 | 6.0 |
| | 8세트 | | **10.0세트분** = 25% |

**한 세트가 1세트분을 초과할 수 있다.** 세부부위 복수 기여를 합산하기 때문. "세트분" 단위 표기를 쓰는 이유이며, CS 문의 원인이 될 수 있음을 PO도 인지.

### 저장

미션별 1행. 홈 조회는 저장값을 반환하고 재집계하지 않는다 (§6).
`numerator`는 소수 보존, 표시할 때만 반올림. `rate`는 캡 없음 (2.0 = 200%).

## 5. 상태 전이

### goal

```
ACTIVE → COMPLETED  (완료 버튼)
       → CHANGED    (다른 목표로 변경)
```

단방향. 재활성 없음 — 불러오기 기능은 PO와 논의해 제외 확정.
완료는 사용자 클릭으로만. 시스템 자동 판정 없음.

> 미해결: TECH-601 §0-4의 "삭제" 조작. 소프트 처리로 통일할지, 하드 삭제(미션 히스토리까지)가 남는지 미확인.

### member_mission

```
IN_PROGRESS → CLEARED    (rate ≥ 1.0)
CLEARED     → REPLACED   (사용자 교체 선택)
둘 다       → CLOSED     (목표 완료·변경)
```

단방향. `REPLACED`/`CLOSED` 도달 후에도 **삭제하지 않고 보존** — 목표별 히스토리(TECH-601 §0-4-1)의 원천.

`CLEARED`는 종료 상태가 아니다. 100% 넘겨도 재계산이 계속 돌아 초과율이 갱신된다. 교체 버튼이 열릴 뿐이고 실제 전이는 사용자 조작이 필요하다.

> 미해결: `CLEARED` 상태에서 기록 수정으로 rate가 1.0 아래로 떨어지면? 문서에 `CLEARED → IN_PROGRESS` 역전이가 없다. PO 확인 필요.

## 6. 저장소에서 확인이 필요한 것

이 설계는 기존 운동 기록 스키마를 전제하는데 실제 구조를 확인하지 못했다.

- [ ] 세트 단위 테이블 구조 — 축 기반 집계가 이걸 전제로 함
- [ ] 부위 기여도 매핑 (직접 1.0 / 보조 0.5) 이 데이터가 어디에 있는지
- [ ] `source='OUTSIDE'` 필드 존재 여부
- [ ] `metric_type` 값 이름 — TECH-1382에 "DB 구조 개편에서 확정, 잠정 표기"로 돼 있음. DBML의 enum은 잠정값
- [ ] `mission_baseline` PK에 `target_param`이 들어가나 유산소·스트레칭은 null. Postgres는 nullable을 PK에 못 넣으므로 센티널 값 또는 서로게이트 키 + unique 제약으로 처리 필요

## 7. 폐기된 초기 가정

Claude Code가 이전 논의 흔적을 발견했을 때 혼동하지 않도록 기록.

| 초기 가정 | 실제 |
|---|---|
| 액션 아이템 = 고정 마스터, 조회 시 필터링 | 규칙 기반으로 매번 생성 |
| 완료수/전체수 종합 달성률 | 종합 지표 없음. 미션별 독립 게이지 |
| `WorkoutCompleted` → 카운트 +1 | 전량 재집계 |
| 멱등키 필요 | 전량 재집계라 불필요 |
| 목표 수정 불가, 슬롯만 교체 | 목표 변경 조작 존재 (TECH-601 §0-4) |
| `MemberMission.status` = ACTIVE/ARCHIVED 2종 | 4종 (IN_PROGRESS/CLEARED/REPLACED/CLOSED) |
| `archived_reason` 컬럼 | 불필요. REPLACED/CLOSED가 구분을 담음 |
| 진척도 별도 테이블 (락 경합 우려) | `member_mission`에 컬럼으로 흡수. 단일 actor라 경합 없음 |
