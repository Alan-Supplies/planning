# Goal/Mission 이벤트 모델링 — 혼란 정리 (TECH-600 계열)

## 1. 액션 아이템 → 미션(Mission) 개념 전환
- **초기 가정(틀림):** 액션 아이템 = 고정 마스터 데이터, 목표 조건으로 조회 시점 필터링 (2-b)
- **PO 문서(TECH-602) 확인 결과:** 미션은 규칙 기반으로 **매번 생성**됨
  - 미션 1개 = 축(부위/효과/성격/출석) 값 + 볼륨 수치
  - 슬롯 최대 5개, 슬롯마다 독립 생애주기
  - 볼륨 = `per_visit_amount × 10 × frequency_factor` (§6), **할당 시점에 계산 후 스냅샷 고정**
  - "액션 아이템은 수정 불가능하다"는 원래 발언은 재해석 필요 — 운동 종목 마스터를 말한 건지, 계수 테이블(변경 가능하나 스냅샷으로 무영향)을 말한 건지 불명확했음

## 2. "완료수/전체수" 합산 달성률 — 폐기
- **초기 가정(틀림):** 목표 전체 달성률 = 완료수/전체수 (필터링된 개수 기준)
- **PO 문서 확인 결과:** "미션끼리 합산·평균하는 지표 없음" (§1-1) — **미션 1개 = 홈 게이지 1개**, 개별 진행률만 존재 (예: 데드리프트 2/3)

## 3. 스냅샷 방식
- **미결이었던 것:** 마스터 테이블 변경 시 스냅샷 vs 라이브 재계산
- **확정:** 스냅샷. 단, FK로 마스터 참조하지 말고 **계산된 최종값을 그대로 복사 저장**
  - `templateId`는 추적용 FK로만 남기고, 조회 로직에서 마스터를 다시 조인해 현재값을 읽지 않도록 주의

## 4. "목표 갱신" — 두 차례 정정됨
- **1차 정정:** "목표는 1개, 갱신 가능"이라는 표현이 실제로는 두 개의 다른 이벤트였음
  - 슬롯(미션) 교체 — 100% 도달 시, 그 슬롯만
  - 목표 완료 → 재선택 — 슬롯 5개 전체 재생성
  - 이 시점에 "목표 자체 수정은 불가, 슬롯 수정만 가능"으로 결론
- **2차 정정 (1차 결론이 틀림):** TECH-601 확인 결과, 목표 상태 조작은 4종류가 명시돼 있었음
  - 완료 / **변경(기존 목표 히스토리로, 미션 수행 내용은 살아있음)** / 삭제(미션 히스토리까지 삭제) / 불러오기(미완료 목표만, 진척 이어받음)
  - "목표 수정 불가"는 하위 문서(TECH-602, 미션 생성 문서)에 안 나온다는 이유로 내린 성급한 추론이었음
- **최종 확정 (PO와 논의 후):** 불러오기 기능은 없애기로 함. 삭제 조작의 최종 처리 방식은 아직 미확정 (아래 6번)

## 5. 네이밍 — MemberMission 확정
- `exercise_*` 접두어(마스터 데이터 네임스페이스와 충돌) → 기각
- `exerciseMission`, `MemberExerciseMission` → 기각 (존재하지 않는 exercise FK 관계를 암시, ATTENDANCE 축과 의미 불일치)
- 다른 층위 미션과의 구분 필요성 → 모듈 경로(`habit-os/`)로 1차 방어, 이름 자체엔 `MemberMission` 유지 결정
- 템플릿/인스턴스 구분 필요 확인 후 `MissionTemplate` / `MemberMission` 쌍으로 확정
  - PO 문서엔 볼륨까지 미리 계산된 템플릿은 없음(할당 시점에 §6 공식으로 매번 계산) — 템플릿은 축/개수 정의 수준

## 6. 필드 추가 기각 — 둘 다 파생 가능 (2026-09-08 확정)

### 6-1. `MemberMission.archivedReason` — 도입 안 함
- 목적이었던 REPLACED vs GOAL_ENDED 구분은 **저장 없이 역산된다**
  - 같은 `goalId + slotNo` 에 자신보다 큰 `slotGeneration` 이 존재 → 교체(REPLACED)
  - 자기가 그 슬롯의 마지막 회차 → 목표 종료(GOAL_ENDED)
- 진행률로 유추하는 방식(100%면 교체)은 불완전 — 100% 도달 후 교체하지 않은 채 목표를 완료한
  케이스(§2-1에서 정상 상태로 명시)가 GOAL_ENDED 인데도 100% 이기 때문. 위의 회차 기준을 쓴다
- 결론: 파생 가능한 중복 컬럼이라 불일치 위험만 늘린다

### 6-2. `priorityListIndex` — 도입 안 함
- 기존 논거("slotGeneration만으로는 충돌 회피 반영된 절대 위치 역산 불가")는 사실이지만
  **generation으로 역산한다는 전제 자체가 틀렸다**
- 미션에 **부위 값이 이미 저장**돼 있고 우선순위 목록은 목적×성별 고정 상수 →
  `list.indexOf(미션.부위)` 가 곧 현재 인덱스
- 교체 알고리즘 (저장 불필요, 매번 계산)
  ```text
  next = (list.indexOf(현재 미션의 부위) + 1) % list.length
  while (next 부위가 다른 슬롯에서 진행 중) { next = (next + 1) % list.length }
  ```
- 부수 결정
  - `slotGeneration` 의 역할은 **인덱스가 아니라 결정성 시드 + 이력 카운터** — §13 볼륨 상향 계수 입력으로만 쓴다
  - 우선순위 목록 개정으로 `indexOf = -1` 이 되는 경우는 필드가 아니라 **fallback 규칙 한 줄**로 처리
    (목록 앞에서부터 진행 중 부위 회피)
  - 부위 없는 미션(유산소·스트레칭·균형)은 로테이션 대상이 아니라 인덱스 개념 자체가 무의미

### 6-3. 원문 서술 불일치 — 원문은 고치지 않음 (2026-09-08 확정)
- `미션생성시스템.md` §4-1(L300) · §4-3(L340) · §7-2(L939) · §7-5(L1077)이 모두
  **"슬롯 회차를 인덱스로 순환 선택"** 이라고 서술 — §7-5의 충돌 회피 규칙과 양립 불가
- 맞는 서술은 **"현재 부위의 다음 값"**
- **원문(PO 문서 전사본)은 수정하지 않는다.** 구현은 6-2를 정본으로 삼고, 원문의 "슬롯 회차를 인덱스로"는
  충돌 회피가 없는 경우에만 우연히 일치하는 축약 표현으로 읽는다

## 7. Goal 삭제 조작 — 소프트 삭제 확정 (2026-09-08)
- **하드 삭제하지 않는다.** 원래 문서 §0-4의 하드 삭제(미션 히스토리까지 삭제)는 적용 안 함
- Goal · MemberMission 모두 ARCHIVED 로 보내는 소프트 처리로 통일
- 근거 — 6-1에서 `archivedReason` 을 기각하고 "같은 `goalId + slotNo` 의 후속 회차 존재 여부"로
  종료 사유를 역산하기로 했으므로, 행이 사라지면 그 역산 근거 자체가 없어진다
- 삭제된 목표의 미션은 통계·이력 조회에서 제외 대상으로만 다루고 행은 보존

## 8. 볼륨 상향 계수 — 도입 안 함 (2026-09-08 확정)
- 개념 — 같은 슬롯에서 미션을 반복 부여받을 때 회차마다 볼륨을 올리는 계수(점진적 과부하).
  `볼륨 = per_visit × 10 × frequency_factor × f(slotGeneration)` 형태로 §6 산식에 항을 추가하려던 것
- **적용하지 않는다.** §6 산식은 지금 형태(`per_visit × 10 × frequency_factor`)를 그대로 유지
- 근거
  - **이중 계상** — `per_visit_amount` 는 실측으로 갱신되는 값(원문 L1143). 회원이 강해지면 실측 1회
    운동량이 올라가 다음 회차 미션이 자동으로 무거워진다. 계수를 곱하면 같은 성장을 두 번 세는 셈
  - **기준선 파괴** — §6 `× 10` 은 "10회 방문 = 100%" 기준선의 근거다. 계수를 곱하면 이 기준선이 깨진다
  - **기준 회차 불일치** — 원문은 슬롯 회차를 쓴다고 하는데, 슬롯은 부위가 로테이션되므로
    슬롯 3회차가 "그 부위를 3번째로 한다"는 뜻이 아니다. 부위별 과부하를 원했다면 기준 자체가 틀렸다
- `slotGeneration` 에 남는 용도 — **이력 카운터 + 종료 사유 역산(6-1) + 결정성 시드**뿐.
  로테이션 인덱스(6-2 기각)도 볼륨 계수(여기서 기각)도 아니다

### 8-1. 원문의 `§13` 참조는 끊긴 링크
- 원문 L269 · L1143 의 `(미결 §13)` 은 **존재하지 않는 섹션을 가리킨다** — `미션생성시스템.md` 는 §9까지만 있음
- 이전 판 주의 문서가 이 표기를 그대로 옮겨 `§13` 으로 적었던 것. 원문은 고치지 않으므로(6-3) 여기에만 기록

## 9. 3번 해소 — ③ 문서 확인 완료 (2026-09-08)

[미션달성률계산시스템.md](미션달성률계산시스템.md)(TECH-1382) 확보. 미결이던 "미션 매칭 방식 · 멱등키"의 답은 다음과 같다.

- **멱등키는 필요 없다** — ③ §2 원칙 7 이 **전량 재산출**이다. "누적 가산이 아니라 원천 전체 재집계 —
  중복·수정·삭제 이벤트에도 항상 정답". 재산출 자체가 멱등이라 이벤트 원장·멱등키를 두면 오히려 원칙 위반
- **매칭 방식** — 이벤트를 미션에 꽂는 게 아니라, 미션의 `metric_type` 별로 원천을 역방향 집계한다.
  ③ §4 가 유형 7종의 분자 산식을 정의
- **기산점** — ③ §2-1 "분자는 그 미션이 슬롯에 부여된 시각 이후 기록만 · **교체 전 초과분 이월 없음**".
  `assigned_at` 이 필수 컬럼
- **재계산 트리거** — 운동 기록 종료·수정·삭제 즉시 + 미션 부여·교체 + 목표 변경·삭제·완료 (③ §6) · 배치 없음

교차 검증으로 얻은 것

| 항목 | ③ 에서의 확인 |
|---|---|
| 6-1 종료 사유 역산 | ③ §6 상태 4종(`IN_PROGRESS`·`CLEARED`·`REPLACED`·`CLOSED`)이 **전부 파생 가능** — 결론 강화 |
| 7 소프트 삭제 | ③ §6 "교체·종료된 미션은 삭제하지 않고 슬롯별로 보존" — 같은 결론 |
| 2 합산 지표 없음 | ③ §1 "종합 달성률 없음 · 미션 1개 = 게이지 1개" — 재확인 |
| 3 스냅샷 | ③ §3 주의 박스가 이 문서 §3·§5 를 직접 인용 |

스키마 반영은 [스키마_draft.md](스키마_draft.md).
