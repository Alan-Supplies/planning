# `scheme.md`와 기획 문서 불일치 정리

> 비교 기준: [`scheme.md`](scheme.md)
>
> 비교 대상: [`미션생성시스템.md`](미션생성시스템.md), [`운동목표문구.md`](운동목표문구.md)
>
> 작성일: 2026-09-09

이 문서는 `scheme.md`를 현재 기준안으로 두고, 두 기획 문서와 비교했을 때 구현 결과가 달라지는 충돌과 스키마 공백을 분리해 기록한다. 단순 용어 차이와 이미 일치하는 내용은 제외한다.

## 요약

| 구분 | 건수 | 우선 확인할 내용 |
|---|---:|---|
| 직접 충돌 | 5 | 유산소 강도, 체력 목적 유산소 2개, 65세 이상 균형, 출석 폴백, 총훈련량 생성 조건 |
| 스키마 공백 | 7 | 목표 문구 마스터, 생성 규칙 마스터, 세그먼트 스냅샷, 로테이션 위치, 직접입력 분류, 삭제, 히스토리 고정 |
| 스키마에만 있음 | 4 | 이유, 설정 종료일, 운동 예정 시간, 문구 스냅샷 |
| 기획 문서 내부·상호 충돌 | 3 | 객관식 전용 대 기타 입력, 최초 슬롯 수, 삭제·불러오기 구판 잔존 |

## 1. 직접 충돌

### C01. 유산소 강도와 달성 단위

| `scheme.md` | `미션생성시스템.md` |
|---|---|
| `CARDIO_MINUTE.targetParam = null` | 강도 파라미터를 중강도·고강도·무관으로 구분 |
| `exercise.training_type = CARDIO`의 실제 운동 분 합산 | 중강도 분 + 고강도 분 × 2로 환산 |
| 유산소 강도 컬럼 불필요 | 유산소 강도 컬럼 신설이 개방 조건 |

영향: 같은 운동 기록으로 계산되는 분자와 목표량이 달라진다. 현재 방향대로라면 `미션생성시스템.md` §1-3, §4-1, §7-1, §7-3, §9-2에서 강도 구분과 환산 내용을 제거하거나 실제 분 기준으로 다시 써야 한다.

### C02. 체력 목적의 유산소 미션 2개

`미션생성시스템.md` §7-1은 체력 목적에 중강도·고강도 유산소를 각각 1개씩 배정한다. 현재 스키마는 두 미션 모두 다음과 같이 동일해진다.

```typescript
{
  metricType: 'CARDIO_MINUTE',
  targetParam: null,
}
```

두 슬롯이 같은 기록을 중복 집계하므로 서로 다른 미션이 되지 않는다. 유산소 강도를 제거하는 방향을 유지한다면 체력 목적의 유산소는 1개로 줄이고 남는 슬롯의 유형을 다시 정해야 한다.

### C03. 65세 이상 균형 미션

`미션생성시스템.md` §7-1과 §8은 65세 이상 건강 목적에 균형 미션 1개를 필수로 요구한다. 그러나 `MissionMetricType`에는 효과별 세션 수 타입이 없고 `targetParam`에도 균형 효과를 저장할 수 없다.

현재 스키마로는 해당 구성을 생성·저장할 수 없다. 다음 중 하나가 필요하다.

- 1차 출시에서 균형 필수 규칙을 비활성화한다.
- 효과 마스터 준비 후 `EFFECT_SESSION`과 효과 파라미터를 스키마에 추가한다.
- 별도 폴백 구성을 확정한다.

### C04. 출석 일수 폴백

`미션생성시스템.md` §1-3과 §9는 생성 검증 실패 시 출석형 미션을 폴백으로 사용할 수 있다고 정의한다. `scheme.md`는 출석 일수 타입을 명시적으로 1차 범위에서 제외한다.

따라서 현재 스키마에는 생성 실패 시 저장할 수 있는 폴백 미션이 없다. 출석 폴백을 제거할지, `ATTENDANCE_DAY`를 추가할지, 출석형이 아닌 폴백 세트를 새로 정의할지 결정해야 한다.

### C05. `BODY_PART_VOLUME` 생성 근거

`scheme.md`는 `BODY_PART_VOLUME`을 1차 타입으로 허용하지만 `미션생성시스템.md`의 기준 운동량 표는 부위별 세트 수만 제공한다. 부위별 kg 기준량도 없고, 부위 미션을 `BODY_PART_SET`과 `BODY_PART_VOLUME` 중 무엇으로 만들지 선택하는 규칙도 없다.

또한 §9-2는 kg 환산 컬럼 신설을 개방 조건으로 두지만 `scheme.md` 재검토 메모는 이미 저장된 kg 사용을 전제로 한다. 다음 세 가지를 함께 확정해야 한다.

- 부위 총훈련량 미션을 1차 생성 대상에 포함할지
- 포함한다면 연령대 × 성별 × 부위별 `per_visit_amount`를 kg 단위로 어떻게 둘지
- lb·보조중량을 포함한 원천 기록을 어떤 규칙으로 kg로 정규화할지

## 2. 기획 요구를 담지 못하는 스키마 공백

### G01. 목표 문구 마스터

`운동목표문구.md` §0-2는 문구·목적 코드·세그먼트·노출 규칙을 가진 목표 마스터 테이블을 필수로 요구한다. `scheme.md`에는 `goalPhraseId`만 있고 참조 대상 인터페이스와 제약이 없다.

최소한 다음 정보의 저장 위치가 필요하다.

```typescript
interface GoalPhrase {
  id: Id;
  phrase: string;
  purpose: GoalPurpose;
  ageBand: 'AGE_10_20' | 'AGE_30' | 'AGE_40' | 'AGE_50_PLUS';
  sex: 'FEMALE' | 'MALE';
  displayOrder: number;
  status: 'ACTIVE' | 'INACTIVE';
}
```

문구 40개 중 중복 문구가 있으므로 `phrase` 단독 UNIQUE는 사용할 수 없다. 세그먼트와 노출 순서를 포함한 유일성 기준을 별도로 정해야 한다.

### G02. 미션 생성 규칙 마스터

`미션생성시스템.md` §5는 다음 데이터를 DB 마스터 또는 변경 가능한 상수로 요구하지만 `scheme.md`에는 정의가 없다.

- 연령대 × 성별 × 지표 × 파라미터별 기준 운동량
- `per_visit_amount`와 `frequency_factor`
- 목적별 미션 개수 배분
- 목적 × 성별별 부위 우선순위

`scheme.md`가 회원 인스턴스 테이블만 다루는 문서라면 별도 마스터 스키마 문서로 분리하고 링크해야 한다. 전체 DDL의 기준이라면 이 테이블들을 추가해야 한다.

### G03. 생성 당시 세그먼트와 규칙 보존

미션 생성은 연령·성별·목적을 입력으로 사용하지만 `UserMission`에는 생성 당시 연령대·성별·규칙 버전이 없다. 회원 정보나 마스터 규칙이 바뀐 뒤 교체 미션을 생성하면 최초 생성과 다른 기준이 적용될 수 있다.

다음 중 보존 범위를 정해야 한다.

- `UserGoal`에 생성 당시 `ageBand`, `sex` 저장
- `UserMission`에 기준 운동량·개수 배분·우선순위 규칙 버전 저장
- 별도의 생성 스냅샷 JSON 또는 생성 배치 ID 저장

`targetTotal`만 스냅샷하면 기존 미션의 분모는 보호되지만 다음 교체 미션의 생성 규칙은 보호되지 않는다.

### G04. 로테이션의 절대 위치

`slotGeneration`만으로는 §7-5의 중복 회피 때문에 실제 우선순위 위치를 항상 복원할 수 없다. 다른 슬롯과 충돌해 한 칸 더 이동한 경우 `slotGeneration`과 우선순위 인덱스가 달라진다. 운영 중 우선순위 목록이 바뀌어도 같은 문제가 생긴다.

결정이 필요하다.

- `priorityIndex` 또는 선택된 규칙 행 ID를 저장한다.
- 현재 `targetParam`을 목록에서 다시 찾아 다음 값을 정하고, 마스터 변경에 따른 결과 변화는 허용한다.

### G05. 직접 입력 문구의 목적 분류

`scheme.md`는 `goalPhraseId = null`인 직접 입력을 허용하고, `미션생성시스템.md`도 기타 입력을 룰 기반으로 분류한다고 적는다. 그러나 참조한 §10이 문서에 존재하지 않고 분류 규칙·실패 처리·신뢰도 기준이 없다.

목적을 결정하지 못하면 `UserGoal.purpose`를 채울 수 없고 미션 생성도 시작할 수 없다. 직접 입력을 출시 범위에서 뺄지, 분류 규칙과 폴백 목적을 정의할지 결정해야 한다.

### G06. 목표 삭제

`UserGoalStatus`에는 삭제 상태가 없고 삭제 시각도 없다. 반면 `운동목표문구.md` 본문은 목표와 미션 히스토리의 물리 삭제를 요구한다. 같은 문서의 주의 문구와 `scheme.md`는 삭제 정책을 미확정으로 둔다.

현재 상태에서는 삭제 API와 DB 동작을 구현할 수 없다. soft delete를 채택한다면 기존 `COMPLETED`·`CHANGED` 상태를 덮어쓰지 않는 `deletedAt` 계열 컬럼이 필요하다.

### G07. 종결 미션의 최종값 고정

`scheme.md`는 `REPLACED`·`CLOSED` 행을 보존하지만, `미션생성시스템.md`는 종결 후 과거 운동 기록이 수정될 때 최종 `numerator`·`rate`를 다시 계산할지 명시하지 않는다. 목표 히스토리를 당시 결과로 보여주려면 종결 행은 이후 재집계 대상에서 제외한다는 규칙이 필요하다.

## 3. `scheme.md`에만 있고 두 기획 문서에 근거가 없는 항목

아래 항목은 반드시 틀렸다는 뜻은 아니다. 현재 두 비교 문서만으로는 생성 시점·필수 여부·수정 정책을 결정할 수 없다는 뜻이다.

| 스키마 항목 | 문서에서 빠진 결정 |
|---|---|
| `UserGoal.reason` | 필수 여부, 최대 길이, 수정 가능 여부, 히스토리 노출 여부 |
| `UserGoal.plannedEndOn` | 입력 화면, 기간 선택 규칙, 변경 가능 여부, 리마인드와 완료 결과에서의 사용 방식 |
| `UserGoalAttendanceTime` | 요일·시각 입력 화면, 목표 변경 시 승계 여부, 캘린더 동기화, 시간대 변경 처리 |
| `UserGoal.phrase` 스냅샷 | 목표 마스터 문구 수정 시 기존 목표에 옛 문구를 유지할지 여부 |

특히 `plannedEndOn`은 미션 목표량과 달성률에 사용하지 않는다는 스키마 주석을 유지해야 한다. `미션생성시스템.md`는 미션에 기간 개념이 없다고 명시하므로 이 날짜로 `targetTotal`을 일할 계산하면 직접 충돌한다.

## 4. 기획 문서 내부 또는 두 문서 사이의 충돌

### D01. 객관식 전용과 기타 직접 입력

- `운동목표문구.md`: 8세그먼트별 5개 문구 중 1개 선택, 마스터 행으로 관리
- `미션생성시스템.md`: 문구 5종 또는 기타 작성, 기타는 룰 기반 목적 분류
- `scheme.md`: `goalPhraseId`가 `null`인 직접 입력 허용

현재 `scheme.md`는 미션 생성 문서 쪽을 따르지만 목표 문구 문서에는 기타 진입 경로가 없다.

### D02. 최초 생성 슬롯 수

- §1-1: 미션은 1~5개 가능
- §2: 최초 부여 시 슬롯 5개 전체 생성
- §7-1: 65세 미만 건강 목적은 총 4개

스키마는 슬롯 1~5를 허용하므로 어느 안도 저장할 수 있지만, 생성기가 목표마다 정확히 몇 행을 만들어야 하는지는 확정되지 않았다.

### D03. 삭제·불러오기 구판 잔존

`운동목표문구.md` §0-4와 §0-4-1은 삭제·불러오기를 정상 기능으로 설명하지만 바로 아래 주의 문구는 불러오기 제외 확정, 삭제 미확정이라고 정정한다. 구현자는 표가 아니라 주의 문구와 `scheme.md`를 따라야 한다. 본문 표와 히스토리 설명도 현재 결정에 맞춰 갱신해야 한다.

## 5. 먼저 결정할 순서

| 우선순위 | 결정 | 후속 작업 |
|---:|---|---|
| 1 | 유산소 강도 제거 확정 | 체력 목적 슬롯 배분과 유산소 목표량 표 재작성 |
| 2 | 65세 이상 균형과 생성 실패 폴백의 1차 범위 | `MissionMetricType` 확정 |
| 3 | `BODY_PART_VOLUME`의 1차 포함 여부 | kg 기준량·정규화·유형 선택 규칙 작성 |
| 4 | 기타 직접 입력 제공 여부 | `goalPhraseId` nullability와 목적 분류 규칙 확정 |
| 5 | 삭제를 soft delete로 할지 | `UserGoal` 삭제 컬럼과 히스토리 조회 조건 확정 |
| 6 | 생성 마스터를 `scheme.md`에 포함할지 | 목표 문구·기준량·개수·우선순위 테이블 작성 |
| 7 | 이유·종료 예정일·운동 예정 시간의 제품 요구사항 | nullable·길이·수정·승계 정책 확정 |

## 6. 이미 일치하는 핵심 규칙

혼선을 피하기 위해 수정할 필요가 없는 항목도 함께 고정한다.

- 목적은 다이어트·근력·건강·체력·자세 5종이다.
- 회원별 활성 목표는 최대 1개다.
- 목표 완료는 미션 달성률과 무관하게 사용자만 결정한다.
- 미션은 최대 5개이고 각 슬롯의 생애주기는 독립적이다.
- `targetTotal`은 부여 시점에 계산해 스냅샷으로 고정한다.
- 미션 하나가 게이지 하나이며 목표 종합 달성률은 만들지 않는다.
- 완료한 미션만 사용자가 교체하고 초과분은 새 미션으로 이월하지 않는다.
- 교체된 미션 행과 목표 변경·완료 시점의 미션 이력은 보존한다.
- 달성률 상한은 두지 않는다.
