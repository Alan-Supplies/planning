# 달성률 계산에 필요한 테이블 변경 명세

> 관련 작업 문서: [DB 구조 업그레이드 방안 — 섹션별](../DB_구조_업그레이드_방안_섹션별/README.md)

[목표 유형 5종](운동%20목표·운동%20기록%20개발%20회의%20문서.md) 각각을 계산하려면 어느 테이블에 무엇을 추가·변경해야 하는지를 컬럼 단위로 정리한 문서.

| 표기 | 의미 |
|---|---|
| **운영 실측** | 운영 DB `gymboxx` 조회 (2026-09-01) — 테이블 존재와 행 수 |
| **로컬 브랜치** | `gymboxx-lib` `feature/exercise-record-improvement` 엔티티 (TECH-998 머지 상태) — 컬럼 정의 |

운영 실측 행 수 — `exercise` 269 · `exercise_effect` **298** · `exercise_recommend_tag` 24 · `exercise_function` 87(구 테이블 잔존) · `exercise_body_part` 369 · `exercise_body_part_detail` 500 · `body_part` 8 · `body_part_detail` 21

## 요약 — 달성률 5종 × 어디에 무엇을

| 달성률 | 분자 원천 | 추가·변경할 것 | 상태 |
|---|---|---|---|
| 방문 횟수 | `access_history` | 없음 | 지금 계산 가능 |
| 근력 세션 | `user_exercise_session_history` → `exercise_effect` | 판정 규칙(주 효과 전용 여부) 확정 · 유산소 기구 5종 오분류 정정 | 데이터 298행 존재 |
| 유산소 분 | `user_exercise_set_history.count` → `exercise.cardio_intensity` | `cardio_intensity` **값** 부여(8종) · `count` 단위 판례 | 컬럼 존재 · 값 NULL |
| 부위 볼륨 | `user_exercise_set_history` → `exercise_body_part_detail` | **`contribution` 컬럼 신설** + 211종 재부여 | 컬럼 자체 없음 |
| 균형 세션 | `exercise_effect` | `exercise` 행 신규 등록 6~10종 | 종목 0건 |
| **(공통)** | — | **목표·주간 진행 테이블 5종 신설** | 전부 미존재 |

## 1. 부위 볼륨 — `exercise_body_part_detail.contribution` 신설

가장 큰 공백. 이 테이블에는 현재 `load_ratio float` 만 있고 기여도 척도 컬럼이 없다.

```sql
-- 대상: exercise_body_part_detail (운영 500행)
ALTER TABLE exercise_body_part_detail
  ADD COLUMN contribution enum('DIRECT','ASSIST') NULL
    COMMENT '부위 기여도 · 직접 1.0 / 보조 0.5'
  AFTER load_ratio;

-- 백필: 새 조사가 아니라 기존 load_ratio 의 2택 변환 (자동 208종 + 수동 3종)
UPDATE exercise_body_part_detail
   SET contribution = if(load_ratio >= <임계값>, 'DIRECT', 'ASSIST');

-- 검증 후
ALTER TABLE exercise_body_part_detail
  MODIFY contribution enum('DIRECT','ASSIST') NOT NULL;
```

- `load_ratio` 는 **삭제하지 않는다** — 원값이 있어야 3단계 척도 전환·사후 재산출이 가능 ([§6 부위 기여도](../DB_구조_업그레이드_방안_섹션별/06_부위_기여도.md))
- 운동별 `load_ratio` 합계 = 1.0 **제약을 폐기해야 한다** — 합계 1.0에 묶이면 데드리프트 둔근 0.1 로 주 4세트 목표 도달에 40세트가 필요해 등급 경계 영구 미달
- 상위 부위로 집계할 때 `body_part_detail.body_part_id` → `body_part` 조인에 **`axis='MUSCLE'` 조건 필수** — 유산소·스트레칭 2종이 부위 운동량에 섞이는 것을 막는 조건 ([§2 부위 라벨 축 구분](../DB_구조_업그레이드_방안_섹션별/02_부위_라벨_축_구분.md))
- 한 세트가 같은 부위의 세부부위 여러 곳에 기여하면 전부 합산 — 1세트가 1세트분을 초과할 수 있고, 단위 표기는 "세트분"으로 통일 (회의 문서 §5-6 확정 4)

## 2. 유산소 분 — 컬럼은 있고 값이 없다

`exercise.cardio_intensity enum('MODERATE','VIGOROUS') NULL` 은 [gymboxx-lib #263](https://github.com/suppliesfitness/gymboxx-lib/pull/263) 으로 신설됨. 필요한 것은 값 부여 마이그레이션.

```sql
-- 대상: exercise 중 measure_type='DURATION' 인 유산소 종목
-- 자동 매핑 근거: 기존 fatigue_level (≤3 중강도 / ≥4 고강도) — 회의 문서 §7-3-3
UPDATE exercise
   SET cardio_intensity = if(fatigue_level <= 3, 'MODERATE', 'VIGOROUS')
 WHERE measure_type = 'DURATION';   -- 트레이너 검수 후 확정
```

- `exercise.fatigue_level float` 이 실제로 존재하므로 자동 매핑의 근거 데이터는 있다 — 신규 조사 불필요
- 다만 트레드밀 런(고강도)/워크(중강도)처럼 같은 기구에서 강도가 갈리므로 **기구 단위가 아니라 종목 단위 검수**가 필요
- 검수 후보 8종 — 로잉 머신 · 버피 · 스텝밀 · 인클라인 트레드밀 · 일립티컬 머신 · 트레드밀 런 · 트레드밀 워크 · 점핑잭
- 값 부여의 선행 조건 — "유산소 주 효과 종목"의 정의(TECH-997 §6(나)) 확정. 정의 없이 값을 넣으면 계산 경로에 근거 없는 계수가 들어감 ([§3 유산소 강도](../DB_구조_업그레이드_방안_섹션별/03_유산소_강도.md))

### 선언되지 않은 문제 — `count` 의 단위

`user_exercise_set_history.count unsigned` 가 횟수와 시간을 겸용하는데 **시간일 때의 단위가 어디에도 선언되어 있지 않다.**

| 근거 | 값 |
|---|---|
| 회의 문서 §6-3 구조도 | `count (횟수 \| 초)` |
| `exercise.unit` 열거값 | `MINUTE` |

유산소 분 산식(`중강도 분 + 고강도 분 × 2`)의 분자가 60배 틀릴 수 있다. `measure_type` 판례집에 **`DURATION` 일 때 `count` 가 초인지 분인지** 명시해야 한다.

## 3. 근력 세션 — 데이터는 이미 운영에 있다

`exercise_effect`(`effect_tag` · `is_primary` · `status` · `active_key` 생성 열)는 TECH-997로 **운영 배포 완료 · 298행**. 계획서의 예상치(이관 63 + 근력 백필 225 ≈ 290)와 정합.

판정 경로 — `user_exercise_session_history.exercise_id` → `exercise_effect` 에서 `effect_tag='STRENGTH' AND status='ACTIVE'` 인 운동을 포함한 세션 수.

남은 것은 스키마가 아니라 **규칙과 데이터 정합** 두 가지.

| # | 남은 것 | 내용 |
|---|---|---|
| 1 | `is_primary` 조건 포함 여부 | 회의 문서는 "근력 성격 운동을 **포함한** 세션"이라 부가 효과도 포함으로 읽히나, 유산소 분은 반대로 주 효과만 세야 워킹 런지 20분이 유산소로 계상되지 않음 · 두 달성률이 같은 태그 테이블을 반대 규칙으로 읽으므로 명문화 필요 |
| 2 | 유산소 기구 5종 오분류 | 좌식 사이클 · 입식 사이클 · 스탭퍼 · 래더밀 · 핸드 바이크 는 `exercise_body_part` 매핑이 **아예 없어** 부위 라벨 기반 STRENGTH 자동 부여에서 **유산소인데 근력으로 붙는다** · 근력 세션은 과다 계상, 유산소 분은 누락 |

→ 2번은 `exercise_body_part` 에 매핑 행을 넣는 작업이며 부위 확정은 트레이너 판단.

## 4. 균형 세션 — 스키마가 아니라 마스터 데이터

종목 1건 등록에 필요한 값:

| 테이블 | 넣을 것 |
|---|---|
| `exercise` | 행 신설 · `measure_type='DURATION'`(한 발 서기 등) · `unit` · `has_weight=0` |
| `exercise_effect` | `effect_tag='BALANCE'` · `is_primary=1` |
| `exercise_body_part` | 없음 또는 코어 — 트레이너 판단 |

6~10종 등록이 목표 개방의 전제다. 종목 0건인 채로 목표를 노출하면 해당 회원(65세+ 169명)의 달성률이 영구 0%가 된다.

## 5. 방문 횟수 — 추가 없음

`access_history` 의 `user_id` · `created_at` · `type='ACCESS'` 로 계산된다. 하루 2회 방문도 1회이므로 일자 단위 중복 제거가 필요하다.

```sql
SELECT COUNT(DISTINCT DATE(CONVERT_TZ(created_at, '+00:00', '+09:00')))
  FROM access_history
 WHERE user_id = ? AND type = 'ACCESS'
   AND created_at >= ? AND created_at < ?;   -- 주 경계 (월요일 00:00 KST)
```

5종 중 유일하게 현재 스키마로 계산 가능하며, 그래서 목표 선택지에서 모든 목적의 기본 선택이 "주 3회 방문"이다.

---

## 6. 가장 큰 공백 — 목표·진행 테이블이 하나도 없다

`gymboxx-lib` 엔티티 전수 확인 결과 `goal`·`progress`·`weekly` 계열 테이블은 **0개**다 (`exercise_recommendation_goal_ratio` 는 추천 엔진용 목적 비율로 무관). 위 5종을 모두 정비해도 **달성률을 저장할 곳이 없다.**

회의 문서 §7-3-1이 "목표 테이블 5종 신설 — 전부 미존재"로 안건화한 부분이며 요구 스펙만 있는 상태.

| 필요한 것 | 담을 내용 |
|---|---|
| 목표 선택지 마스터 | 성별 × 연령 세그먼트별 동기 문구 · 행동 선택지 · 기본값과 범위(주 3회 / 2~7회) |
| 회원 활성 목표 | 동기 1 + 행동 1 · 지표 종류(5종) · 목표선 · 시작일 · 교체 이력 |
| 주간 진행 | 회원 목표 × 주 1행 · **목표선 스냅샷** · 실적 · 달성률 · 진행/확정 상태 · 확정 시각 · **부분 주 표식** |
| 실행 스케쥴 | 화·목·토 저녁 7시 (부가 지표 · 달성률 계산 대상 아님) |

주간 진행 테이블에서 **목표선 스냅샷과 부분 주 표식**이 특히 중요하다 — 회의 문서 §5-6 확정 2가 "주 중간 목표 생성 시 남은 일수 비율로 목표선 조정(목요일에 주 3회 생성 → 그 주는 2회 기준)"이므로, 목표선을 회원 목표에서 조인해 오면 그 주의 실제 기준을 잃는다.

## 7. 부수적으로 걸리는 것 — 세트에 수행 시각이 없다

`user_exercise_set_history` 는 PK가 `(user_exercise_session_history_id, set_number)` 자연키이고 **수행 시각 컬럼이 없다.** 달성률은 주 경계(월요일 00:00 KST)로 실적을 가르는데, 세트가 어느 주에 속하는지를 세션의 `started_at`/`end_at` 으로만 판단하게 된다.

회의 문서 §5-6 확정 3(자정에 걸친 세션도 예외 없이 미반영)이 이 한계를 정책으로 흡수한 것이고, [§10 세트 대리키·수행 시각](../DB_구조_업그레이드_방안_섹션별/10_세트_대리키_수행_시각.md)이 신규 기록부터 해결한다.

## 착수 순서

| 순위 | 작업 | 성격 |
|---|---|---|
| 1 | `contribution` 신설 + 211종 재부여 | 부위 볼륨은 컬럼이 없어 계산 자체가 불가 |
| 2 | 유산소 기구 5종 `exercise_body_part` 매핑 확정 | 근력·유산소 두 달성률을 동시에 오염시키는 중 · 트레이너 판단 |
| 3 | `cardio_intensity` 값 부여(8종 검수) + `count` 단위 판례 확정 | 트레이너 검수 대기 |
| 4 | 근력·유산소 판정에서 `is_primary` 적용 규칙 명문화 | 결정 사항 · 코드 이전에 문서 |
| 5 | 목표·진행 테이블 5종 스펙 확정 후 신설 | 스펙 미확정 |
| 6 | 균형 종목 6~10종 등록 | 트레이너 자문 |

순수 개발만으로 지금 진행 가능한 것은 1번의 DDL과 5번의 스펙 작성이다. 2·3·6은 트레이너 검수 대기, 4는 결정 대기.

| 항목 | 확인 방법 |

| PR 263 컬럼(`body_part.axis` · `exercise.measure_type` · `cardio_intensity`)의 **운영 배포 여부** | PR 263이 draft 상태이므로 미배포로 추정되나 운영 `information_schema` 조회로 확정 필요 |
| `exercise_effect` 298행의 `effect_tag`별 · `is_primary`별 분포 | 근력 종목 수와 주 효과 부여 완료 여부가 근력 세션 계산 가능성을 결정 |
| `exercise_body_part_detail` 500행 중 `load_ratio` 분포 | `contribution` 2택 변환의 임계값 결정 근거 |

> 운영 DB 접속 정보가 저장소에 평문으로 커밋되어 있다(`docs/ai/gymboxx.db.md` · `.vscode/settings.json`). 위 확인 작업 전에 계정 회수·로테이션과 추적 제외를 먼저 처리할 것.
