# 12. 개인 최고 기록 이력 테이블 신설

> [전체 목차](README.md) · [통합 원문](../DB_구조_업그레이드_방안.md)
>
> 2026-09-03 변경 — 기록 종류를 **참조 테이블에서 `record_kind` enum 으로** 뒤집는다(2026-08-21 결정 폐기) · 신설 테이블 2개 → 1개 · 상세 근거와 DDL: [최고 기록 종류 enum 변경 명세](최고기록_종류_enum_변경_명세.md)

기간 내 최고 기록 달성 수 산출과 랭킹 조회 경량화의 전제가 되는 이력 테이블을 신설하는 작업

## 무엇을 바꾸는가

회원×종목 단위로 최고 기록의 이력을 쌓는 테이블을 신설하고, 갱신할 때 기존 행을 고치지 않고 행을 추가한다.

부위별 최고 기록은 저장하지 않는다 — 부위 강도는 종목에 종속되므로 종목 단위 기록에 부위 매핑을 적용해 파생으로 계산한다(작업 원칙 3에 따름).

## 어떻게 바꾸는가

**기록 종류를 이력 테이블의 `record_kind` enum 으로 관리한다(2026-09-03 확정).** 종전의 "참조 테이블로 관리"(2026-08-21) 결정을 뒤집은 것이다.

1. 최고 기록 이력 테이블 1개만 신설 — 회원 · 종목 · `record_kind` enum · 기록 값 · 근거 세트의 무게·횟수·수행 시간 · 근거 세트 참조 · 달성 시각 · 근사값 여부

2. 표기명 · 단위 · 정렬 순서 · 유효 범위는 서버 상수가 단일 출처이며 메타 API 로 노출한다(유효 범위는 검증 전용 · 노출 안 함)

3. 갱신 시 이전 행의 `is_current` 를 0으로 내리고 새 행을 넣는다 · 현재 최고값은 `is_current` 로 구분한다. **부분 고유 제약(생성 열 `current_key`)은 보류다(2026-09-03)** — 아래 「현재값 1행 보장」 참조

4. 근거 세트 참조는 세트 대리키([10](10_세트_대리키_수행_시각.md))가 전제 — 자연키 복합 기본키를 참조하면 세트가 재삽입될 때 다른 기록을 가리킨다. **대리키는 이미 반영됐다.**

5. 과거 기록으로 초기 적재 — 기존 세트에서 회원×종목×종류별 최고값을 1건씩 생성

### 종류를 enum 으로 되돌린 근거

**enum 은 참조 테이블이 있어도 사라지지 않는다.** 서버는 종류마다 계산이 다르다 — 최고 중량은 `weight` 비교, 최고 반복 수는 `count` 비교, 단일 세트 최고 훈련량은 `weight × count` 비교다. 이 분기의 키가 코드 상수로 반드시 존재하므로, 참조 테이블을 두면 그 테이블의 `code` 컬럼과 서버 상수를 다시 대조하게 된다. 즉 참조 테이블은 enum 을 대체하는 선택지가 아니라 enum 위에 얹는 선택 레이어다. 얹을 이유가 생길 때 얹는다([아래](#나중에-참조-테이블이-필요해지는-조건)).

**성립 규칙은 플래그가 더 잘 담는다.** `personal_record_type.applies_to_measure` 는 enum 단일값이라 "무게도 있고 시간도 있는" 종목을 표현하지 못하고 AND 조건도 쓸 수 없다. 참조 테이블을 택한 가장 큰 근거가 이 항목이었으므로, 근거가 `exercise` 플래그 쪽으로 넘어갔다([04](04_측정_방식.md)).

**되돌릴 수 있는 결정이다.** 세트 이력이 전건 남아 있으므로 최고 기록 테이블은 파생 캐시다. 어느 형태를 골라도 세트에서 재계산해 다른 형태로 옮길 수 있다.

## `record_kind` 값과 성립 조건

|`record_kind`|표기명|단위|성립 조건|비교 대상|
|---|---|---|---|---|
|`MAX_WEIGHT`|최고 중량|kg|`has_weight = 1`|세트 `weight`|
|`MAX_REPS`|최고 반복 수|회|`has_reps = 1`|세트 `count`|
|`MAX_SET_VOLUME`|단일 세트 최고 훈련량|kg·회|`has_weight = 1 AND has_reps = 1`|세트 `weight × count`|
|`MAX_DURATION`|최장 지속 시간|초|`has_duration = 1`|세트 `duration_second`|

성립 조건은 **DB 가 강제하지 못한다.** MySQL CHECK 제약은 같은 행만 참조하므로 이력 테이블에서 `exercise` 의 플래그를 볼 수 없다. 서버 검증 + 주기 감사 쿼리로 막는다. **참조 테이블 안에서도 동일한 한계였다** — 외래키만으로는 "이 종목에 이 종류가 성립하는가"를 강제할 수 없다. 이 항목은 enum 전환의 손실이 아니다.

## 무엇이 선행이고 무엇이 선행이 아닌가

**기록 종류 목록 확정이 선행이 되었다.** enum 이므로 시작 값 목록이 곧 컬럼 정의다. 종전에 참조 테이블을 택한 이유가 이 선후 관계를 끊는 것이었으나, 목록이 위 4종으로 확정되어 선행 조건으로 되돌려도 막히지 않는다.

종류 추가 비용은 낮다 — MySQL 8 에서 enum 목록 **끝에** 값을 추가하는 것은 저장 크기가 바뀌지 않는 한(255개 이하 → 1바이트) 테이블 재구성 없이 INPLACE 로 끝나며, 행 수와 거의 무관하다.

### 🔴 enum 값 변경 규율 — 기존 값 이름은 바꾸지 않는다

비용이 연산별로 크게 갈린다.

|변경|MySQL 8 비용|
|---|---|
|목록 **끝에** 값 추가|INPLACE · 테이블 재구성 없음 · 행 수와 거의 무관|
|값 **이름 변경**|COPY · 전 행 재작성|
|값 **삭제**|COPY · 전 행 재작성|
|값 **순서 변경**|COPY · 전 행 재작성 · 게다가 할 이유가 없다(화면 정렬은 서버 상수의 `sortOrder` 소관이며 enum 순서와 무관)|

이 테이블은 회원 수에 비례해 계속 커지므로 비싼 쪽 비용이 시간이 갈수록 오른다. 따라서 **기존 값의 이름을 바꾸거나 삭제하지 않는다.** 의미가 달라지면 새 값을 목록 끝에 추가하고, 데이터를 옮기고, 옛 값은 쓰기를 멈추되 목록에 남겨 둔다. 이 순서를 지키면 COPY 를 영구히 회피할 수 있다.

값을 추가할 때 배포 순서는 **DB 먼저**다 — `ALTER` 가 나간 뒤 서버의 종류 상수를 배포한다. 코드가 먼저 나가면 DB 에 없는 값을 쓰려다 실패한다.

`varchar` + 서버 검증만으로 두는 선택지도 검토했으나 enum 을 유지했다 — 오타·쓰레기 값 유입을 DB 가 막아 주는 값어치가 크고(이 테이블이 랭킹·리포트·푸시의 근거다), `record_kind` 가 랭킹 인덱스에 들어가므로 1바이트 고정이 유리하다. 이름 변경 비용은 위 규율로 회피한다.

선행 1 — 기록 값을 담는 모양

|종류|값의 형태|단위|시작 enum 포함|
|---|---|---|---|
|최고 중량|숫자 1개|킬로그램|포함|
|최고 반복 수|숫자 1개|회|포함|
|단일 세트 최고 훈련량|숫자 1개|킬로그램·회|포함|
|최장 지속 시간|숫자 1개|초|포함|
|세션 최고 훈련량|숫자 1개|킬로그램·회|미포함 — 세트 1건이 근거가 아니므로 `source_set_id` 모양에 맞지 않음|

전부 숫자 하나 + 단위 형태다. 따라서 기록 값(숫자) + 단위(종류가 규정하는 메타) + 근거 세트 참조 + 달성 시각 구조로 두면 종류가 몇 개든 같은 모양에 들어간다.

선행 2 — **측정 방식 플래그([04](04_측정_방식.md))** · 어느 종류가 어느 종목에 성립하는지를 규칙으로 담으려면 종목별 플래그가 먼저 정해져 있어야 한다. 유산소 종목에 "최고 중량" 기록이 생기는 것을 막는 장치가 여기서 나온다. 강제 순서 §4 → §12.

선행 3 — 세트 대리키([10](10_세트_대리키_수행_시각.md)) · `source_set_id` 의 참조 대상. **이미 반영 완료.**

시작 종류 선정의 실측 근거 (세트 기록 301,572행 · 2026-08-21)

|항목|값|비율|
|---|---|---|
|무게가 0보다 큰 세트|288,798행|95.8%|
|횟수가 0보다 큰 세트|301,572행|100%|
|무게 없는 세트(횟수만 종목)|12,774행|4.2%|

최고 중량 · 최고 반복 수 · 단일 세트 최고 훈련량 3종에서 지금 있는 기록의 95% 이상이 기록을 만든다.

`MAX_DURATION` 도 시작 값에 포함한다. 종전에 제외한 근거는 "세트 테이블에 시간 컬럼이 아예 없음"이었으나 **`duration_second` 가 신설되어 그 근거가 소멸했다.**

## 무엇이 좋아지는가

**기간 내 최고 기록 달성 수를 목표로 쓸 수 있다** — 주간·월간 리포트의 "이번 달 달성한 최고 기록" 항목과 개인 최고 기록 갱신 목표가 이 테이블에 의존한다. 현재값만으로는 산출되지 않는 유일한 항목이며, 이력 테이블이 필요한 가장 강한 근거다.

랭킹 조회가 가벼워진다 — 종목별 순위를 낼 때마다 29만 건의 세트를 스캔하는 대신 회원별 최고값만 읽으면 된다. 모집단 4.5만 명 규모에서 응답 시간 차이가 크다.

오염 기록을 사후에 무효화할 수 있다 — 맨몸 종목에 무게가 들어온 세트처럼 잘못된 기록이 최고 기록을 만든 경우, 근거 세트 참조가 있으면 그 최고 기록만 골라 무효 처리할 수 있다. 참조가 없으면 전량 재계산이 유일한 방법이다.

기준 변경에 강하다 — 추정 최대 중량의 계산식이나 반복 수 상한이 바뀌어도 근거 세트의 무게·반복 수가 남아 있으므로 이력을 다시 만들 수 있다.

표기명 배포 경로가 짧아진다 — 표기명 오타 하나를 고치는 데 프론트는 앱 심사와 사용자 업데이트가 걸리지만, 서버 상수는 배포 한 번으로 끝나며 구버전 앱에도 즉시 반영된다. 참조 테이블을 없애면서 잃는 "런타임 조정 가능"이 여기서 대부분 회복된다.

## 초기 적재

|단계|내용|
|---|---|
|대상|`user_exercise_set_history` 전건에서 회원×종목×종류별 최고값 1건씩|
|`achieved_at`|`done_at` 이 있으면 그 값 · 없으면 소속 세션의 `started_at` 으로 근사하고 `is_approximate = 1`|
|`source_set_id`|근거 세트의 `id` — 세트 대리키가 이미 있으므로 초기 적재분도 채운다(종전 안은 NULL 이었으나 전제가 바뀌었다)|
|`is_current`|전부 1 — 초기 적재는 종류별 1건뿐|

**개발 DB `done_at` 이 0건이므로 사실상 전건이 근사값이 된다.** 클라이언트가 이 값을 전송하기 시작한 뒤에 적재하면 근사 비율이 줄어든다. 적재 시점 선택이 데이터 품질에 직접 영향을 준다.

## 나중에 참조 테이블이 필요해지는 조건

아래 중 하나라도 성립하면 그때 얹는다. 지금은 하나도 성립하지 않는다.

|조건|왜 그때는 필요한가|
|---|---|
|종류가 10종을 넘음|서버 상수 목록이 코드 리뷰로 관리하기 어려워지는 규모|
|유효 범위를 운영에서 조정해야 함|배포 없이 값을 바꿔야 하면 DB 가 답|
|트레이너·기획이 종류를 직접 등록|어드민 화면이 붙으려면 행이어야 함|

마이그레이션 경로 — `personal_record_type` 을 신설하고 `code` 에 enum 값을 그대로 적재한 뒤, 이력 테이블에 `record_type_id` 를 추가해 병행 운영하다 전환한다. `record_kind` enum 은 서버 분기 키로 남으므로 제거하지 않는다. 이력 데이터를 재적재할 필요가 없는 경로다.

## 주의

- 🔴 **현재값 1행 보장이 없다.** `is_current` 는 랭킹 조회 경량화를 위한 비정규화이고 읽는 쪽은 "(회원, 운동, 종류) 당 현재값 1행" 을 가정하지만, 그것을 강제하는 DB 제약을 이번 범위에서 넣지 않았다. 갱신 순서("선 강등, 후 삽입")를 어기면 실패하지 않고 조용히 2행이 된다 — 랭킹이 그 회원을 중복 계상하고 "현재 최고값" 의 답이 없어진다.

  이 테이블은 행 0개로 시작하고 이번 범위에서 아무도 쓰지 않으므로 지금 오염될 일은 없다. **app-server 가 쓰기를 시작하기 전에 제약을 넣는 편이 훨씬 싸다** — 쓴 뒤에 넣으면 이미 오염된 행 때문에 제약 생성이 실패할 수 있고, 순서를 틀린 코드가 그때부터 `errno 1062` 로 실패하기 시작한다. 넣는 절차(위반 행 확인 → 생성 열 + 제약 추가 → 랭킹 인덱스 교체)는 `V4_31_5__user_personal_record_history.sql` 에 적어 뒀다.

  app-server 의 세션 행 배타 잠금(TECH-1231)에 기대면 안 된다 — 그 잠금은 세트 전량 삭제·재삽입의 갭 락 데드락 대책이고, 최고 기록 키는 세션을 넘으므로(같은 회원·같은 종목이라도 세션이 다르면 잠기는 행이 다르다) 애초에 그 잠금이 닿지 않는다.

- 갱신 방식을 수정으로 하면 목적이 사라진다 — 다만 **정체 구간은 현재값만으로도 계산된다**(현재 최고값과 그 달성 시각이 있으면 "몇 주째 미갱신"이 나온다). 이력이 실제로 필요한 것은 **기간 내에 달성한 최고 기록 수**이며, 이쪽은 현재값만으로는 산출되지 않는다.

- `MAX_REPS` 적재에 오염 위험이 있다 — `count` 주석대로 **과거 행에는 초값이 그대로 남아 있어서**, `unit='MINUTE'` 종목의 과거 세트를 그대로 넣으면 "60초"가 "60회" 최고 기록으로 들어간다. 적재 쿼리에서 `has_reps = 1` 이 아니라 `has_duration = 0 AND has_reps = 1` 조건으로 걸러야 하고, 두 플래그가 모두 1인 종목은 과거 행을 아예 제외한다.

- 값이 종류에 맞는지 DB 가 보장하지 못한다 — 값 모양을 일반화했으므로 "최고 반복 수" 기록에 무게 값이 들어가도 숫자로는 유효하다. 서버 상수의 단위·유효 범위를 근거로 서버가 검증해야 한다. **참조 테이블 안에서도 같았던 한계다.**

- 추정 최대 중량은 파생값이므로 계산식과 함께 기록한다 — 어떤 규칙으로 만든 값인지 남기지 않으면 규칙 변경 후 과거 값과 비교가 불가능하다.

- 초기 적재분의 달성 시각은 근사값이며 `is_approximate` 로 구분한다.

- 감사 쿼리로 성립하지 않는 종류를 검출한다.

```sql
SELECT r.id, r.exercise_id, r.record_kind
  FROM user_personal_record_history r
  JOIN exercise e ON e.id = r.exercise_id
 WHERE (r.record_kind = 'MAX_WEIGHT'     AND e.has_weight = 0)
    OR (r.record_kind = 'MAX_REPS'       AND e.has_reps = 0)
    OR (r.record_kind = 'MAX_SET_VOLUME' AND (e.has_weight = 0 OR e.has_reps = 0))
    OR (r.record_kind = 'MAX_DURATION'   AND e.has_duration = 0);
```
