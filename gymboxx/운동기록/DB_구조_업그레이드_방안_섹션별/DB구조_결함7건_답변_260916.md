## 1. `equipment_type` — 완료 (단, 12종이 아니라 11종)

### 적용 결과 (운영 실측)

```text
enum('MACHINE','SMITH','CABLE','CARDIO','BARBELL','DUMBBELL',
     'KETTLEBELL','BAND','STRUCTURE','BODYWEIGHT','PROP')

DUMBBELL 55 · MACHINE 45 · BODYWEIGHT 41 · BARBELL 31 · CABLE 28
STRUCTURE 15 · SMITH 12 · PROP 11 · CARDIO 11 · BAND 10 · KETTLEBELL 6 · (NULL) 9
```

머신 68종 전건 NULL → **NULL 9종**(그중 `ACTIVE` 는 1종)으로 줄었다. 실사용 0건이던 `SMITH`·`CARDIO` 도 채워졌다.

### 계획안(12종)과 달라진 점 — `PIN`·`PLATE_LOADED` 를 `MACHINE` 하나로 합쳤다

핀/플레이트 구분을 종목 컬럼에 두는 것은 **성립하지 않는다**는 결론이다. 근거는 두 가지다.

- **같은 운동이 지점에 따라 둘 다다.** 자동 부여 대상 45종 중 **31종(69%)이 핀 머신과 플레이트 머신 양쪽에 연결**되어 있다. `exercise` 1행당 단일 열거값으로는 표현할 수 없는 사실이다.
- **다수결로 채운 값은 사실이 아니다.** 그 값으로 지점 가능 운동을 판정하면 틀린 답이 나온다 — 핀 머신만 있는 지점에서 '플레이트' 로 적힌 운동이 불가능으로 빠진다.

`SMITH`·`CARDIO` 는 반대로 기구 마스터와 **100% 일치**해서 그대로 분리했다 (`CARDIO` 11종은 연결 기구 전건 `machine.type='CARDIO'`, `SMITH` 12종은 전건 `type_detail='SMITH'`).

### 지적된 문제점별 대응

|문제점|대응|
|---|---|
|1. 머신 68종 미착수|해소 — 45종 `MACHINE` · 12종 `SMITH` · 11종 `CARDIO`|
|2. 유산소 기구와 근력 머신 분리 불가|해소 — `CARDIO` 11종이 분리됨. 장비·단위 2컬럼 동시 참조 불필요|
|3. 지점 기구 인벤토리 매칭 불가|**종목 컬럼으로는 못 푼다** — 정본 경로는 `exercise_machine → machine → gym_machine`. 남은 일은 구조물 12종의 `exercise_machine` 매핑 작성 하나이며, 그것만 하면 지점 판정이 성립한다(새 테이블 불필요)|
|4. 장비 선호 분포 29% 결손|해소 — 결손이 `ACTIVE` 1종으로 줄어 유사 회원 비교가 성립|
|5. 기구 프리필 유효 범위 미정의|**남음** — 프리필을 켜는 조건 컬럼은 여전히 없음. 별건|

### 남은 것

- id 171 인버티드 로우 — 기구 미연결 `ACTIVE` 1종. `MACHINE` 유지 vs `STRUCTURE` 재분류 미결
- 미연결 `INACTIVE` 8종 — 정상 NULL 로 두는 방침. `NOT NULL` 전환은 이 8종 처리 후
- `gymboxx-lib` enum·엔티티·마이그레이션 반영 (`V4_31_7` 은 구 12종 표기라 다시 씀)

## 2. `contribution` — 완료

### 적용 결과 (운영 실측)

```text
contribution enum('DIRECT','ASSIST') NOT NULL DEFAULT 'ASSIST'

DIRECT 268행 / ACTIVE 514행 / 248종
DIRECT 1개 230종 · 2개 16종 · 3개 2종   (DIRECT 0개인 운동 0종)
```

판정 기준은 계획안대로 **그 운동 `ACTIVE` 행의 `load_ratio` 최댓값 대비 60% 이상**이다. `load_ratio` 원값은 지우지 않았다.

### 지적된 문제점별 대응

|문제점|대응|
|---|---|
|1. 「부위별 운동량」 분모·분자 단위 불일치|해소 — `DIRECT` 행을 세트 단위로 세면 목표선("세부부위당 주 4세트")과 같은 단위가 됨|
|2. 기여도가 등록 부위 수에 종속|해소 — 합계 1.0 제약을 받는 `load_ratio` 대신 상대 기준으로 판정. 부위를 5개 등록해도 주 부위가 사라지지 않음|
|3. 다관절 운동 역전|해소 — 상대 기준이라 최댓값 자체가 낮은 운동도 주 부위가 잡힘. 절대 0.5 기준이었으면 5부위 운동은 전건 보조가 됐다|
|4. 부위 불균형 리포트 오진단|해소 방향 — 세트 수 순위와 가중 순위가 갈리던 원인이 분배율이었음. 판정의 정본이 컬럼으로 옮겨감|

### 남은 것 (2건, 그중 1건은 지금 값이 틀린 실버그)

- **검수 18종** — `DIRECT` 가 2개 이상 잡힌 종목. 60% 기준과 "최댓값만" 기준이 갈리는 전부가 여기 있고, 이 목록만 보면 검수가 닫힌다. 다관절 운동은 `DIRECT` 복수가 정상이라 전부 고칠 대상은 아니다
- 🔴 **`gymboxx-app-server` `ExerciseRecommendationDAO.getAllActiveExercises`** 의 `exercise_body_part_detail` relation 에 `status='ACTIVE'` 필터가 없다. INACTIVE 이력 행이 보조근 점수에 섞인다 — `contribution` 과 무관하게 **지금 틀린 값을 내고 있는 버그**
- `SecondaryMuscleScorer` 를 `ASSIST` 만 보게 바꾸는 건 추천 점수 분포가 바뀌므로 회귀 검증을 붙여 별건
- `replaceBodyPartDetails` 가 `contribution` 을 함께 쓰도록 수정 + "ACTIVE 행 중 `DIRECT` 최소 1개" 서버 검증

## 3. 부위 매핑 고유 제약 · 대리키 — 진행하지 않았다 (의도)

### 이유

**제약을 걸어도 그것을 쓰는 경로가 실제로 없다.** 이 항목이 여는 것은 "같은 조합을 비활성 처리한 뒤 다시 넣는" 정정 이력 보존인데, 운영에서 그 작업이 일어나지 않는다. 분류 수정은 기존 행을 덮어쓰는 방식으로 처리되고 있고, 그래서 `exercise_body_part_detail` 514행이 전건 `ACTIVE` 다. 대리키로 이관해도 **쓰는 쪽이 생기기 전까지는 스키마만 바뀌고 동작은 그대로**다.

중복 차단 쪽도 지금 당장 막는 값이 없다 — 중복 **0건**이며, 계획 문서도 이 항목을 "예방 목적·우선순위 후속"으로 분류하고 있다.

### 현재 상태 (실측)

```text
exercise_body_part          PK = id (대리키 이미 있음) · UNIQUE 0개 · ACTIVE 286 / INACTIVE 90
exercise_body_part_detail   PK = (exercise_id, body_part_detail_id) 복합 자연키 · 514행 전건 ACTIVE
```

`exercise_body_part` 는 대리키가 이미 있어 남은 것은 부분 고유 제약 하나다. 세부부위 쪽이 기본키 이관이 필요한 쪽이다.

### 재개 조건

- 비활성 90행을 되살리는 정정 작업이 실제로 계획될 때 (그 순간 같은 조합 2행이 성립하고 DB가 막지 않는다)
- 또는 분류 정정 이력을 리포트 근거로 쓰기로 결정될 때

그 전까지는 **이중 계상 방어를 집계 쿼리의 중복 제거로 유지**한다. 이게 이 결정의 비용이며, 집계 쿼리를 새로 쓸 때 중복 제거를 빠뜨리면 조용히 틀린다는 위험은 그대로 남는다.

## 4. 측정 방식 — 부분

플래그 3종(`has_weight`·`has_duration`·`has_reps`)은 **운영에 이미 존재한다**. 계획안의 `exercise_measurement` 매핑 테이블 신설과 `measure_type` enum 은 2026-09-03 에 폐기하고 플래그로 대체하기로 확정했다 — enum 단일값은 "무게도 있고 시간도 있는" 종목(웨이티드 플랭크)을 표현하지 못하고 성립 조건을 AND 로 못 쓴다.

남은 것은 구조가 아니라 **연결**이다.

- 서버 입력 검증이 플래그를 참조하지 않음 — `has_weight=0` 종목의 무게 유입이 1,621건에서 4,505건으로 늘어난 원인
- `count` 의미 이원화 — 시간 종목의 초 값이 `count` 와 `duration_second` 에 중복 저장. 유산소 세트 17%는 `duration_second` NULL 이고 `count` 에만 초 값 보유
- 필수·선택 구분은 플래그로 표현 불가 — 필요해지면 그때 매핑 테이블을 얹는다
- 거리 항목은 제외 확정 (해당 종목 0건)

착수 전제는 **트레이너 검수**다.

## 5. 운동 성격 판정 근거 이중화 — 착수 (정정안 작성 완료)

**효과 축(`exercise_effect`)의 값 33종이 틀렸다. 그것부터 고친다.** 어느 컬럼을 성격 판정의 정본으로 쓸지는 아직 열린 결정이다 — [달성률/이슈검토.md](../달성률/이슈검토.md) 우선순위 2 §12 에 「성격 축 정본 — `training_type` 컬럼인가 부위 라벨 파생인가」가 미결로 등재되어 있고, [미션/specification.md](../달성률/미션/specification.md) **R38** 은 이미 "유산소 판정의 정본은 `exercise.training_type` 이다" 로 채택했다.

반대로 계획안(TECH-602)의 "성격은 저장 안 하고 파생" 근거 두 개는 실측으로 반박되어 있다 — 파생이 주장한 근력 253종이 실측 212/216 과 어긋나고([이슈검토 §16](../달성률/이슈검토.md)), "효과 축 `MOBILITY` 에 스트레칭 0종"도 사실과 다르다(7종 전량 태깅 · §17).

정본이 어느 쪽으로 정해지든 **효과 축 33종은 틀린 값이다.** 효과 축은 성격 판정에 쓰이지 않더라도 「효과 — 세션 수」 미션 유형(균형·순발력)의 원천이고, 이슈검토도 같은 건을 "균형은 오분류 8종뿐(중대 5)"으로 지목하고 있다. 그래서 정본 결정을 기다리지 않고 값부터 고친다.

### 불일치는 27종이 아니라 33종

|그룹|내용|종수|
|---|---|---|
|A|`MUSCLE` 인데 주 효과 `ENDURANCE` — 맨몸 스쿼트·런지·푸시업류|11|
|B|`MUSCLE` 인데 주 효과 `MOBILITY` — 머신·케이블·밴드 저항 운동|7|
|C|`MUSCLE` 인데 주 효과 `BALANCE` — 플랭크·단측 하체|8|
|D·E|주 효과 `PLYOMETRIC` — 스플릿 점프 투 박스 · 버피 · 점핑잭|3|
|F|**`MOBILITY` 인데 주 효과 `STRENGTH`** — 스트레칭 3종이 근력 세션으로 계상 중. 27종 집계에 없던 건|3|
|G|**효과 축 행이 0개인 `ACTIVE` 종목** — `274 케이블 닐링 크런치`. 효과 축을 정본으로 쓰면 모든 지표에서 사라짐|1|

`training_type` enum 도 실제로는 `enum('MUSCLE','CARDIO','MOBILITY')` 다(`STRETCHING` 아님).

### 적용 후 달라지는 값 (2026-08 세션)

|지표|현재|적용 후|
|---|---|---|
|근력 세션 수|15,958|**16,001**|
|유산소 세션 수|3,858|**3,680**|
|균형 세션 수|608|**0** — 목표 닫힘|

적용 후 효과 축 기준과 `training_type` 기준이 완전히 일치한다. "한쪽을 지워도 된다"가 아니라 **두 컬럼이 더 이상 다른 답을 내지 않는다**는 뜻이다 — 그 상태가 되어야 정본 결정(§12)을 어느 쪽으로 내려도 지표가 안 움직인다.

🔴 **균형 세션 수가 0이 된다.** C 8종이 전부 근력 운동이었기 때문이다. [14번 문서](14_선택_변경된_사항.md)의 "주 효과만 채택 · 신규 균형 종목 4~6종 등록 후 개방" 결정과 정합하며, 개방 전제인 신규 종목 등록은 아직 0건이다.

🔴 **리포트·달성률에 이미 노출된 값이 있으면 적용 전후로 수치가 바뀐다.** 회원 노출 지표라면 공지 또는 적용 시점 표시가 선행이다.

산출물 — [성격판정_이중화_해소.md](성격판정_이중화_해소.md)(33종 판정 근거) · [성격판정_이중화_적용.probe](성격판정_이중화_적용.probe)(사전점검·적용·검증·롤백)

### 남은 순서

1. 효과 축 33종 정정 — 개발 적용 → 검증 → 운영
2. 서버 검증 추가 — "ACTIVE 종목은 주 효과 정확히 1개 · `PLYOMETRIC` 은 주 효과로 쓰지 않는다"
3. **성격 축 정본 결정** ([이슈검토 §12](../달성률/이슈검토.md)) — 1이 끝나면 어느 쪽을 골라도 지표가 안 움직인다
4. 정본 아닌 쪽의 처리(유지 / 조회 뷰 / 폐기) — 착수 전제는 `training_type` · `exercise_function` 참조 지점 전수 조사([13-3](13_실행_순서와_의존_관계.md))
5. 균형 종목 4~6종 신규 등록 — 균형 목표 개방의 짝

**파생을 정본으로 고를 경우에만** 선행 조건이 하나 더 붙는다 — F 3종(스트레칭)의 부위가 `SHOULDER`(근육 축)로 등록되어 있어 "근육 부위 보유 = 근력" 파생 규칙이 오판한다. `STRETCHING` 으로 옮기는 작업이 먼저다. `training_type` 을 정본으로 고르면 불필요하다.

## 6·7. 감사 컬럼 — 미진행

### 6. 신설 테이블

```text
user_exercise_metadata           user_id · level · purpose          → 시각 컬럼 0개
user_exercise_session_body_part  user_exercise_session_id · body_part_id → 시각 컬럼 0개
```

지적에 동의한다. 지금 추가해도 과거 변경 시점은 복원되지 않지만, **오늘 넣지 않으면 오늘 이후도 못 본다**("수집 컬럼은 먼저 열고 강제는 나중에" 원칙). 스키마 변경 1건씩이라 비용이 작다 — 다음 마이그레이션에 넣는 것을 제안한다.

### 7. `user_exercise_set_history`

```text
전체 497,791행 · created_at NULL 459,985 (92.4%) · updated_at NULL 497,791 (전건)
```

- **`created_at` 백필은 하지 않는 편이 맞다.** 과거 세트의 저장 시각을 알 원천이 없고, 상위 세션 `created_at` 으로 근사하면 추정치가 원천 테이블에 실측처럼 들어간다 — 작업 원칙 3(파생은 저장하지 않고 원천 보관) 위반이고, 세트 간 휴식 분석이 보간으로 만든 균등 간격을 실제 패턴으로 오해한다. **백필 대신 "시각 기반 분석은 2026-09-11 이후 표본"이라고 리포트에 명시**하는 쪽을 제안한다.
- **`updated_at` 은 별건이고 지금 해야 한다.** 전건 NULL 인 이유는 컬럼이 채워질 저장 경로가 없어서다. §10의 실질이 "삭제 후 재삽입 → 갱신 방식 전환"이었는데 그 전환이 안 되어 있으면 시각 컬럼이 있어도 값이 매 저장마다 재작성된다. **저장 방식 전환이 선행**이고, 그게 끝나야 세트 수정 추적이 성립한다.
