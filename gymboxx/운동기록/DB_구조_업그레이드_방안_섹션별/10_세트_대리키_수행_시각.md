# 10. 세트 테이블에 대리키·수행 시각 추가

> [전체 목차](README.md) · [통합 원문](../DB_구조_업그레이드_방안.md)

세트에 안정된 식별자와 수행 시각을 부여해 시간 흐름 분석을 여는 작업

## 무엇을 바꾸는가

세트 테이블에 대리키와 세트 수행 시각을 추가하고, 저장 방식을 삭제 후 재삽입에서 갱신 방식으로 전환

현행 세트 테이블 — 컬럼 4개(운동 기록 식별자 · 세트 번호 · 횟수 · 무게) · 기본키가 자연키 복합(운동 기록 식별자 + 세트 번호) · 시각 컬럼 없음 · 301,572 행(2026-08-21 실측 · 문서 최초 작성 시점 296,176행에서 증가)

## 어떻게 바꾸는가

1. 대리키 추가 후 기본키 이관 — 기존 자연키 복합 기본키는 고유 제약으로 유지

2. 세트 수행 시각 컬럼 추가 — 회원이 그 세트를 마친 시각 · 클라이언트가 전달

3. 기록 저장 시각·수정 시각 추가 — 서버 기준

4. 저장 방식 전환 — 현재는 세트를 고칠 때 해당 운동의 세트를 전부 지우고 다시 넣는 방식이라 시각이 매번 재작성됨 · 갱신 방식으로 바꾸지 않으면 시각 컬럼을 추가해도 값이 무의미

5. 세트 시작 시각은 후속 — 타이머 화면이 준비될 때 추가

전환 범위 확정(2026-08-21) — 두 항목의 적용 범위를 다르게 둠

|항목|적용 범위|근거|
|---|---|---|
|대리키 부여|전건(301,572행)|값 자체에 의미가 없어 소급 부여가 안전·최고 기록의 근거 세트 참조가 과거 기록에도 필요|
|수행 시각|신규 기록만·과거는 빈 값 유지|과거 세트의 실제 수행 시각을 알 근거가 없음|
|저장 방식(갱신 전환)|신규 기록만|과거 기록을 갱신 방식으로 소급 전환할 대상이 없음|

과거 기록에 시각을 채우지 않는 이유 — 세션의 시작·종료 시각으로 보간하면 추정치가 원천 테이블에 실측값처럼 들어감 · 그러면 세트 간 휴식 분석이 보간 으로 만들어낸 균등 간격을 실제 휴식 패턴으로 오해 · 작업 원칙 3(파생 지표는 저장하지 않고 원천을 보관)에 정면으로 어긋남 수행 시각과 저장 시각을 나누는 이유 — 휴식 시간 분석은 회원이 실제로 세트를 마친 시각이 필요함 · 저장 시각은 화면을 벗어날 때 한꺼번에 기록될 수 있 어 세트 간 간격을 나타내지 못함

## 무엇이 좋아지는가

세트 간 휴식 시간을 산출할 수 있음 — 다음 세트 수행 시각에서 이전 세트 수행 시각을 빼면 휴식 간격이 나옴 · 지금은 세트에 시각이 전혀 없어 이 분석이 원천적으로 불가능하고, 운동 단위 시각만으로는 세트 간격을 알 수 없음 세션 내 시간 흐름 분석이 열림 — 운동 효율성 리포트(시간당 훈련량·준비 대기 시간·운동이 길어지는 원인)와 수행 품질 리포트(세트 후반 지연)가 이 값에 의존

개인 최고 기록의 근거를 참조할 수 있음 — 현재 기본키가 자연키 복합이라 같은 (운동, 세트 번호)가 다른 값으로 재삽입되면 참조가 다른 기록을 가리킴 · 대 리키가 있으면 "이 최고 기록은 이 세트에서 나왔다"를 안정적으로 남길 수 있고, 나중에 오염 기록이 발견되면 그 최고 기록만 무효화 가능 세트 수정 이력이 보존됨 — 삭제 후 재삽입 방식은 회원이 무게를 고칠 때 이전 값을 지움 · 갱신 방식으로 바꾸면 수정 시각이 남아 비정상 입력 패턴을 탐지 할 수 있음

## 주의

- 저장 방식 전환이 이 항목의 실질 — 컬럼만 추가하고 저장 방식을 그대로 두면 시각 값이 매 저장마다 갱신되어 분석에 쓸 수 없음 과거 기록에는 수행 시각을 소급 채울 수 없음 · 운동 단위 생성 시각으로 근사하면 세트 간격이 모두 0이 되므로 비워 두고 분석 대상 기간을 이후로 한정 시각 기반 분석의 표본이 전환 시점 이후로 한정됨 — 초기 몇 개월은 세트 간 휴식·세션 내 시간 흐름 분석의 표본이 부족함 · 리포트에 수집 시작 시점을 반드시 표시해야 하고, 표시하지 않으면 휴식 시간 평균이 전체 기간 평균으로 오해됨 대리키 추가 시 기존 자연키 조합을 고유 제약으로 남겨야 함 · 같은 운동에 같은 세트 번호가 두 번 들어오는 것은 여전히 차단 대상
