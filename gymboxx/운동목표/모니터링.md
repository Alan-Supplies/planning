# 운동목표 사용 현황 모니터링

운동목표(habit-OS) 배포 후 회원이 얼마나 잘 쓰는지 주기적으로 본다. 오류 감시가 아니라 사용 지표다.

## 방식

- Metabase 대시보드 하나 + 대시보드 구독(슬랙/이메일, 매일 또는 매주).
- 봇을 만들지 않는다. 운영 DB 접속 경로를 새로 열 필요가 없고, 끝나면 구독만 끈다.
- 쿼리는 읽기 전용 운영 DB 에서 숫자를 검증한 뒤 Metabase 질문으로 옮긴다.
- 해석이 필요할 때만 Claude 에게 묻는다. 정기 요약까지 필요해지면 그때 Metabase API 로 읽는 방식을 검토한다.

## 지표 정의

공통: `user_goal.started_at >= '2026-10-19'` 인 목표만 본다(10/17~18 은 내부 테스트). 날짜는 KST.
최소 기간(5주)이 지나기 전이라 목표 수보다 **회원 수**를 기준으로 본다.

| 지표 | 원천 · 정의 |
|---|---|
| 일별 신규 목표 회원 수 | 회원별 첫 목표의 `user_goal.started_at` 일자로 센다. 같은 회원이 종료·재생성해도 한 번만 |
| 진행 중 목표 보유 회원 수 | `user_goal.status = 'IN_PROGRESS'` |
| 목표 종료 구분(완료·종료·삭제) | `user_goal.status` |
| 미션 진행률 분포(근력 부위·유산소·스트레칭별) | `user_mission.current_value / target_value`, `round` |
| 목표 보유자 중 주간 운동 기록 비율 | `user_exercise_session` 중 **종료된 세션(`end_at IS NOT NULL`, `is_deleted = 0`) + 세트 1개 이상**(`user_exercise_set_history`). 시각은 `COALESCE(started_at, created_at)` — 미션 집계와 같은 기준 |
| 목표 보유자 중 주간 출석 비율 | `access_history.type = 'ACCESS'` |

### 참고: 세션 시작 시각이 출석 시각과 같은 경우 (2026-10-20 확인)

- 일반 흐름은 운동 시작 시각을 출석과 따로 찍는다.
- 앱 2.4.0 의 "출석만 한 날에 운동 뒤늦게 추가" 흐름(`supplies-apps` `useBackfillEmptyDay.ts`)은
  `started_at` 을 **그날 출석 시각**으로 의도적으로 고정한다. 타이머를 안 맞추면 `end_at` 도 출석 시각이다.
- 운영 실측(10/17~10/20 생성 세션, 운영 DB): 2.4.0 세션 145건 중 60건이 `started_at = 출석 시각`, 46건이 `end_at = started_at`.
  2.3.x 는 10,689건 중 4건.
- 영향: 출석 → 목표 생성 → 뒤늦게 운동 추가 순서면 세션 시각이 미션 `assigned_at` 보다 앞서 미션에 잡히지 않는다.
  10/20 11:50 기준 목표 보유자 5명, 104세트가 이 경우다. 정책 결정 필요(아래 "정할 것").

## 정할 것

- 미션 지표를 분포로 볼지, "미션 진척 회원 수"로 볼지
- 주기(매일/매주)
- 받는 곳: 일단 test 채널에서 받는다. (private 채널) id: C08USFT0YDU
- 기준 시점: `started_at >= 2026-10-19` 로 정함. 최근 N주 창을 따로 둘지
- 내부 테스트 계정 제외 기준 (10/19 이후에도 397029 · 384014 남음)
- 뒤늦게 추가한 운동(출석 시각 고정)을 목표 생성 전 세션으로 볼지 — 미션 기산점 정책.
  개발 제안은 2안(그날 출석 시각으로 기산점 당김), PO 결정 대기: TECH-3098
