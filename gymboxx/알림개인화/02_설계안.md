# 알림 개인화 설계안

작성: 2026-10-07
상태: 초안. 구현 전에 [README](README.md)의 결정 항목을 먼저 정한다.

10/8 갱신: [개편 착수 계획](00_개편_착수계획.md)에 Slack 논의와 Linear의 10/7 기획 요구를 추가했다. 이 문서의 카테고리 후보·새 테이블은 기술 제안이며, 최신 기획의 3종 동의·기존 토글 유지 요구와 대조해 확정해야 한다. 특히 동의 컬럼 매핑·기존 회원 승계·수신 시간대와 디스패처의 이번 구현 포함 여부를 확인한다.

## 1. 목표

- 회원이 알림을 카테고리 단위로 켜고 끈다.
- 회원이 받지 않을 시간대를 정한다.
- 모든 발송이 같은 규칙으로 판정되고, 판정 결과가 남는다.

## 2. 카테고리

```
전체 알림                         ← 기존 app_push_agreement
├─ 서비스 알림   (끌 수 없음?)     결제·멤버십·PT 일정·G오더 주문·락커 만료
├─ 회원 활동(가칭)                출석 리마인드 · 공유 리마인드 · 운동 알림 · 챌린지 결과 · 배지
├─ 커뮤니티     (?)               같이운동 멘션·참여
└─ 광고                          ← 기존 marketing_push_agreement. 야간 광고는 별도 동의
```

- `회원 활동` 은 출석·공유 리마인드를 묶는 상위 개념의 임시 이름이다. 정식 이름은 보류다.
- 푸시 타입마다 카테고리를 **정확히 하나** 정한다. 매핑은 코드 한 곳(lib)에 둔다. 지금처럼 enum 값이 제목을 겸하는 구조에서는 매핑을 빠뜨리기 쉬워서, 매핑이 없는 타입은 발송을 막는 쪽으로 둔다.
- 하위 항목(출석 리마인드만 끄기 등)까지 열지는 3절의 데이터 모델로 나중에 정할 수 있다. 처음에는 카테고리 단위로 시작한다.

## 3. 데이터

### 3-1. 수신 설정

컬럼을 계속 늘리지 않고 행으로 둔다.

`user_notification_preference`

| 컬럼 | 설명 |
|---|---|
| `user_id`, `category` | PK |
| `enabled` | 수신 여부 |
| `agreed_at`, `revoked_at` | 마지막 동의·철회 시각. 지금은 철회 시각이 남지 않는다 |
| `updated_at` | |

- 하위 항목이 필요해지면 `category` 를 `MEMBER_ACTIVITY.ATTENDANCE` 같은 경로로 넓힌다. 행 구조라 스키마 변경이 필요 없다.
- 기존 4개 컬럼은 지우지 않는다(하위호환). 옮기는 동안 양쪽에 쓰고, 읽기를 새 테이블로 바꾼 뒤 기존 컬럼 제거는 별건으로 한다.
- 광고 동의는 법적 증빙 대상이라 이력 테이블(`user_notification_consent_history`: 누가·언제·어느 화면에서·켬/끔)을 따로 둘지 정해야 한다.

### 3-2. 수신 시간대

`user_notification_quiet_hours`

| 컬럼 | 설명 |
|---|---|
| `user_id` | PK |
| `enabled` | |
| `start_time`, `end_time` | KST `TIME`. 자정을 넘길 수 있다(22:00~07:00) |

적용 범위와 동작은 README 결정 항목이다. 선택지는 버림, 끝나면 발송(보류), 카테고리별로 다르게, 이렇게 세 가지다.

### 3-3. 발송 이력

`notification_dispatch_log`

| 컬럼 | 설명 |
|---|---|
| `id` | |
| `target_kind`, `target_id` | `MEMBER` / `TRAINER`. 지금은 구분이 없다 |
| `push_type`, `category` | |
| `dedupe_key` | UNIQUE. 예: `share-reminder:session:123`, `attendance-before:plan:45:2026-10-07` |
| `decision` | `SENT` / `SKIPPED_PREFERENCE` / `SKIPPED_QUIET_HOURS` / `DEFERRED` / `DUPLICATE` / `NO_TOKEN` |
| `scheduled_at`, `created_at` | |

- 배치마다 따로 만들던 중복 방지(슬롯 계산, 상태 값, 발송 시각 컬럼)를 `dedupe_key` 하나로 바꾼다. TECH-2585 의 `share_reminder_sent_at` 도 이 키로 대체할 수 있다.
- 행 수가 많아지므로 보존 기간을 정한다(예: 90일).

## 4. 판정

모든 발송은 아래 함수 하나를 거친다.

```
decide(target, pushType, now) → SEND | DEFER(until) | SKIP(reason)
  1. 대상 유효: 회원 ACTIVE, 토큰 있음
  2. 카테고리 = mapping[pushType]  (없으면 SKIP)
  3. 전체 알림 OFF → SKIP           (서비스 알림 예외 여부는 결정 항목)
  4. 카테고리 OFF → SKIP
  5. 광고 && 21~08시 && 야간 동의 없음 → SKIP 또는 DEFER
  6. 수신 시간대 안 → 카테고리 규칙에 따라 SKIP 또는 DEFER
  7. dedupe_key 중복 → SKIP
```

## 5. 어디에 둘 것인가 (도메인 분리 수준)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. app-server 모듈 | `notification` 모듈이 설정 API·판정을 갖고, 배치는 lib 의 판정 함수를 쓴다 | 지금 구조와 가깝다 | 판정 코드가 서버·배치 두 런타임에 복제된다. 발송처가 6벌인 지금 문제가 그대로 남는다 |
| B. 디스패처 | 발송처는 "보낼 의도"(대상·타입·dedupe_key·내용)만 큐에 넣고, 디스패처 하나가 판정·이력·FCM·알림함 적재를 한다 | 판정이 한 곳에 모인다. 발송처를 고칠 필요가 줄어든다 | 디스패처를 새로 만들거나 기존 컨슈머를 넘겨받아야 한다 |
| C. 외부 도구 위임 | Braze 의 구독 그룹·Quiet Hours·빈도 제한을 쓴다 | 이미 마케팅 푸시에 쓰는 도구다 | 서비스 알림까지 외부로 돌리면 결제 같은 알림이 외부 장애에 묶인다. 배치·서버 푸시 경로를 모두 바꿔야 한다 |

**제안: B.**
- 지금도 모든 앱 푸시가 SQS `app_push` 한 곳으로 모인다. 그 컨슈머가 판정 지점이 되기에 가장 자연스럽다.
- 다만 컨슈머 코드를 아직 찾지 못했다. 그래서 1단계는 컨슈머 위치와 동작을 확인하는 것이다.
- 광고 캠페인은 계속 Braze 가 보낸다. 대신 수신 설정은 이 도메인이 정본을 갖고, CRM 으로 동기화한다. 지금은 출석 약속 동의가 Braze 에 동기화되지 않는다.

## 6. 단계 (안)

1. 조사: `app_push` 컨슈머 위치·동의 검사 여부·알림함 적재 방식 확인. 트레이너 대상 푸시 구분 방식 확인
2. 카테고리 확정 + 푸시 타입별 매핑 표(lib)
3. 설정·시간대 테이블과 API, 기존 컬럼과 양쪽 쓰기, 앱 설정 화면
4. 디스패처: 판정 + 발송 이력. 처음에는 결과만 기록하고 막지 않는 모드(shadow)로 돌려 영향 범위를 본다
5. 판정 적용(차단 켜기). 배치별 중복 방지를 `dedupe_key` 로 교체
6. 기존 동의 컬럼 읽기 제거(별건)
