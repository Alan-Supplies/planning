# 테스트 세션 사전 자료 — 세션 전에 이것만 읽고 오세요

> 읽는 데 10분이면 충분합니다. 테스트를 한 번도 안 써봤다는 전제로 썼습니다.
> 외우거나 준비할 것은 없고, 마지막의 **"세션 전에 하나만 생각해 오기"**만 해오시면 됩니다.

---

## 1. 테스트 코드가 뭔가요?

한 문장으로: **"내가 손으로 확인하던 것을 코드가 대신 확인하게 만든 것"**입니다.

예를 들어 주문 생성 API를 수정했다고 해봅시다. 지금 우리는 이렇게 확인합니다.

1. 서버를 켠다
2. 포스트맨(또는 키오스크)에서 주문을 넣어본다
3. DB를 열어서 값이 잘 들어갔는지 눈으로 본다
4. 다음에 또 수정하면 → 1번부터 다시

테스트 코드는 이 확인 과정을 코드로 적어둔 것입니다. 한 번 적어두면 이후로는 명령어 한 줄로, 몇 번이고 같은 확인을 반복할 수 있습니다.

그래서 테스트의 목적은 "버그 없는 완벽한 코드"가 아닙니다. **"내 변경이 뭔가를 깨뜨렸는지 빠르게, 반복해서 확인하는 장치"**입니다. 이게 이번 세션 전체를 관통하는 한 문장입니다.

## 2. 실제 테스트 하나 뜯어보기

preppers-order-server에있는 테스트입니다. `test/customer-order/create-customer-order.e2e-spec.ts`에서 가져왔습니다.

```ts
it('cardCompany가 있고 installment가 없으면 00을 저장한다', async () => {
  // 1) 준비: 카드사만 있고 할부 개월수는 없는 주문 데이터를 만든다
  const createDto = createOrderDto({
    orderAmount: 10000,
    payment: { amount: 10000, cardCompany: '신한카드', approvedAt: new Date() },
  })

  // 2) 실행: 주문 생성 API를 호출한다
  const response = await createOrder(createDto).expect(201)

  // 3) 검증: DB에 저장된 결제를 꺼내서, installment가 '00'인지 확인한다
  const payment = await paymentRepo.findOne({ where: { orderId: response.body.id } })
  expect(payment?.installment).toBe('00')
})
```

처음 보는 문법이 있어도 구조만 보면 됩니다. 대부분의 테스트는 이 세 단계로 읽을 수 있습니다.

| 단계 | 이 테스트에서 | 손으로 하던 일에 비유하면 |
| --- | --- | --- |
| **준비** (Arrange) | 할부 없는 카드 결제 주문 데이터를 만든다 | 포스트맨에 요청 바디를 채운다 |
| **실행** (Act) | 주문 생성 API를 호출한다 | Send 버튼을 누른다 |
| **검증** (Assert) | 저장된 `installment`가 `'00'`인지 확인한다 | DB를 열어 눈으로 확인한다 |

그리고 맨 윗줄의 이름을 다시 보세요 — `'cardCompany가 있고 installment가 없으면 00을 저장한다'`. 코드를 한 줄도 안 읽어도 **"우리 시스템은 할부 정보가 없는 카드 결제를 일시불(00)로 저장한다"**는 비즈니스 규칙이 읽힙니다.

테스트가 쌓이면 현재 팀이 합의한 규칙을 실제 실행으로 확인하는 **실행 가능한 명세서**가 생깁니다. 규칙이 깨지면 빨간불이 들어옵니다. 다만 기대 결과를 잘못 적으면 잘못된 규칙도 통과할 수 있으므로, **무엇이 정답인지는 사람이 확인해야 합니다.**

## 3. 이 단어들만 알면 세션을 따라올 수 있습니다

세션과 코드 리뷰에서 자주 나오는 용어 7개입니다. 이 표만 훑고 오세요.

| 용어 | 뜻 |
| --- | --- |
| **테스트 / 스펙(spec)** | 확인 항목을 담은 코드. 파일 이름이 `~.spec.ts`, `~.e2e-spec.ts`인 이유 |
| **단언(assertion), `expect`** | "이 값은 이래야 한다"는 선언. `expect(x).toBe(y)` = "x는 y여야 한다" |
| **통과 / 실패 (초록 / 빨강)** | 단언이 전부 맞으면 통과(초록), 하나라도 어긋나면 실패(빨강) |
| **회귀(regression)** | 잘 되던 기능이 다른 수정 때문에 **다시** 깨지는 것. 테스트가 가장 잘 잡아주는 유형 |
| **픽스처(fixture)** | 테스트를 위해 미리 만들어두는 데이터. 예: 테스트용 매장, 테스트용 주문 |
| **목(mock)** | 진짜 대신 세워두는 가짜. 예: 테스트 중 진짜 Slack 알림이 가지 않도록 가짜 Slack을 꽂아둔다 |
| **플레이키(flaky)** | 코드는 그대로인데 어떤 때는 통과하고 어떤 때는 실패하는 불안정한 테스트. 신뢰를 갉아먹는 주범 |

코드 예시에서 본 **`it(...)`**은 테스트 하나를 표현하고, **`describe(...)`**는 관련 테스트를 하나로 묶습니다. 용어라기보다 코드를 읽기 위한 표현으로 알아두면 됩니다.

## 4. "테스트가 실패한다"는 좋은 소식일 수 있습니다

직관과 반대라서 미리 말해두는 부분입니다. 세션의 라이브 데모에서 이 장면을 실제로 보게 됩니다.

테스트가 없을 때 최악의 시나리오는 이렇습니다.

> 환불 로직을 수정했다. 환불은 잘 된다. 배포했다. 그런데 그 수정이 **매출 집계**를 조용히 틀어놨다. 아무도 모른 채 몇 주가 지나고, 정산 때 숫자가 안 맞는다는 제보가 온다. 이제 몇 주치 커밋을 뒤져야 한다.

같은 상황에서 테스트가 있다면:

> 환불 로직을 수정하고 테스트를 돌린다. 내가 건드린 적 없는 `매출 집계` 테스트가 **빨간불**이 된다. "어? 이게 왜 깨지지?" — 우선 방금 한 변경을 중심으로 원인을 찾을 수 있다.

이런 빨간불은 사고가 아니라 **사고를 배포 전에 발견할 기회**입니다. 다만 테스트가 실패했다고 항상 구현의 버그라는 뜻은 아닙니다. 먼저 원인을 구분합니다.

- 요구사항이 바뀌어 기대 결과가 달라진 것 → **테스트의 기대 결과를 고친다**
- 잘 되던 동작이 의도치 않게 깨진 것(회귀) → **테스트는 그대로 두고 코드를 고친다**
- 테스트 코드·데이터·실행 환경의 문제 → **테스트 기반을 고친다**

## 5. 전부 테스트해야 하는 건 아닙니다

"그럼 모든 코드에 테스트를 다 붙여야 하나요?" — 아니요. 그건 목표가 아닙니다.

기준은 하나입니다: **"이게 틀어지면 얼마나 아픈가?"**

우리 서비스에서 아픈 순서로 예를 들면:

1. **돈과 상태**: 결제·취소·환불, 주문 상태 전이 — 틀어지면 고객 돈 문제
2. **계산**: 금액, 수량, 매출 집계, 시간대(KST/UTC) — 틀어지면 정산 문제
3. **권한**: 다른 매장 데이터가 보이면 안 되는 규칙
4. **한 번 났던 버그**: 같은 사고가 두 번 나는 것을 막는 재현 테스트

반대로 단순 조회, 프레임워크가 보장해 주는 동작 같은 것은 우선순위가 낮습니다. **적게, 아픈 곳부터.** 세션에서도 각자 "규칙 1개"만 고릅니다.

## 6. (선택) 세션 전에 직접 한번 돌려보고 싶다면

필수는 아닙니다. 하지만 한 번 돌려보고 오면 세션 데모가 훨씬 잘 보입니다.

```bash
# preppers-order-server에서 테스트 DB와 .env.test 등 실행 환경을 준비한 뒤
npm run test:e2e
```

실행 환경이 잡혀 있지 않거나 DB 연결·권한 문제로 실패하면 그냥 넘어가세요. 세션에서 실제 실행 화면을 함께 봅니다.

---

## 7. 세션 전에 하나만 생각해 오기 (이건 꼭)

세션 마지막에 각자 이 문장을 채우는 시간이 있습니다.

> "나는 `______` 규칙의 `정상 / 예외` 케이스를 테스트하겠다."

그래서 미리 이것 하나만 생각해 오세요.

**"내가 최근에 작업한 기능에서, 틀어지면 가장 아픈 규칙 하나"**

거창할 필요 없습니다. 위의 `installment` 예시처럼 "이 조건이면 이 값이어야 한다" 한 줄이면 충분합니다. 잘 안 떠오르면 그것대로 괜찮습니다. 세션에서 함께 고릅니다.

## 자주 하는 걱정 미리 답변

**"저 테스트 한 번도 안 써봤는데 따라갈 수 있나요?"**  
네. 이 문서의 2번(3단계 구조)과 3번(용어 표)만 읽고 오면 됩니다. 세션은 이론 강의가 아니라 데모를 같이 보는 자리입니다.

**"바빠 죽겠는데 테스트 짤 시간이 어디 있어요?"**  
처음 쓰는 시간은 분명히 듭니다. 대신 배포 전마다 손으로 누르던 시간, 장애 원인을 커밋 이력에서 뒤지던 시간이 줄어듭니다. 그리고 전부가 아니라 **아픈 규칙 1개부터** 시작합니다. 세션의 데모로 이 교환이 실제로 이득인지 함께 봅니다.

**"AI한테 짜달라고 하면 되는 거 아닌가요?"**  
초안은 AI가 잘 만듭니다. 다만 AI는 **지금 구현된 동작을 정답으로 믿고** 테스트를 만들 수 있습니다. 버그까지 정답으로 고정할 수 있다는 뜻입니다. 그래서 기대 결과가 진짜 기획 의도와 맞는지는 사람이 확인해야 합니다. **작성은 AI의 도움을 받되, 의도와 기대 결과에 대한 책임은 우리에게 있습니다.**
