### 그런데 앱 코드는 두 축을 섞어 쓴다

회원 목적 6개 중 **2개**가 두 테이블에 걸친 태그를 한 배열에서 사용:

| 회원 목적 | 매핑 태그 | 분리 후 소속 |
|---|---|---|
| `WEIGHT_LOSS` | `FAT_LOSS`, `ENDURANCE` | 추천용 + 효과 축 ← 혼용 |
| `HEALTH_MANAGEMENT` | `RECOVERY`, `MOBILITY` | 추천용 + 효과 축 ← 혼용 |

→ `exercise-recommendation.dao.ts` L97에서 **두 테이블을 모두 로드**해야 한다. 합집합을 만들지 않으면 `FunctionalCompatibilityScorer.score()`가 교집합 개수를 점수로 쓰기 때문에 **감량 목적 회원 점수가 조용히 절반으로 떨어진다.**

### 기능성 풀 판정 — (b) 채택

| 판정 방식 | 종목 수 | 근거 강도 |
|---|---|---|
| 현재 (`exercise_function` 행 보유) | 43종 | 실행일정 2절 실측표 有 |
| (a) `exercise_recommend_tag` 보유 | 22종 | **4-7절 표에만 있음 — 쿼리 미기재** |
| **(b) `exercise_effect` − `STRENGTH`** | **42종** ✅ | 실행일정 2절 실측표 有 |
| (c) 합집합 나이브 치환 | 266종 ✗ | 위와 같음 |

- (c)는 `STRENGTH` 백필 225행이 들어오는 순간 사실상 전 종목이 기능성이 되어 `general`/`functional` 풀 분리가 소멸
- (b)와 현행의 차이는 **`id=55` 맨몸 레그레이즈 1종**뿐 (`FAT_LOSS`만 보유 → 효과 축 행이 없어 이탈)

**⚠️ "42종"이 두 가지 뜻으로 쓰인다**

| 표기 | 뜻 | 빠지는 종목 |
|---|---|---|
| "43종(ACTIVE 42종)" | `status='ACTIVE'` 종목 | `id=241` 머신 리버스 하이퍼 익스텐션 |
| "(b) 42종" | 효과 축 태그 보유 종목 | `id=55` 맨몸 레그레이즈 |

우연히 둘 다 42다. 회귀 대조 쿼리에 `status` 조건을 넣을지 **명시해야 한다.**

### distinct 43종으로 세는 이유

`candidate-pool.filter.ts`의 `isFunctional(exercise)`가 **종목 단위**로 판정한다 — 태그 4개짜리나 1개짜리나 똑같이 1종. 그래서 후보 풀 크기를 정하는 것은 87행이 아니라 `distinct exercise_id` = 43종이다.

행으로 비교하면 "63행이 효과 축으로 가니 72% 유지"로 읽히지만, 실제 질문은 **"효과 축 태그를 하나라도 가진 종목이 몇 종이냐"**이고 답은 42종이다.

교차 검증: `42 + 22 − 43 = 21종이 양쪽 태그 보유` → `43 − 42 = 1종만 추천용 전용` = `id=55`. **`id=55`가 특정된 것 자체가 distinct 카운트의 산물이다.** 행 수로만 봤으면 어느 종목이 이탈하는지 알 수 없었다.

## 2026-08-26 추가 — 단위를 기구(machine)에 두자는 의견

**결론: 반대.** 단, 프리필·검증 용도로는 별도 컬럼으로 살릴 만하다.

두 가지가 섞여 있다:

| | 무엇 | 어디 속성인가 |
|---|---|---|
| (가) 이 장비는 몇 단위 표기인가 | 장비의 사실 | 기구 |
| (나) **이 기록은 어느 단위로 입력됐나** | 입력 사건의 사실 | 기록 |

`weight_kg` 환산에 필요한 건 (나)다. 파운드 입력 계속 허용 확정(2026-08-21)이고, lb 표기 머신에서 kg으로 환산해 입력하는 회원이 있으면 (가) ≠ (나)다.

**반대 근거 4가지**

1. **커버리지 붕괴** — `weight_type`은 NULL 0건(kg 137,120 / lb 10,553). 반면 기구 연결률은 `CABLE` 100% · `MACHINE` 88.3% · `BARBELL` 16.1% · `BODY` 9.8% · `PROP` 7.1% · **`DUMBBELL` 1.8%.** 무게 종목의 주력인 덤벨·바벨이 기구에 안 붙어 있다. 100% 채워진 필드를 대부분 NULL로 바꾸는 거래가 된다
2. **생성 열 제약은 그대로** — 세트 → 개별운동 → 기구 **2홉**. 결국 세트 행으로 복사해야 한다. 경로만 길어진다
3. **과거 해석이 흔들린다** — 기구 표기 정정·장비 교체 시 조회 시점 조인 방식에서는 과거 전체 기록의 해석과 랭킹이 **소급 변경**된다. 기록 행에 박은 단위는 시점 사실이라 그런 일이 없다
4. **계층 불일치** — `machine`은 모델 마스터 1,155행, 지점 설치는 `gym_machine` 6,420행. 단위는 지점마다 다를 수 있는데 모델에 달면 표현 못 한다. 게다가 기록의 `machine_id`는 `machine`(모델)을 가리켜 `gym_machine`에 닿지 못한다

**기구 단위의 쓸 곳 — 원천이 아니라 보조**

1. **입력 기본값(프리필)** — lb 지점에서 lb가 기본 노출. 기록 해석에는 관여하지 않음
2. **입력 검증 신호** — 기구 표기와 입력 단위 불일치 시 경고만. 막지 않는다 ((가)≠(나)가 정상이므로)
3. **오염 탐지** — `has_weight=0`인데 무게 있는 세트 4,390건 / 43종목, `unit='MINUTE'`인데 무게 2건의 원인 추적

→ 필요하면 **`gym_machine`에 별도 컬럼** 신설하고 용도를 규약에 명시. **이번 개편 범위 밖 후속 별건.**

## 2026-08-26 정정 — 세트 테이블 쓰기 경로는 1개

코드 직접 확인 결과, **"저장 경로가 여러 개라 앱마다 다를 수 있다"는 근거는 현재 코드에 해당하지 않는다.** (방안 문서 §9의 서술을 검증 없이 인용한 것)

| 위치 | 동작 |
|---|---|
| `user-exercise.dao.ts:542` (`putUserExerciseSetHistory`) | `em.save(newSetHistories)` — **유일한 INSERT** |
| `user-exercise.dao.ts:529` (같은 메서드) | `em.delete` — 재삽입 전 전량 삭제 |
| `user-exercise.dao.ts:502` (`deleteUserExerciseSessionHistoryAndShiftRoundNumber`) | `em.delete` — 자식 정리 |

- 참조 파일은 `gymboxx-app-server`의 `user-exercise` 모듈 **4개**(controller/module/service/dao)
- **cascade 우회 없음** — `user_exercise_session_history.ts:61`의 `@OneToMany`에 cascade 옵션이 없어 부모 저장으로 세트가 삽입되지 않는다
- 다른 gymboxx 서버 레포 7개(trainer/headquarter/branch-admin/public/community/kiosk/pass) + `supplies-data-clean` 전부 참조 **0파일**

### 그래도 생성 열이 맞는 이유 (근거 교체)

1. **마이그레이션 백필이 두 번째 쓰기 주체다** — 32.9만 행을 채우는 건 앱이 아니라 스크립트다. 일반 컬럼이면 `× 0.45359237` 수식이 **백필 SQL과 DAO 두 곳에 각각 구현**되고, 두 구현이 같은지는 아무것도 보장하지 않는다. 생성 열이면 백필 자체가 없다 — 컬럼 추가 시점에 DB가 전건 계산
2. **그 유일한 경로가 delete + reinsert다** — 수정마다 수식이 재실행된다. 게다가 이 메서드는 `created_at` 리셋·대리키 `id` churn 때문에 어차피 **upsert로 재작성될 대상**이다. 수식을 든 채 재작성되는 메서드
3. **비용이 0이다** — 어차피 컬럼을 추가한다. `decimal(10,7)` 표현식 한 줄이고 앱 코드 변경이 없다

### 인덱스 불필요 판단 → VIRTUAL 생성 열

"`weight_kg` 인덱스 특별히 필요 없다, 오히려 쓰기 성능 저하" 판단이 맞다면 **VIRTUAL 생성 열**이 답이다.

| | 저장 공간 | 쓰기 비용 | 읽기 |
|---|---|---|---|
| `STORED` | 행에 저장 | 있음 | 즉시 |
| **`VIRTUAL`** | **0** | **0** | 조회 시 계산 |

인덱스를 걸지 않는다면 VIRTUAL로 두면 **쓰기 성능 저하가 원리적으로 없다.** 방안 문서 §9는 "환산 무게에 인덱스 부여"를 전제로 썼으므로, 인덱스를 빼는 결정을 하면 `STORED`/`VIRTUAL` 선택을 함께 정해야 한다.

### 이 질문이 겨냥한 급소

**일반 컬럼을 택하면 `weight_unit` 복사가 필수가 아니다.** 앱이 쓰기 시점에 상위 행을 읽어 계산해 넣으면 되니까. 즉 "단위를 세트에 둬야 한다"의 **강제성은 생성 열을 택했기 때문에 생긴다.**

생성 열을 포기해도 `weight_unit` 복사는 여전히 원한다 — 이유가 보장이 아니라 **조회**로 바뀔 뿐이다(집계 시 조인 제거, 원단위 표시가 세트 행에서 완결). 강제가 아니고 이득.

## 확인 필요 — 검증 쿼리

```sql
-- (a) 추천용 태그 보유 22종 검증 (실행일정 4-7절 표에 쿼리가 적혀 있지 않음)
SELECT COUNT(DISTINCT exercise_id) AS recommend_only
  FROM exercise_function
 WHERE functional_tag IN ('FAT_LOSS','RECOVERY');

-- 두 태그를 모두 가진 종목이 정확히 2종인가 (24행 → 22종의 근거)
SELECT exercise_id, GROUP_CONCAT(functional_tag) AS tags
  FROM exercise_function
 WHERE functional_tag IN ('FAT_LOSS','RECOVERY')
 GROUP BY exercise_id
HAVING COUNT(*) > 1;

-- 기록의 machine_id 실제 채움률 (위 연결률은 exercise_machine 기준이라 별개)
SELECT COUNT(*) AS total,
       SUM(machine_id IS NULL) AS machine_null,
       ROUND(100 * SUM(machine_id IS NOT NULL) / COUNT(*), 1) AS fill_pct
  FROM user_exercise_session_history;

-- 같은 기구에서 kg·lb가 섞이는가 → 섞이면 "기구 = 단위"가 성립하지 않는 직접 증거
SELECT machine_id,
       SUM(weight_type = 'kg') AS kg_cnt,
       SUM(weight_type = 'lb') AS lb_cnt
  FROM user_exercise_session_history
 WHERE machine_id IS NOT NULL
 GROUP BY machine_id
HAVING kg_cnt > 0 AND lb_cnt > 0;
```

**`exercise_equipment` · `exercise_type` 테이블의 정체** — [table.probe](table.probe)에 조회 쿼리가 있는데 방안·실행일정 두 문서 어디에도 등장하지 않는다. 장비 분류 신설(§5)과 역할이 겹치면 `equipment_type` 컬럼 신설의 전제 자체가 바뀐다.
