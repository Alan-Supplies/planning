# DB 구조 업그레이드 실행 일정 (v2)

> 이 문서는 [`DB_구조_업그레이드_방안.md`](DB_구조_업그레이드_방안.md)의 §17-1 "한 장 요약" 실행 우선순위를 캘린더 일정으로 변환한 것입니다. 방안 문서가 "무엇을·왜"를 다룬다면, 이 문서는 "언제·어떤 순서로"만 다룹니다 — 방안 문서 본문·`database/` 폴더는 수정하지 않았습니다.
>
> **v1은 코딩 공수를 기간 결정 변수로 삼아 10주를 산출했습니다. v2는 전제를 뒤집습니다 — 코드 작성 1일 · 배포 검증 1일 · 운영(prod) 배포 제외.**
> 이 전제에서 기간을 결정하는 것은 코드가 아니라 **"그 컬럼에 넣을 값이 이미 정해져 있는가"** 하나뿐입니다. 그래서 이 문서의 절반은 일정이 아니라 **데이터 준비 상태 실측**(3절)과 **모듈 영향도 실측**(4절)입니다.

## 1. 목적과 전제

- **오늘 날짜**: 2026-08-25(화)
- **실측 기준일**: 방안 문서 원본 실측은 2026-08-19·2026-08-21(read-replica). 이 문서를 위해 **2026-08-25**에 운영 읽기전용 계정(`readonlyuser`)으로 행수·테이블 구조(`SHOW CREATE TABLE`)·MySQL 버전·값 분포를 재조회했습니다(2절·3절). **SELECT/SHOW만 실행했고 DDL/DML은 실행하지 않았습니다.**

### 1-1. v2 전제 3가지

| 전제 | 값 | 근거 |
|---|---|---|
| **코드 작성** | **1일 / 배치** | 사용자 지정 — AI 활용을 전제로 하면 순수 편집량은 병목이 아닙니다 |
| **배포 검증** | **1일 / 배치** | 사용자 지정 |
| **운영(prod) 배포** | **일정에서 제외** | 사용자 지정 — 개발/스테이징까지의 반영·검증만 다룹니다. 빠진 것은 **8절**에 별도로 기술합니다 |
| (파생) 배치 단위 | **lib 버전업 1회 = 1배치** | `gymboxx-app-server`가 `@suppliesfitness/gymboxx-lib`을 `4.28.17-dev.0`으로 고정 pin. 엔티티 변경마다 lib 버전업이 필수라 이것이 최소 릴리스 단위입니다 |

### 1-2. 이 전제에서 기간을 결정하는 것

> **코드가 항상 1일이면, 기간을 결정하는 것은 "그 컬럼에 넣을 값이 이미 정해져 있는가" 하나뿐입니다.**

따라서 이 문서는 임계 경로를 **코딩 공수 → 데이터 확정 상태**로 재정의하고, §1~§12 전 항목을 "자동 확정 / 부분 확정 / 미확정" 3분류로 판정합니다(3절). 그 결과 일정은 **두 개의 트랙**으로 갈라집니다.

- **트랙 1 (코드·배포검증)** — 통제 가능. 배치 1~6, 투입 14영업일.
- **트랙 2 (사람 판단)** — 통제 불가. 트레이너 검수 회신·기획 결정. **전체 종료일을 결정하는 것은 이쪽입니다.**

### 1-3. 범위

- **산출**: 일정표 문서 1건.
- **범위 밖**: 실제 마이그레이션 SQL·엔티티 코드 작성, 사람 판단 항목(29종 검수, 장비 29종 판례, 최고기록 적재 범위)을 **대신 결정하는 것**, DB DDL/DML 실행, **운영(prod) 배포 일정**(8절), §15 "부위별 랭킹 산정 기준"(방안 문서 자체가 범위 밖으로 선언).

#### (1) 이관 63행 — 자동 확정

`SELECT functional_tag, COUNT(*) FROM exercise_function GROUP BY functional_tag` 실측: `ENDURANCE` 25 · `BALANCE` 20 · `MOBILITY` 18 · `FAT_LOSS` 14 · `RECOVERY` 10 = **87행**(distinct 운동 43종). 방안 문서 §1 수치와 **전부 일치**.
→ 효과 축으로 **63행**, 추천용으로 **24행**. **사람 판단이 개입할 여지가 없는 `INSERT ... SELECT` 1건.**

#### (2) STRENGTH 백필 225/28 — 쿼리로 재현했고 문서와 정확히 일치

```sql
SELECT SUM(f.exercise_id IS NULL)     AS no_endur_mob,   -- 225
       SUM(f.exercise_id IS NOT NULL) AS review_target    -- 28
  FROM (SELECT DISTINCT exercise_id FROM exercise_body_part
         WHERE body_part_id BETWEEN 1 AND 6) m
  LEFT JOIN (SELECT DISTINCT exercise_id FROM exercise_function
              WHERE functional_tag IN ('ENDURANCE','MOBILITY')) f
         ON f.exercise_id = m.exercise_id;
```

| 항목 | 실측 | 방안 문서 `:351` | 일치 |
|---|---|---|---|
| 근육 부위 라벨 보유 종목 | **253** | 253 | ✅ |
| 지구력·이완 태그 없음 → 근력 확정 | **225** | 225 | ✅ |
| 지구력·이완 태그 보유 → 검수 대상 | **28** | 28 | ✅ |

> **주의 — 위 재현 쿼리의 `body_part_id BETWEEN 1 AND 6`은 조사용 SQL이지 애플리케이션 코드가 아닙니다.** 앱·서버 코드에 이 형태의 범위 조건은 **실측 0건**입니다(4-4절).

**결론 — 225종은 규칙만으로 자동 부여 가능하고, 사람 판단이 필요한 것은 28종뿐입니다.**

| 안 | 내용 | 사람 판단 | 정확성 |
|---|---|---|---|
| **A. 다수결 채택 (권고)** | 80% 규칙으로 31종 자동, 15종 사람 판단 | **15종** | 대표 표기로는 타당, 지점 판정용으로는 부정확 |
| B. 위임 | MACHINE 66종을 `equipment_type='MACHINE'` 하나로 두고 구분은 `machine.type`에 위임 | 0종 | 지점 판정은 정확. 단 §5의 "12종" 목표에서 2종이 빔 |
| C. 전건 사람 판단 | 54종 전부 | 54종 | A와 동일한 한계 |

**권고: A로 진행하되 "다수결 값은 대표 표기이며 지점 가능 운동 판정에는 `exercise_machine`을 쓴다"를 규약에 명시합니다.** B는 §5 목표(12종 분류)를 포기하는 것이라 결정 권한이 이 문서 밖에 있고, C는 A보다 나은 점이 없습니다. **이 선택 자체를 검수 요청서 B의 첫 질문(Q4)으로 넣습니다.**

### 4-6. §10에서 발견된 미기재 코드 변경 — `putUserExerciseSetHistory`의 delete + reinsert

### 4-7. 의미 변경 판정 — 추천 로직은 두 축을 섞어 쓴다

`constants/goal-to-specific-compatibility.constants.ts` 전문(분리 후 어느 테이블로 가는지 표시):

| 회원 목적 | 매핑 태그 | 분리 후 소속 |
|---|---|---|
| `WEIGHT_LOSS` | `FAT_LOSS`, `ENDURANCE` | **추천용 + 효과 축** ← 혼용 |
| `STRENGTH_GAIN` | `ENDURANCE` | 효과 축 |
| `ENDURANCE_GAIN` | `ENDURANCE`, `BALANCE` | 효과 축 |
| `HEALTH_MANAGEMENT` | `RECOVERY`, `MOBILITY` | **추천용 + 효과 축** ← 혼용 |
| `POSTURE_CORRECTION` | `MOBILITY`, `BALANCE` | 효과 축 |
| `ATHLETIC_PERFORMANCE` | `BALANCE`, `MOBILITY`, `ENDURANCE` | 효과 축 |

**6개 목적 중 2개(`WEIGHT_LOSS`·`HEALTH_MANAGEMENT`)가 두 테이블에 걸친 태그를 한 배열에서 섞어 씁니다.** 분리 후 이 모듈은 두 테이블을 모두 조회해 합집합을 만든 뒤 교집합을 계산해야 합니다. `FunctionalCompatibilityScorer.score()`가 "교집합 개수"를 점수로 쓰므로, 합집합을 만들지 않으면 **감량 목적 회원의 점수가 조용히 절반으로 떨어집니다.**

**더 큰 문제였던 것 — 기능성 풀의 정의**

```ts
// candidate-pool.filter.ts — 현재
private isFunctional(exercise: ExerciseEntity): boolean {
  return (exercise.exercise_function?.length ?? 0) > 0
}
```

| 판정 방식 | 기능성으로 판정되는 종목 수 | 현행 대비 |
|---|---|---|
| **현재**(`exercise_function` 행 보유) | **43종**(ACTIVE 42종) | — |
| (a) `exercise_recommend_tag` 보유 | 22종 | −21 |
| **(b) `exercise_effect` 중 `STRENGTH` 제외분 보유** | **42종** | **−1** ✅ 채택 |
| (c) 두 테이블 합집합 (나이브 치환) | 266종 | **+223 (6.2배)** ✗ |

(c)로 나이브 치환하면 STRENGTH 백필 225행이 들어오는 순간 "기능성 운동"이 사실상 전 종목이 되어 `general` 풀과 `functional` 풀의 분리가 소멸하고 추천 결과가 통째로 바뀝니다.

**✅ 확정 방침 — (b) `exercise_effect` − `STRENGTH`**

실측 검증: `exercise_effect`에서 `STRENGTH`를 뺀 종목 = `ENDURANCE`/`MOBILITY`/`BALANCE` 보유 **42종**(`PLYOMETRIC`은 0행). 현행 43종과의 차이는 **정확히 1종**입니다.

| 이탈 종목 | 사유 |
|---|---|
| `id=55 맨몸 레그레이즈`(BODY, ACTIVE) | `FAT_LOSS` 태그만 보유 → 분리 후 `exercise_recommend_tag`로만 가고 효과 축 행이 없어 기능성 풀에서 빠짐 |

**추천 결과 변화는 이 1종뿐이며, 43 → 42는 사실상 불변입니다.** 따라서 배치 4의 회귀 대조는 "**이 1종 외에 차이가 없는가**"를 확인하는 작업이 됩니다.

**구현 지침 (배치 4):**

```ts
// candidate-pool.filter.ts — 분리 후
private isFunctional(exercise: ExerciseEntity): boolean {
  return (exercise.exercise_effect ?? [])
    .some(e => e.effect_tag !== EXERCISE_EFFECT_TAG.STRENGTH)
}
```

- `exercise-recommendation.dao.ts` L97: `exercise_function: true` → `exercise_effect: true` **+** `exercise_recommend_tag: true`(태그 혼용 때문에 스코어러가 양쪽을 다 봐야 함)
- `goal-to-specific-compatibility.constants.ts`: 태그 배열은 **값 그대로 유지**하되 타입만 `(EXERCISE_EFFECT_TAG | EXERCISE_RECOMMEND_TAG)[]`로 넓힙니다. 값을 바꾸지 않는 것이 "추천 결과 불변" 요구의 핵심입니다
- `functional-compatibility.scorer.ts` `extractFunctionalTags()`: 두 테이블 태그를 **합집합**으로 반환하되 `STRENGTH`는 제외
- **API 계약 유지**: `exercise-recommendator.ts` L177·L184-191의 `specific` 필드도 같은 합집합(STRENGTH 제외)을 씁니다 → **응답 값이 현행과 동일하게 유지되어 클라이언트 변경이 불필요합니다**

### 4-8. 모듈 영향도 한 줄 결론

> 파일 17개 · 변경 지점 약 50라인 · 테스트 픽스처 49곳으로 **편집량은 작습니다.** `exercise-recommendation` 모듈이 두 축을 섞어 쓰고 기능성 풀이 6.2배 부풀 위험이 있었지만, 사양이 **(b) `exercise_effect` − `STRENGTH`로 확정**되어 기능성 풀은 43 → **42종**(차이 1종)이 되고 `specific` API 응답도 그대로여서 **클라이언트 계약 변경이 없습니다.**
> 남은 작업은 기계적 치환 + **차이가 1종으로 한정되는지 확인하는 회귀 대조 1건**, 그리고 별도로 발견된 두 건 — **status 필터 2지점 추가(4-5)**와 **`putUserExerciseSetHistory` upsert 전환(4-6)**입니다. 뒤의 두 건은 방안 문서·v1 일정 어디에도 작업 항목으로 등록돼 있지 않았습니다.

#### 배치 2 보충

- **PK 교체 DDL 작성 제약 — 반드시 단일 ALTER 문**: `DROP PRIMARY KEY` + `ADD COLUMN id ... AUTO_INCREMENT PRIMARY KEY` + `ADD KEY (exercise_id, body_part_detail_id)`를 **한 ALTER 문 안에** 넣어야 합니다. 나눠 실행하면 `exercise_id` FK가 지지 인덱스(기존 PK의 왼쪽 컬럼)를 잃는 순간이 생겨 **errno 1553으로 실패**합니다 — 2절 실측(구조)과 방안 문서 §7-3 "누락하면 실행 오류"가 같은 지점을 가리킵니다.
- **스테이징 드라이런 필수**: `gymboxx-lib` 마이그레이션 **228개 전수에서 `DROP PRIMARY KEY` 선례 0건** — 저장소에 전례가 없습니다. 2일차의 실체가 이 드라이런입니다.
- **status 필터 2지점 추가를 같은 배포에 포함**(4-5). 누락하면 무증상 추천 순위 회귀가 발생합니다.
- **§7은 앱 쓰기 경로 0건**: `exercise_body_part_detail`에 대한 INSERT/UPDATE/upsert 경로가 app-server 전체에 없고 참조 4개 파일이 **전부 읽기 전용**입니다. 현재 중복도 0건(§7 `:680`)입니다. **이 제약이 실제로 막는 대상은 사람이 직접 실행하는 SQL뿐**이며, 그래서 §7은 "예방 목적·우선순위는 후속"이라는 방안 문서 서술대로 2일 경량 배치로 처리합니다.
- **DDL 잠금은 무해**: `AUTO_INCREMENT` 대리키 추가가 동시 DML을 막지만(2절) **514행이라 리빌드가 즉시 끝나므로 실행 창구 제약이 없습니다.** 이 판단이 배치 3과 갈리는 지점입니다.

#### 배치 3 보충

- **"INPLACE라 논블로킹"을 근거로 쓰지 않습니다.** `AUTO_INCREMENT` 대리키 컬럼 추가는 `ALGORITHM=INPLACE`이면서 **Permits Concurrent DML: No**입니다(MySQL 8.0.45). 32.9만 행 리빌드 구간 내내 `user_exercise_set_history`의 쓰기가 막히며, 이 테이블은 **하루 5,000~7,000행이 실제로 쓰이고 있습니다.** → **저트래픽 시간대(새벽) 실행 창구 확정은 선택이 아니라 필수 조건**이고, 실제 차단 시간은 리허설일에 측정합니다.
- **배포검증 항목에 "세트 수정 후 `id`가 유지되는가"를 명시적 체크로 추가**합니다 — 4-6의 upsert 전환 누락을 잡는 유일한 관문이며, 이것이 §12의 `source_set_id` 정합성을 좌우합니다.
- 착수 직전 **이력 테이블 행수 재실측**이 필요합니다(하루 약 5,000~7,000행 증가).

#### 배치 4 보충

- 이관·백필 SQL에서 `is_primary` 기본값 0을 유지하고, 자동 부여 대상(효과 축 행 1개인 237종)에서 **`exercise_id IN (135, 233)`을 예외로 제외**합니다.

```sql
-- 효과 축 행이 1개인 종목에 주 효과 자동 부여 — 단 135·233은 제외(PLYOMETRIC 보류)
UPDATE exercise_effect e
  JOIN (SELECT exercise_id FROM exercise_effect WHERE status='ACTIVE'
         GROUP BY exercise_id HAVING COUNT(*) = 1) s ON s.exercise_id = e.exercise_id
   SET e.is_primary = 1
 WHERE e.status = 'ACTIVE'
   AND e.exercise_id NOT IN (135, 233);   -- 버피·점핑잭: PLYOMETRIC 결정 전까지 보류
```

- 자동 주 효과 부여는 237종 → **235종**, 보류 2종.
- **회귀 대조 기준**: 배포검증일에 전 회원 목적 6종 × 부위 조합으로 추천 결과를 전/후 비교하고, 차이가 **`id=55 맨몸 레그레이즈` 관련 1건**으로 한정되는지 확인합니다(4-7).
- **29종 검수 회신이 늦으면 배치를 쪼갭니다** — "구조·이관·STRENGTH 225·`is_primary` 235 자동분"을 먼저 내고 "29종 검수 반영"을 후속 UPDATE로 분리합니다(9-3절).

#### 배치 6 보충 — 자동 매핑 규칙 우선순위

1. `unit='MINUTE'` → 유산소 기구 (기구 마스터 `type='CARDIO'`와 100% 일치)
2. `name LIKE '%스미스%'` → 스미스 (`type_detail='SMITH'`와 100% 일치)
3. `type` 1:1 매핑 → 덤벨 55 · 바벨 31 · 케이블 27 · 맨몸 41
4. `PROP` 이름 규칙 → 케틀벨 6 · 밴드 12 · 구조물/소도구 약 10
5. **MACHINE 다수결** → 연결 기구의 80% 이상이 `PIN`이면 핀 머신(18), `PLATE_LOADED`면 플레이트 머신(13)
6. 잔여 **29종은 검수 회신 후 UPDATE**, 미연결 INACTIVE 8종은 **NULL 유지**(재활성화 시 필수 입력으로 차단)

**병행 컬럼 방식**(§5 `:540`)이라 **부분 적용이 이미 허용**돼 있습니다 — 회신이 늦으면 자동 244종만 먼저 적용하고 29종을 후속으로 남길 수 있습니다.

### 7-2. **줄어들지 않는 것 — 코드 속도로 해결되지 않는 4가지**

> **이것이 이 문서의 핵심 메시지입니다. 임계 경로는 코드가 아닙니다.**

1. **§1 29종 트레이너 검수 회신 (목표 09/03 목)** — 검수 자체는 반나절이지만 **트레이너 일정 확보가 통제 밖**입니다. 늦으면 배치 4가 "구조 분리 + 이관 + STRENGTH 225 + `is_primary` 235 자동분"까지만 나가고 **29종의 주 효과가 빈 채로 남습니다.** 다만 **기구 유산소 11종의 주 효과는 자동 확정되므로 유산소 시간 목표는 계산 가능**하고, 막히는 것은 **균형 세션 목표**(균형 주 효과 적격 판정이 29종 안에 있음)뿐입니다.

2. **§5 장비 29종 회신 (목표 09/10 목)** — **전체 종료일을 결정하는 유일한 항목.** 대상이 68 → 29종으로 줄고 성격도 가벼워졌지만(MACHINE 15종은 데이터가 다 나온 표기 규칙 결정), **코드 2일 vs 회신 대기 11영업일**이라는 비율은 여전히 압도적입니다. 회신이 밀려도 09/23까지는 추석에 닿지 않습니다(완충 7영업일).

3. **§9·10·11 스테이징 리허설 1일** — 32.9만 행 리빌드의 실제 소요를 코드로 줄일 수 없습니다. **물리 시간**입니다. 게다가 `INPLACE`가 동시 DML을 허용하지 않아 차단 시간 측정은 생략할 수 없습니다.

4. **§11 세트 강도 수집률 판정** — 컬럼 추가는 즉시 되지만 "세션 기준선 57.4% 대조"는 **실사용 누적**이 필요하고, 그 전에 **입력 화면이 있어야 합니다.** 화면 수요 조사(§15)가 미결이므로 **이 지표의 판정 시점은 무기한 후속이며 v2 일정에 넣지 않습니다**(9-2절).

여기에 **v2 자체가 만든 후속 4건**을 더해야 합니다 — 어드민 화면 부재로 검수 결과를 SQL로 옮겨 적는 단계(4-1), 신규 유산소 강도 필수 입력 규칙(배치 1 범위 밖), 구 컬럼·구 테이블 폐기, prod 적용 절차 전반(8절).

> **결론: 투입이 45일 → 14일로 준 것은 코드를 빨리 써서가 아닙니다.** 줄어든 31일의 대부분은 **(a) 운영 배포를 제외**했고 **(b) 실측으로 블로커가 소멸**했고 **(c) 사람이 볼 목록을 68 → 29종으로 줄였기** 때문입니다. **일정을 더 당기는 유일한 방법은 검수 대상을 더 줄이거나 회신을 더 빨리 받는 것이며, 인원을 2배로 늘려도 캘린더 이득은 최대 4일입니다**(5-2).

## 8. 이 일정에 포함하지 않은 것 — 운영(prod) 배포

v2 일정은 **개발/스테이징 환경까지의 반영과 검증만** 다룹니다. 아래는 명시적으로 이 일정 밖이며 별도 릴리스 프로세스로 처리해야 합니다.

| 제외 항목 | 내용 | 상태 |
|---|---|---|
| **prod DDL 적용 절차·주체** | `gymboxx-lib`의 `src/sqlv4/`는 CLAUDE.md에 "실행 자동화 스크립트가 아니라 이력 기록용이며 실제 DB 반영은 별도 프로세스"로 명시. **누가·어떤 승인으로 prod에 적용하는지 v1·v2 두 번의 조사로도 확인되지 않았습니다** | **미확인 — 11절 유일 잔여 질문** |

| **구 컬럼·구 테이블 폐기** | `exercise.type`(§5 병행 대조 검증 후), `exercise_function`(§1 앱 코드 전환 확인 후). 둘 다 병행 기간이 필요하고 그 기간은 prod 운영 관찰에 종속 | 방안 §17-3 `:1153` |
