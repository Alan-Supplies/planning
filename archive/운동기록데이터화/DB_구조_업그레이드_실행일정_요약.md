## 결론

> **2026-08-26(수) ~ 2026-09-14(월) · 투입 14영업일 · 캘린더 3주**
> 단, **운영(prod) 배포는 일정에서 제외**했습니다. 제외한 것은 아래 "일정 밖에 남는 것"에 있습니다.

**전제 3가지**: 코드 작성 1일/배치 · 배포 검증 1일/배치 · 운영 배포 제외.
이 전제에서 기간을 결정하는 것은 코드가 아니라 **"그 컬럼에 넣을 값이 이미 정해져 있는가"** 하나입니다.
배치 단위는 **lib 버전업 1회 = 1배치** — `gymboxx-app-server`가 `gymboxx-lib`을 고정 pin하므로 이것이 최소 릴리스 단위입니다.

## 임계 경로는 코드가 아니다 — 줄어들지 않는 4가지

1. **§5 장비 29종 회신(09/10)** — 전체 종료일을 결정하는 유일한 항목. 코드 2일 vs 회신 대기 11영업일.
2. **§1 29종 검수 회신(09/03)** — 늦으면 배치 4가 자동분까지만 나가고 29종 주 효과가 빔. 다만 유산소 시간 목표는 계산 가능하고 막히는 건 **균형 세션 목표**뿐.
3. **§9·10·11 리허설 1일** — 32.9만 행 리빌드 실측. 물리 시간이라 코드로 줄일 수 없음.
4. **§11 세트 강도 수집률 판정** — 실사용 누적 + 입력 화면 필요. 화면 수요 조사가 미결이라 **v2 일정에 넣지 않음**.

**인원을 2배로 늘려도 캘린더 이득은 최대 4일**입니다(배치 3·4 병렬 → 코드 트랙 14→11일, 그러나 §5 회신이 09/10). 반면 **검수 목록을 68→29종으로 줄인 것만으로 8일을 벌었습니다.**

> v1 45영업일 → v2 14영업일로 줄어든 31일의 대부분은 코드를 빨리 써서가 아니라 **(a) 운영 배포 제외 (b) 실측으로 블로커 소멸 (c) 사람이 볼 목록 축소** 때문입니다.

## 일정 밖에 남는 것 (운영 배포 제외분)

**운영 배포를 제외하면 3주로 보이지만 아래가 뒤에 남습니다.**

- **prod DDL 적용 주체·승인 절차 — 미확인.** v1·v2 두 번의 조사로도 확인되지 않은 **유일한 잔여 질문**. `gymboxx-lib`의 `src/sqlv4/`는 "이력 기록용이며 실제 DB 반영은 별도 프로세스"로만 명시돼 있음
- lib 버전업 → 소비 저장소 pin 갱신 → 각 서버 배포 사이클 **최대 6회** (CI/CD 리드타임 미확인)
- 32.9만 행 **prod 리빌드 실행 창구** 확보·롤백 준비·대응 인력
- 구 컬럼·구 테이블 폐기(`exercise.type`, `exercise_function`) — 병행 기간이 prod 관찰에 종속
- **신규 유산소 등록 시 강도 필수 입력 규칙** — 방안 477행이 "필요"로 명시하나 §17-1 8개 순위 어디에도 미배정. `cardio_intensity`가 NULL 허용이라 DB가 막지 못함 → **후속 별건**
- §11 세트 강도 **입력 화면** (수요 조사 미결)
- **어드민 화면 부재** — 성격 태그·장비 분류 관리 화면이 어느 저장소에도 없어 검수 결과를 SQL로 옮겨 적어야 함. 다음 정정 때 같은 문제가 반복됨
- MACHINE `equipment_type` 다수결 값의 **오용 방지** — 대표 표기일 뿐이므로 "지점별 가능 운동" 판정에 쓰면 틀림(정확한 경로는 `exercise_machine → gym_machine`)
