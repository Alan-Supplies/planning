# 무게 단위 정책 수정사항 (2026-09-02)

기존 문서(`DB_구조_업그레이드_방안.md` §9 등)는 수정하지 않는다. 이 문서가 §9 무게 단위 환산 절을 대체하는 **정본**이며, 기존 문서와 충돌하는 부분은 이 문서를 따른다.

대상 PR: [suppliesfitness/gymboxx-lib#267](https://github.com/suppliesfitness/gymboxx-lib/pull/267) (TECH-999)

## 1. 변경된 정책

| 항목 | 기존 설계 (문서 §9) | 변경 후 |
|---|---|---|
| `user_exercise_set_history.weight` | 회원 입력 원값(kg 또는 lb) | **킬로그램 고정** |
| `weight_unit enum('kg','lb')` 세트 컬럼 | 신설 (상위 세션 `weight_type` 복사) | **신설하지 않음** |
| `weight_kg decimal(10,7)` STORED 생성 열 | 신설 (lb × 0.45359237) | **신설하지 않음** |
| `weight_kg` 인덱스 | 신설 (최고 중량 조회용) | **신설하지 않음** — 필요해지면 `weight` 에 별도 추가 |
| 파운드 입력 | 원값 저장 + 환산 열 병행 | **입력 경로에서 kg 으로 환산해 저장. 원값(lb)은 저장하지 않음** |
| `user_exercise_session_history.weight_type` | 원값 보존 · 세트 행으로 복사 | 원값 보존 · **복사하지 않음**. 역할은 회원의 표시 단위 선호로 한정 |

핵심: 저장 계층은 단위를 모른다. 무게는 언제나 kg 이고, 단위 변환은 입력·표시 경계에서만 일어난다.

## 2. 그렇게 바꾼 이유

기존 설계는 "입력 원값 보존 + 계산용 환산 열" 이라는 이중 보관 구조였고, 이 때문에 세트 행에 단위 컬럼 복사(백필 30만 행)와 STORED 생성 열이 필요했다. 단위를 저장하지 않기로 하면 그 이중 구조 자체가 사라진다.

- 계산(랭킹·훈련량)이 `weight` 를 그대로 쓸 수 있다 — 단위 분기·NULL 전파(단위 미상 → 환산값 NULL) 문제가 없어진다.
- 30만 행 단위 백필과 STORED 생성 열 추가(테이블 재구축)가 마이그레이션에서 빠져 잠금 시간이 줄어든다.
- lb 원값을 버리는 손실은 표시 단위 선호(`weight_type`)로 역환산해 복원 가능한 범위이며, 정밀도 손실은 소수 7자리 저장에 비해 무시할 수준이다.

## 3. 기존 데이터를 환산 백필하지 않는 근거

문서 §9 실측: 세션 `weight_type='lb'` 9,507건(7.1%), `kg` 124,276건. 표면상 lb 값이 섞여 있는 것처럼 보이지만, 저장 경로를 확인한 결과 **환산 로직이 존재한 적이 없다**.

- `gymboxx-app-server` `src/modules/user-exercise/user-exercise.dao.ts` — `weight_type` 을 세션 행에 그대로 저장할 뿐, 세트 `weight` 에 대한 단위 분기·환산이 없다.
- `gymboxx-app-server` `src/modules/user-exercise/user-exercise.service.ts` — 훈련량 합산이 `Σ count × weight` 로 단위 구분 없이 더한다.

즉 서버는 처음부터 `weight` 를 kg 로 취급해 왔고, `weight_type` 은 표시 단위 선호로만 쓰였다. 따라서 과거 행에 대한 환산 UPDATE 는 하지 않는다.

**단, 이 전제는 마이그레이션 실행 전에 반드시 데이터로 확인한다.** 마이그레이션 SQL §1(4) 에 점검 쿼리를 주석으로 남겼다.

```sql
select h.weight_type, count(*) c, avg(s.weight) avg_w, max(s.weight) max_w
from user_exercise_set_history s
join user_exercise_session_history h on h.id = s.user_exercise_session_history_id
where s.weight is not null
group by h.weight_type;
```

판정 기준: 두 집단의 평균·최댓값이 비슷한 범위면 전제가 맞다(전건 kg). lb 집단이 kg 집단의 2배 안팎으로 크면 원값이 그대로 쌓여 온 것이므로 **마이그레이션을 중단하고 환산 백필을 다시 논의한다.**

## 5. app-server 후속 조건 (gymboxx-lib 범위 밖)

- 회원이 파운드로 입력하면 **저장 전에 kg 으로 환산**한다(× 0.45359237). `weight` 에는 환산값만 넣고 원값은 남기지 않는다.
- 화면 표시는 `user_exercise_session_history.weight_type` 을 보고 조회 시점에 역환산한다.
- 대리키 전환에 따른 저장 방식 전환("삭제 후 재삽입" → "갱신")은 기존 조건 그대로 유효하다 — 미전환 시 새 UNIQUE 위반(errno 1062).

## 6. 후속 이슈에 미치는 영향

- TECH-1000 `user_personal_record_history` 는 최고 기록 값을 `weight_kg` 컬럼명으로 두기로 했었다. 세트 쪽에 `weight_kg` 가 사라졌으므로 **컬럼명을 `weight` 로 맞출지 결정 필요** — 값 자체는 어느 쪽이든 kg 이다.
- 랭킹·최고 중량 조회 인덱스는 `weight_kg` 가 아니라 `weight`(또는 `(exercise_id, weight)` 복합)에 걸어야 한다. 쿼리 확정 후 별도 판단.
