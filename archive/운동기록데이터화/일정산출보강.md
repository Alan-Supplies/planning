# 운동 기록 데이터 개선 일정 산정 및 검증 계획

## 1. 목적

`Gymboxx 데이터 자산화` 프로젝트의 `[운동기록]` 이슈에 대해 다음을 명확히 한다.

* 전체 일정 산정 근거
* 이미 사용한 일정과 남은 일정
* 병행 가능한 작업
* 외부 검수가 필요한 항목
* 개발 완료와 최종 완료의 차이
* PO에게 설명할 일정과 전제 조건

---

## 2. 대상 이슈

| 이슈        | 내용                                                                   | 최초 산정 |
| --------- | -------------------------------------------------------------------- | ----: |
| TECH-997  | `exercise_function`을 `exercise_effect`, `exercise_recommend_tag`로 분리 |    3일 |
| TECH-998  | 부위 매핑 제약 교체 및 `axis`, `cardio_intensity`, `measure_type` 추가          |    1일 |
| TECH-999  | 세트 이력 단위·환산무게·대리키·수행시각 추가 및 마이그레이션                                   |    2일 |
| TECH-1000 | 개인 최고 기록 테이블 신설·초기 적재·배치                                             |    2일 |
| TECH-1001 | 장비 분류 12종 및 부위 기여도 추가                                                |    1일 |

단순 합계는 9일이지만, TECH-997과 TECH-998의 일부 작업을 같은 릴리스와 검증 과정에서 병행할 수 있으므로 전체 달력 일정은 8영업일로 산정한다.

## 3. 전체 일정

| 기간    | 작업                            |       일정 |
| ----- | ----------------------------- | -------: |
| 1~2일차 | TECH-997 중심 조사·설계·구현          |    사용 완료 |
| 3일차   | TECH-997·TECH-998 통합 마무리 및 검증 |       1일 |
| 4~5일차 | TECH-999 테이블 변경·마이그레이션        |       2일 |
| 6~7일차 | TECH-1000 테이블·초기 적재·배치        |       2일 |
| 8일차   | TECH-1001 장비 분류·부위 기여도 적용     |       1일 |
| 합계    |                               | **8영업일** |

현재 TECH-997에 2영업일을 사용했다.

남은 일정은 다음과 같다.

```text
TECH-997·998 마무리   1일
TECH-999             2일
TECH-1000            2일
TECH-1001            1일
-------------------------
남은 일정             6일
```

## 4. TECH-997과 TECH-998 병행 근거

TECH-997과 TECH-998은 완전히 독립된 작업이 아니다.

두 이슈 모두 다음 영역을 공유한다.

* `gymboxx-lib`의 운동 데이터 구조
* app-server의 운동 추천 모듈
* DB 마이그레이션
* 앱 코드 전환
* 스테이징 검증
* 릴리스 및 배포 준비

현재 두 이슈 모두 lib와 app-server PR이 존재한다.

따라서 TECH-997의 3일과 TECH-998의 1일을 완전히 순차적으로 더하지 않고, 남아 있는 통합 검증과 릴리스 준비를 한 번에 처리한다.

### 병행 일정이 성립하기 위한 조건

* TECH-997의 주요 코드 구현이 완료돼 있어야 한다.
* TECH-998도 주요 코드와 자동 매핑이 준비돼 있어야 한다.
* 두 이슈의 DDL을 같은 스테이징 검증 과정에서 확인할 수 있어야 한다.
* lib와 app-server 배포 순서를 함께 검증할 수 있어야 한다.
* 외부 검수 대기 중에도 자동 처리 부분을 진행할 수 있어야 한다.

이 조건이 충족되지 않으면 병행으로 절약한 1일을 다시 일정에 추가해야 한다.

## 5. 이슈별 일정 근거

## TECH-997: function을 effect와 recommend tag로 분리

### 전체 공수

3영업일

### 사용 공수

2영업일

### 남은 작업

* DDL을 개발 환경에 실제 실행하고 데이터 검증
* lib 배포 후 app-server `package-lock.json` 갱신
* 추천 로직의 effect/tag 경로 강제 실행 테스트
* 외부 검수 요청 및 결과 반영
* 앱 코드 전환 확인 후 기존 `exercise_function` 제거
* 백업 테이블 유지 및 복구 가능성 확인

### 일정 근거

`exercise_function`은 두 컬럼으로 구성된 N:N 테이블이지만, 작업 범위는 테이블 구조 변경에 한정되지 않는다.

다음 내용을 함께 확인해야 한다.

* 기존 function의 비즈니스 의미
* `exercise_effect`와 `exercise_recommend_tag`의 역할 차이
* 기존 87행의 분리 기준
* 근력 운동 225종의 추가 백필
* 겸함 운동과 예외 운동 처리
* 추천 알고리즘의 조회 경로 변경
* 기존 추천 결과의 비회귀
* 앱 코드와 DB 마이그레이션의 배포 순서

따라서 3일은 작은 N:N 테이블을 파악하는 시간이 아니라, 데이터 의미 분리·백필·추천 로직 전환·마이그레이션과 검증을 포함한 전체 공수다.

### 검증 범위

현재 운영 추천은 다음 상태다.

* 부위 추천: 100%
* 기능 추천: 0%
* 기능 추천을 평가할 사용자 행동·성과 데이터가 부족함

따라서 운영 결과가 동일하다는 사실만으로 TECH-997의 성공을 판단할 수 없다.

다음 검증을 별도로 수행한다.

* 기존 87행의 effect/tag 매핑 누락 확인
* 신규 데이터의 중복 및 참조 무결성 확인
* 근력 백필 225종과 제외 28종 확인
* 부위 추천 100% 결과의 비회귀 확인
* 테스트 환경에서 effect/tag 추천 비율 강제 적용
* 각 운동 목적에 대해 추천 결과가 비어 있지 않은지 확인
* 기존 알고리즘과 새 알고리즘의 결과 차이 확인

검증 가능한 범위는 다음과 같다.

| 검증 대상           |  가능 여부 |
| --------------- | -----: |
| 데이터 이전 정확성      |     가능 |
| 새 추천 로직의 기술적 동작 |     가능 |
| 현재 부위 추천 비회귀    |     가능 |
| 정책 규칙 반영 여부     |     가능 |
| 실제 추천 품질 개선     | 현재 불가능 |

실제 추천 품질은 사용자 행동·성과 데이터가 축적된 이후 별도로 검증한다.

2영업일

### 2일차: 마이그레이션과 검증

* 스테이징 리허설
* 실행 시간 측정
* 마이그레이션 중 잠금과 DML 영향 확인
* 운영 실행 창 확정
* `weight_unit` 백필
* 대리키 전건 부여
* 환산 무게 검증
* 운영 실행
* 사후 건수와 데이터 검증
* 실패 시 복구 절차 확인

### 일정 근거

추가 1일은 단순 SQL 실행 시간이 아니라 스테이징 리허설, 운영 실행, 데이터 검증과 복구 확인을 포함한 마이그레이션 작업 시간이다.

실제 잠금과 DML 영향은 MySQL/RDS 버전 및 ALTER 종류에 따라 달라질 수 있으므로 스테이징에서 확인한다.

### 공수

2영업일

### 1일차: 테이블과 조회 구조 신설

* `personal_record_type` 신설
* `user_personal_record_history` 신설
* 현재 최고 기록 구분 방식 구현
* 측정 방식별 기록 종류 검증
* 기존 세트 이력과의 참조 구조 구현

### 2일차: 공통 계산 로직·초기 적재·배치

* 최고 기록 계산 로직 구현
* 초기 최고 기록 적재
* 초기 적재 결과 검증
* 같은 계산 로직을 사용하는 일일 배치 구현
* 배치 재실행과 중복 방지 검증

### 0.5일을 별도로 추가하지 않는 근거

초기 적재와 일일 배치는 동일한 최고 기록 계산 로직을 사용한다.

마이그레이션 과정에서 공통 계산 및 검증 코드를 만들고, 이를 일일 배치 실행 형태로 연결한다. 따라서 배치 작성 0.5일은 마이그레이션 작업 1일 안에 포함한다.

초기 적재와 일일 배치가 별도의 구현을 요구하는 것으로 확인되면 0.5일을 추가한다.

### 선행 작업

TECH-1000은 다음 이슈가 완료돼야 착수할 수 있다.

* TECH-998의 `measure_type`
* TECH-999의 환산 무게와 세트 대리키

초기 적재 범위가 확정되지 않으면 마이그레이션과 배치 범위를 결정할 수 없다.

## 6. 외부 검수 관리 원칙

외부 검수 시간은 Alan의 개발 공수와 분리한다.

각 이슈를 진행하면서 검수가 필요한 항목을 빠르게 요청하고, 회신 전 진행 가능한 자동 작업은 먼저 진행한다.

완료 상태는 다음 두 가지로 구분한다.

* 개발 및 자동 적용 완료
* 외부 검수 반영까지 최종 완료

외부 검수가 늦어지면 개발 공수는 변하지 않지만 최종 완료일은 달라질 수 있다.

### 공통 작성 형식

```markdown
## 외부 확인

- 확인 요청 대상:
- 확인 요청 내용:
- 요청 시점:
- 회신 전 진행 가능한 범위:
- 회신이 필요한 완료 조건:
- 회신 지연 시 처리:
```

## 8. 일정에 포함되지 않는 항목

다음은 8영업일의 개발 공수에 포함하지 않는다.

* 외부 검수자의 회신 대기시간
* 사용자 행동 데이터 축적 시간
* 실제 추천 품질 평가
* 기획 변경으로 새로 추가되는 범위
* 운영 배포 승인 대기시간
* 초기 적재 범위가 바뀌면서 발생하는 추가 구현
* TECH-1000의 초기 적재와 배치가 별도 로직으로 확인될 경우의 추가 0.5일

## 9. 일정 위험

다음 조건이 발생하면 8영업일 일정이 늘어날 수 있다.

1. TECH-997과 TECH-998을 동일한 검증·릴리스 흐름으로 처리할 수 없는 경우
2. TECH-998의 PK 교체가 예상보다 큰 잠금이나 마이그레이션 문제를 일으키는 경우
3. TECH-999 운영 마이그레이션 실행 창이 늦어지는 경우
4. TECH-1000 초기 적재 범위가 늦게 확정되는 경우
5. 초기 적재와 일일 배치가 동일한 계산 로직을 재사용할 수 없는 경우
6. 외부 검수 결과로 자동 매핑 규칙이 변경되는 경우
7. 현재 운동 기록 시스템 개선으로 인해 DB 구조가 다시 변경되는 경우

위 조건이 발생하면 기존 일정 안에 억지로 포함하지 않고, 변경된 범위와 추가 일정을 별도로 제시한다.

## 10. PO에게 설명할 내용

> 전체 일정은 최초 착수부터 8영업일로 산정했습니다. 첫 이틀 동안 TECH-997을 중심으로 진행했고, 동일한 운동 데이터 구조와 추천 모듈을 수정하는 TECH-998도 일부 함께 진행했습니다. 두 이슈는 lib·app-server 릴리스와 스테이징 검증 과정을 공유할 수 있어 남은 작업을 합쳐 하루로 산정했습니다.
>
> 이후 세트 이력 구조 변경과 마이그레이션에 2일, 개인 최고 기록 테이블·초기 적재·배치에 2일, 장비 분류와 부위 기여도 작업에 1일이 필요합니다.
>
> TECH-1000의 초기 적재와 일일 배치는 동일한 최고 기록 계산 로직을 재사용하는 전제로 2일 안에 포함했습니다. 별도 로직이 필요하다고 확인되면 0.5일을 추가하겠습니다.
>
> 외부 검수는 각 이슈를 진행하면서 바로 요청하고, 회신 전 가능한 자동 작업은 먼저 진행하겠습니다. 개발 및 자동 적용은 8영업일 기준이지만, 외부 검수 반영까지의 최종 완료일은 회신 일정에 따라 달라질 수 있습니다.
>
> 현재 운영은 부위 추천 100%이고 기능 추천은 비활성화돼 있으므로, 운영 결과만으로 TECH-997을 검증하지 않겠습니다. 데이터 이전 정확성, 현재 추천 비회귀와 테스트 환경의 effect/tag 강제 실행까지 완료 조건에 포함하겠습니다. 실제 추천 품질은 사용자 행동 데이터가 축적된 이후 별도로 검증해야 합니다.
